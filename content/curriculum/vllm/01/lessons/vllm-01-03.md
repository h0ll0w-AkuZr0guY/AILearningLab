title: "Engine Arguments · SchedulerConfig"

[SchedulerConfig 参数区](https://docs.vllm.ai/en/latest/configuration/engine_args/#schedulerconfig)承诺了本课用到的一组公开契约：`--max-num-batched-tokens`（单次迭代最多处理的 token 数）、`--max-num-seqs`（单次迭代最多序列数）、`--enable-chunked-prefill`（prefill 可按剩余预算切块）、`--long-prefill-token-threshold`（超过该长度的 prompt 每次分配被钳制）、`--scheduling-policy`（`fcfs` 或 `priority`）。这些参数共同决定「每步批多大、谁能进批、进不去时谁被挤出去」。版本边界 v0.26.0。

### 逐段讲解

- 调度约束在 `__init__` 固化：`max_num_running_reqs = scheduler_config.max_num_seqs`、`max_num_scheduled_tokens` 默认回落 `max_num_batched_tokens`，即每步同时受「token 预算」与「序列上限」双重约束。
- 抢占的触发点在 **running 轮**：为正在运行的请求分配新 KV 块时，`allocate_slots` 返回 None（KV 耗尽），调度器进入 `while True` 抢占循环，逐个挤出 running 中的请求腾块，直到块够或抢占到当前请求自身（`preempted_req == request` 时 `break`）。
- 抢占选择：PRIORITY 策略选 `max(running, key=(priority, arrival_time))` 即最不重要者；FCFS 策略直接 `running.pop()` 队尾——running 是按调度顺序维护的，队尾是「最近才被调进 running、已算 token 最少」的请求。
- 被挤出的请求经 `_preempt_request`（L1212-1234）处理：释放全部 KV 块、`num_computed_tokens = 0`、`num_preemptions += 1`、`waiting.prepend_request` 放回队首。
- 关键的门禁：waiting 接纳循环只在 `if not preempted_reqs` 时执行（L666）。也就是说只要本步发生过抢占，本步就不再接纳任何 waiting 请求；被抢占者放回队首后，下一轮以最高优先权重新 prefill。
- waiting 轮内 `allocate_slots` 失败只会 `break` 拒绝该请求，**不会**再触发抢占；`enable_chunked_prefill=False` 且 `num_new_tokens > token_budget` 时同样 `break`。

```python
self.max_num_running_reqs = self.scheduler_config.max_num_seqs
self.max_num_scheduled_tokens = (
    self.scheduler_config.max_num_scheduled_tokens
    if self.scheduler_config.max_num_scheduled_tokens is not None
    else self.scheduler_config.max_num_batched_tokens
)

# schedule() running 轮：块分配失败 -> 抢占循环
with record_function_or_nullcontext("schedule: allocate_slots"):
    while True:
        new_blocks = self.kv_cache_manager.allocate_slots(
            request, num_new_tokens,
            num_lookahead_tokens=self.num_lookahead_tokens,
        )
        if new_blocks is not None:
            break                    # 块够：调度成功
        # KV 耗尽：抢占最低优先级请求腾出块
        if self.policy == SchedulingPolicy.PRIORITY:
            preempted_req = max(
                self.running,
                key=lambda r: (r.priority, r.arrival_time),
            )
            self.running.remove(preempted_req)
        else:
            preempted_req = self.running.pop()   # FCFS：队尾
        self._preempt_request(preempted_req, scheduled_timestamp)
        preempted_reqs.append(preempted_req)
        if preempted_req == request:
            break                    # 抢占到自己：本步无法继续

# schedule() waiting 轮：本步有抢占则整轮跳过
if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:
    while (self.waiting or self.skipped_waiting) and token_budget > 0:
        num_running = len(self.running) + self.num_waiting_for_streaming_input
        if num_running >= self.max_num_running_reqs:
            break                    # 序列上限先耗尽：剩余 token 预算被放弃
        # ... 计算 num_new_tokens 并分配块；失败只 break，不抢占

# _preempt_request：抢占的完整代价
def _preempt_request(self, request: Request, timestamp: float) -> None:
    self._free_request_blocks(request)     # 1. 释放全部 KV 块
    request.status = RequestStatus.PREEMPTED
    request.num_computed_tokens = 0        # 2. 已算的 token 全部作废
    request.num_preemptions += 1           # 3. 记录抢占次数（指标可观测）
    self.waiting.prepend_request(request)  # 4. 放回队首，下轮优先重新调度
    self.reset_preempted_req_ids.add(request.request_id)
```

## 导读

把一个 GPU 当「自习室」来想：`max_num_batched_tokens` 是自习室每轮能处理的「作业字数」，`max_num_seqs` 是每轮最多能坐的「人数」。座位没满但字数额度没了，或者额度还剩但座位满了，都得停下来。而抢占是「作业写到一半时，座位被收回，写过的字全部作废，回到门口重新排队」——作废重算，就是抢占最贵的部分。

本课回答三个问题：每步批大小为什么由 token 与 seq 两个预算共同决定；KV 耗尽时「挤谁出去」由策略决定；被挤出去的请求代价是什么。需要先纠正一个常见直觉：V1 的抢占**不是**为了「给新请求让位」而主动发起的，它只在 running 轮 KV 块分配失败时被动触发，而且触发后本步立即停止接纳新请求。第三课建立在第一课的统一预算之上：`_preempt_request` 把 `num_computed_tokens` 清零，正是第一课「欠账」模型的一个分支动作。

## 分章正文

### 为什么 batch 不是越大越好

kicker: "01 · OBSERVE"

直觉上「批越大吞吐越高」在 LLM serving 里有三个反例。第一，显存：每个序列都要占 KV cache 块，批越大可用块越少，`allocate_slots` 失败的概率越高，而失败会直接触发抢占风暴。第二，延迟：`max_num_batched_tokens` 决定单步计算量，单步时长随 token 数增长，TTFT 与 TPOT 都被拉高，超出 SLO 就得不偿失。第三，CPU 开销：V1 的每个调度步都要在 CPU 上重新组装输入批次，批太大时 GPU 等 CPU，出现「GPU 利用率很高但吞吐不涨」。

所以 vLLM 用两个参数而不是一个：token 预算管「每步算多少」，序列上限管「多少路并行」。生产调优时两者都要试：短 prompt 高并发场景常被 `max_num_seqs` 卡住，长 prompt 场景常被 `max_num_batched_tokens` 卡住。

#### 本章结论

批大小不是越高越好；token 预算与序列上限是两个独立的瓶颈维度。

### 两道预算：谁先耗尽谁决定批大小

kicker: "02 · BUDGETS"

源码里 waiting 接纳循环的退出条件有两个：`token_budget > 0` 与 `num_running < max_num_running_reqs`。前者是 token 额度，后者是座位数。每接纳一个请求都要同时扣 token 与占座位，因此实际批大小 = min(「token 预算能容纳的请求数」,「max_num_seqs - 当前 running」)。

一个典型误判：只调 `max_num_batched_tokens` 到 8192，却忘了 `max_num_seqs` 默认 128，短对话场景根本用不满 token 预算就被座位数拦住。反过来，`max_num_seqs` 调大但 token 预算不变，decode 请求多了会把预算全部吃掉，新 prefill 进不来。这两个参数必须按负载形态一起调。

#### 本章结论

批大小是两个预算的交集；只调一个参数无法扩大批容量。

### 抢占的触发点：running 轮的 KV 耗尽

kicker: "03 · TRIGGER"

抢占循环嵌套在 running 轮的 `allocate_slots` 调用处：每个 running 请求每步都要为「新 token 的 KV 块」分配空间，当空闲块不够时 `allocate_slots` 返回 None，调度器进入 `while True`：挤出一个 running 请求、把它的块归还、再试；块还不够就再挤下一个；直到块够，或者挤到了当前请求自己（`preempted_req == request` → `break`）。

注意这个触发点与直觉相反：抢占不是因为「新请求来了要腾位子」，而是因为「正在跑的请求没块可用了」。KV 预算（由第四课的 `gpu_memory_utilization` 决定）过小、或并发跑得太满，才会频繁走到这里。这也解释了为什么诊断抢占要先看 `kv_cache_usage_perc` 而不是看请求队列长度。

#### 本章结论

抢占由 running 轮 KV 块分配失败触发；它是显存压力事件，不是接纳决策事件。

### 挤谁出去：FCFS 与 PRIORITY 的差异

kicker: "04 · SELECT"

PRIORITY 策略选 `max(running, key=(priority, arrival_time))`：priority 值越大越不重要（`lower value means earlier handling`），同优先级时按到达时间排序，即「最不重要且最晚到」的请求被挤掉。FCFS 策略直接 `running.pop()` 队尾——running 列表按调度顺序维护，队尾是「最近才被调进 running」的请求，理论上已算 token 最少、重算成本最低。

这个选择有明确的工程动机：抢占代价近似正比于已计算 token 数（全部作废重算），所以两个策略都倾向牺牲「投入最少」的请求。区别在于：FCFS 用「调度顺序」近似「投入量」，PRIORITY 允许调用方用 priority 字段表达业务重要度，宁可牺牲投入多但次要的请求。

#### 本章结论

两个策略都优先挤「投入最少」者；PRIORITY 额外按显式优先级排序。

### 抢占的代价：释放 KV、清零进度、回队重算

kicker: "05 · COST"

`_preempt_request` 的四步把代价说得很清楚：释放全部 KV 块、`num_computed_tokens = 0`、`num_preemptions += 1`、放回 waiting 队首。关键在第二步：已计算的 prompt 部分全部作废，重新调度时要从头 prefill（除非前缀缓存命中，见自动前缀缓存特性）。这意味着一次抢占的实际成本 = 重算被抢占请求的全部已计算 token + 期间 GPU 被占用的机会成本。

量化一下：一个已算 1500 token 的请求被抢占，重算这部分要再跑一次同等量的 prefill；若抢占频繁（`num_preemptions` 指标持续增长），有效吞吐会被重算吃掉。vLLM 的缓解手段是前缀缓存（相同前缀的 KV 块可复用，抢占后命中缓存的部分不用重算）与 `long_prefill_token_threshold`（限制单次分配块大小，减少「大块占满后被迫挤人」的概率）。另外注意：发生抢占的这一步，waiting 接纳被整体跳过（`if not preempted_reqs`），所以抢占还会造成「本步零新请求入场」的连锁延迟。

#### 本章结论

抢占 = KV 释放 + 进度清零 + 回队重算，且触发抢占的步骤不再接纳新请求。

### chunked prefill 与阈值如何改变权衡

kicker: "06 · CHUNK"

`enable_chunked_prefill`（默认 True）允许把长 prompt 按剩余预算切块，因此「token 预算不够」不再必然导致拒绝——新请求可以先拿剩余预算的一部分进批。代价是切块本身降低 prefill 并行性（尾块重复加载权重）。`long_prefill_token_threshold`（默认 0 关闭）把单次分配钳制在阈值内，配合 `max_long_partial_prefills`（默认 1）限制同时进行的大块 prefill 数量，避免多个超大 prompt 反复切块互相拖慢。

权衡的完整画面是：预算大 → 单步吞吐高但延迟差、显存压力大；预算小 → 延迟好但 CPU 组装开销占比高；chunked 开 → 公平性好但大 prefill 变慢；阈值设大 → 大 prefill 保持并行但可能挤占 decode。没有全局最优，只有按负载形态选参数。

#### 本章结论

chunked 把「拒绝」变成「切块」，阈值控制切块的粒度；参数之间存在此消彼长。

### 从指标反推瓶颈

kicker: "07 · DIAGNOSE"

生产排障顺序：先看 `vllm:num_requests_waiting` 是否长期非零（在排队的请求说明某道预算被耗尽）；再看 `vllm:num_preemptions` 是否增长（在抢占说明 KV 块不足，是显存压力）；最后看 `vllm:kv_cache_usage_perc` 与 `vllm:iteration_tokens_total`。等待增长但无抢占 → token/seq 预算偏小；等待与抢占同增 → KV cache 偏小（调小 `max_model_len`、启用前缀缓存或换显存更大的卡）；迭代 token 数长期远低于 `max_num_batched_tokens` → 序列上限或单请求欠账不足。

这套诊断全部建立在第一、二课的概念上：预算、欠账、区间与抢占计数。第四课会继续拆显存预算如何决定 KV 块总数。

#### 本章结论

用 waiting、preemptions、kv_cache_usage 三组指标即可区分「预算太小」与「显存不足」。

## 核心机制

- 批大小 = min(token 预算可容纳数, max_num_seqs - running)，两个维度独立。
- 抢占由 running 轮 `allocate_slots` 失败触发；PRIORITY 挤掉最不重要者，FCFS 挤掉队尾（已投入最少者）。
- 抢占四步：释放 KV、`num_computed_tokens=0`、`num_preemptions+=1`、回队首等待；发生抢占的步骤跳过 waiting 接纳。
- chunked prefill 把「拒绝」变成「切块」，`long_prefill_token_threshold` 控制单块粒度。

## 常见误区

- 以为 `max_num_batched_tokens` 管「批里几个请求」；它是 token 数上限，请求数由 `max_num_seqs` 管。
- 认为抢占是「为了给新请求让位」而主动发起的；实际触发点是 running 轮 KV 块分配失败，且抢占后本步不再接纳新请求。
- 认为抢占只是「暂停」；`num_computed_tokens` 清零意味着已算部分作废重算。
- 在 FCFS 下用 priority 字段期望高优先级请求先被调度；`--scheduling-policy` 未选 priority 时该字段不生效。
- 只调 `max_num_batched_tokens` 忽略 `max_num_seqs`，短请求场景被座位数卡住。

## 实现变体

### 变体 A：FCFS 抢占（默认）

useWhen: "负载无显式优先级，追求简单与公平，抢占尽量选已投入最少的请求。"
tradeoff: "获得：实现简单、`running.pop()` 即队尾；牺牲：无法表达业务优先级，同优先级长请求可能反复被挤。"

#### 代码

```python
def preempt_fcfs(running: list[Request]) -> Request:
    return running.pop()   # 队尾：最近才进 running，已算 token 最少
```

### 变体 B：PRIORITY 抢占

useWhen: "调用方按业务重要度设置 priority，需要保证重要请求不被抢占。"
tradeoff: "获得：显式优先级与到达时间双排序；牺牲：堆维护成本、prepend 不再保证插队语义。"

#### 代码

```python
def preempt_priority(running: list[Request]) -> Request:
    return max(running, key=lambda r: (r.priority, r.arrival_time))
```

## 可运行示例

```python
class Request:
    def __init__(self, rid: str, prompt: int, priority: int = 0,
                 arrival: int = 0, computed: int = 0) -> None:
        self.id = rid
        self.num_prompt_tokens = prompt
        self.num_computed_tokens = computed
        self.priority = priority
        self.arrival_time = arrival
        self.num_preemptions = 0


def select_victim(running: list[Request], policy: str) -> Request:
    """复刻抢占选择：PRIORITY 取 (priority, arrival) 最大者，FCFS 取队尾。"""
    if policy == "priority":
        victim = max(running, key=lambda r: (r.priority, r.arrival_time))
        running.remove(victim)
        return victim
    return running.pop()


def schedule_step(running: list[Request], waiting: list[Request],
                  budget: int, max_seqs: int, blocks_free: int,
                  policy: str = "fcfs") -> dict[str, int]:
    """复刻 schedule()：running 轮块不足触发抢占；有抢占则该步跳过 waiting 轮。"""
    out: dict[str, int] = {}
    preempted = False
    req_index = 0
    while req_index < len(running) and budget > 0:
        req = running[req_index]
        if blocks_free >= 1:
            out[req.id] = 1                  # decode 每步 1 token
            budget -= 1
            blocks_free -= 1
            req.num_computed_tokens += 1
            req_index += 1
            continue
        # KV 块耗尽：抢占直到块够或抢占到自己（真实代码为 while True 循环）
        preempted_self = False
        while blocks_free < 1 and running:
            victim = select_victim(running, policy)
            blocks_free += victim.num_computed_tokens   # 释放其 KV 块
            victim.num_computed_tokens = 0              # 进度清零
            victim.num_preemptions += 1
            waiting.insert(0, victim)                   # 回队首
            preempted = True
            if victim.id in out:                        # 本步已调度过：回收预算
                budget += out.pop(victim.id)
                req_index -= 1                          # 真实代码：补偿列表位移
            if victim is req:
                preempted_self = True
                break                                   # 抢占到自己：本步放弃
        if preempted_self:
            break
        if blocks_free < 1:
            break
        out[req.id] = 1
        budget -= 1
        blocks_free -= 1
        req.num_computed_tokens += 1
        req_index += 1

    if preempted:
        return out                       # 本步有抢占：waiting 轮整体跳过
    for req in list(waiting):
        if budget <= 0 or len(running) >= max_seqs:
            break                        # token 或序列预算耗尽
        n = min(req.num_prompt_tokens, budget)
        if blocks_free < n:
            break                        # 块不足：直接拒绝，不触发抢占
        out[req.id] = n
        budget -= n
        blocks_free -= n
        req.num_computed_tokens = n
        running.append(req)
        waiting.remove(req)
    return out


# PRIORITY：低优先级但已投入最多的 low 被挤掉，high/mid 保住
low = Request("low", 100, priority=5, arrival=10, computed=50)
mid = Request("mid", 100, priority=3, arrival=15, computed=50)
high = Request("high", 100, priority=1, arrival=20, computed=50)
newbig = Request("new", prompt=200)
r = [low, mid, high]
waiting = [newbig]
assign = schedule_step(r, waiting, budget=300, max_seqs=4, blocks_free=1,
                       policy="priority")
assert low.num_preemptions == 1 and low.num_computed_tokens == 0
assert high.num_preemptions == 0 and mid.num_preemptions == 0
assert "low" not in assign and "high" in assign and "mid" in assign
assert "new" not in assign                      # 本步有抢占，waiting 轮被跳过
assert low in waiting                           # 被抢占者回到 waiting 队首

# FCFS：队尾（最近进 running 的 c）被挤掉
a = Request("a", 50, computed=50)
b = Request("b", 50, computed=50)
c = Request("c", 50, computed=50)
w = [Request("new2", prompt=200)]
assign2 = schedule_step([a, b, c], w, budget=300, max_seqs=4,
                        blocks_free=1, policy="fcfs")
assert c.num_preemptions == 1 and c.num_computed_tokens == 0
assert "a" in assign2 and "b" in assign2 and "c" not in assign2
assert "new2" not in assign2                    # waiting 轮被跳过
assert c in w                                   # c 回到 waiting 队首

# 无抢占时 waiting 轮正常接纳；序列上限独立生效
a2 = Request("a2", 50, computed=50)
b2 = Request("b2", 50, computed=50)
small = Request("small", prompt=10)
assign3 = schedule_step([a2, b2], [small], budget=300, max_seqs=2,
                        blocks_free=100, policy="fcfs")
assert "small" not in assign3                   # max_seqs=2 已满，座位预算拦住

big = Request("big", prompt=100)
assign4 = schedule_step([], [big], budget=200, max_seqs=4, blocks_free=100,
                        policy="fcfs")
assert assign4 == {"big": 100}                  # 预算充足时整个 prompt 一次给完
```

## 搭积木复现

### 积木 1：实现两道预算的接纳条件

写 waiting 循环，同时检查 `token_budget > 0` 与 `num_running < max_num_seqs`，用「预算足但座位满」「座位足但预算缺」两个用例断言。

### 积木 2：实现块分配与失败探测

加入 `allocate_slots` 与 KV 块计数器，断言 running 轮块耗尽时无法继续分配。

### 积木 3：实现 FCFS 抢占循环

块不足时 `running.pop()`，把 victim 的已算 token 释放回块池并清零，断言 victim 是队尾且块池恢复。

### 积木 4：实现 PRIORITY 抢占与 waiting 轮门禁

按 `(priority, arrival_time)` 选 victim；发生抢占后本步跳过 waiting 接纳，victim 回队首，下一步以最高优先权重新调度。断言「有抢占 → 无新请求入场」。

### 积木 5：对照上游源码

对照 `_preempt_request`（scheduler.py L1212-1234）与 `if not preempted_reqs` 门禁（L666），列出省略的 encoder cache 释放、spec 草稿清理与异步 KV 加载分支，说明多模态请求的抢占为何额外释放 encoder 缓存、异步加载中的请求为何不可抢占。

## 自检

### 问题

`max_num_batched_tokens=2048`、`max_num_seqs=32`，31 个请求在 running 中，KV 块池已耗尽。此时一个 100 token 的新请求到达。请描述下一个调度步的完整行为：running 轮会发生什么、谁可能被抢占、waiting 轮是否执行、被抢占请求的计数器如何变化。

### 站内答案

结论：running 轮第一个需要新块的请求会触发抢占循环，挤出一个 running 请求腾出 KV 块；本步有抢占时 waiting 轮被整体跳过，新请求本步不会被接纳；被抢占请求 `num_computed_tokens=0`、`num_preemptions += 1`、KV 块全部归还、回到 waiting 队首。机制：抢占不是「给新请求让位」的主动决策，而是 running 轮 `allocate_slots` 返回 None 时的被动应急；PRIORITY 选 `max(running, key=(priority, arrival_time))`，FCFS 选 `running.pop()` 队尾。源码证据：scheduler.py v0.26.0 的 running 轮抢占循环（L571-599）、`_preempt_request`（L1212-1234）、waiting 轮门禁 `if not preempted_reqs and ...`（L666）与序列上限检查（L673）；`max_num_running_reqs = scheduler_config.max_num_seqs` 在 L110。可运行验证：把本课示例的 `schedule_step` 用 31 个 running 请求、`blocks_free=0` 重跑，断言本步有抢占、`"new"` 不在返回字典、victim 的计数被清零。工程取舍：抢占的代价是重算 victim 已计算的全部 token，因此两个策略都倾向牺牲「投入最少」的请求；生产上若 `num_preemptions` 持续增长，应缓解 KV 压力（调小 `max_model_len`、启用前缀缓存、调低并发或增大显存），而不是调大 batch 参数——batch 越大 KV 越紧，抢占反而更频繁。适用边界：本结论针对纯文本生成与同步调度；异步 KV 加载（KV 连接器）中的请求不可抢占，多模态请求抢占时还会释放 encoder 缓存，这些场景的代价模型需另行展开。
