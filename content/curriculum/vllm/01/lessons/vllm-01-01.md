官方博客的调度器一节明确承诺：V1 调度器「removes the traditional distinction between 'prefill' and 'decode' phases by treating user-given prompt tokens and model-generated output tokens uniformly」（取消了 prefill 与 decode 两个阶段之间的传统区分，把用户给定的 prompt token 与模型生成的输出 token 统一对待），并把调度决策表示为 `{request_id: num_tokens}` 字典。这一节只承诺调度语义，不承诺 kernel 层是否仍然按 prefill/decode 优化。调度预算参数见 [Engine Arguments · SchedulerConfig](https://docs.vllm.ai/en/latest/configuration/engine_args/#schedulerconfig)（`--max-num-batched-tokens`、`--enable-chunked-prefill`）。本文以 v0.26.0（2026-07-27 发布）为版本边界。

### 逐段讲解

- `schedule()` 开头先用注释声明「调度器里没有 decode 阶段也没有 prefill 阶段」，随后把每步预算初始化为 `token_budget = self.max_num_scheduled_tokens`，该值在 `__init__` 中默认回落到 `max_num_batched_tokens`。
- 先遍历 `self.running`（正在生成的请求），对每个请求计算 `num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens`，即「还差多少个 token 没算」，再被 `long_prefill_token_threshold`、`token_budget`、`max_model_len` 逐层钳制。
- KV 块分配失败时进入抢占分支：PRIORITY 策略选 `max(running, key=(priority, arrival_time))` 即最不重要者，FCFS 策略直接 `running.pop()` 队尾；随后 `_preempt_request` 把它放回 waiting。
- 分配成功就把请求记入 `scheduled_running_reqs`，`num_scheduled_tokens[request_id] = num_new_tokens`，并 `token_budget -= num_new_tokens`。
- running 轮完后才轮到 WAITING 请求，同一份 `token_budget` 继续被消耗；`enable_chunked_prefill=False` 且新请求超出剩余预算时直接 `break`，不再接纳新请求。

### 源码节选

```python
def schedule(self, throttle_prefills: bool = False) -> SchedulerOutput:
    self.current_step += 1
    # NOTE(woosuk) on the scheduling algorithm:
    # There's no "decoding phase" nor "prefill phase" in the scheduler.
    # Each request just has the num_computed_tokens and
    # num_tokens_with_spec. num_tokens_with_spec =
    # len(prompt_token_ids) + len(output_token_ids) + len(spec_token_ids).
    # At each step, the scheduler tries to assign tokens to the requests
    # so that each request's num_computed_tokens can catch up its
    # num_tokens_with_spec. This is general enough to cover
    # chunked prefills, prefix caching, speculative decoding,
    # and the "jump decoding" optimization in the future.

    scheduled_new_reqs: list[Request] = []
    scheduled_running_reqs: list[Request] = []
    preempted_reqs: list[Request] = []
    num_scheduled_tokens: dict[str, int] = {}
    token_budget = self.max_num_scheduled_tokens   # 每步可调度的 token 总数

    # 第一轮：RUNNING 请求（正在生成的请求，每步通常只需 1 个新 token）
    req_index = 0
    while req_index < len(self.running) and token_budget > 0:
        request = self.running[req_index]
        num_new_tokens = (
            request.num_tokens_with_spec        # 已拥有的 token 总数（含草稿）
            + request.num_output_placeholders   # 异步调度预留的占位 token
            - request.num_computed_tokens       # 已完成计算的 token 数
        )
        num_new_tokens = min(num_new_tokens, token_budget)
        num_new_tokens = min(                   # 位置不得超过模型最大长度
            num_new_tokens,
            self.max_model_len - request.num_computed_tokens
            - self.num_sampled_tokens_per_step,
        )
        # 为新 token 分配 KV cache 块；失败则抢占最低优先级请求（省略）
        new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens)
        if new_blocks is None:
            break
        scheduled_running_reqs.append(request)
        num_scheduled_tokens[request_id] = num_new_tokens
        token_budget -= num_new_tokens          # 同一预算被 running 与 waiting 共享
        req_index += 1

    # 第二轮：WAITING 请求（新请求或抢占后回队的请求），消耗剩余预算
    if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:
        while (self.waiting or self.skipped_waiting) and token_budget > 0:
            request = request_queue.peek_request()
            num_new_tokens = request.num_tokens - num_computed_tokens
            num_new_tokens = min(num_new_tokens, token_budget)
            if num_new_tokens == 0:
                break
            # ... 分配 KV 块、记录 num_scheduled_tokens、扣减 token_budget
```

删减说明：生产实现还包含 encoder 输入预算、spec decode 的草稿 token 记账、KV 连接器、PauseState 暂停态、Mamba 块对齐等分支，这里只保留「统一 token 预算」这条主路径；被删分支不会改变本课结论，但会影响多模态与混合架构下的精确预算计算。

## 导读

一次典型的「长 prompt 饿死 decode」事故是这样发生的：在线服务同时收到一个 8000 token 的文档问答请求和几十个正在流式输出的短对话请求。旧式两阶段调度器把迭代分成 prefill-only 和 decode-only 两种，一个长 prefill 会独占整个迭代，短对话的每个 token 都要等它跑完才能生成，首 token 延迟和 TPOT 一起劣化，客户端纷纷超时重试，队列越积越长。

V1 调度器的答案是：不再区分「这是 prefill 请求」还是「这是 decode 请求」，只问「这个请求还有多少 token 没算」。每个请求维护 `num_computed_tokens`（已算完的 token 数）与 `num_tokens_with_spec`（应有 token 总数）两个计数器，调度器每步在固定 `token_budget` 内尽可能让前者追平后者。decode 请求每步需要 1 个 token，长 prompt 的 prefill 每步需要几百个 token，两者只是「欠账多少」的差别，在同一份预算里公平竞争。

理解这条主路径的价值在于：chunked prefill、prefix caching、speculative decoding 在 V1 里不是三个特例分支，而是同一个「追平计数器」模型的自然结果。本课是模块 01 的地基：第二课讲 TTFT/TPOT 如何从事件时间戳算出来，第三课讲预算不足时的抢占代价，都建立在本课的 `token_budget` 与两个计数器之上。

## 分章正文

### 从「长 prompt 饿死 decode」的故障现场进入

kicker: "01 · OBSERVE"

给一个只有 decode 的在线场景：50 个请求同时在流式输出，每步每请求 1 个新 token，共 50 token；此时进来一个 2000 token 的 prefill。在两阶段调度下，调度器要么先排空当前 decode 批（长 prefill 等到天荒地老），要么立刻切到 prefill-only 迭代（50 个在线对话全部停顿一个 prefill 时长）。前者把 TTFT 推到分钟级，后者把 TPOT 拉到秒级——不管选哪边，都有一个用户群体被牺牲。

V1 不再做这个二选一：50 个 decode 各 1 token，加上 prefill 的 1950 token（如果预算够），一个迭代同时完成。真正可观察的变化是「长 prefill 不再阻塞 decode」：只要 `max_num_batched_tokens` 预算允许，prefill 被切成块混进每个迭代，decode 每步照常推进。

#### 本章结论

阶段划分消失的直接收益是：长 prefill 与 decode 共享同一个 token 预算，不再互相饿死。

### 两个计数器与统一 token 预算

kicker: "02 · MODEL"

每个请求携带两个关键计数器。`num_computed_tokens` 表示该请求已完成 forward 计算的 token 数；`num_tokens_with_spec` 是 prompt token 数、已生成 output token 数与 spec（草稿）token 数之和，即「这个请求应该算到的位置」。每步需要补算的量是二者之差；调度器的任务是在 `token_budget` 内让尽量多的请求追平。

这个模型统一了三种情况：新请求刚进队时 `num_computed_tokens=0`、`num_tokens_with_spec=len(prompt)`，欠账是全部 prompt；正在生成的请求每次追平 1 个 token，欠账恒为 1（除非有草稿 token 或异步占位）；被抢占的请求回队后 `num_computed_tokens` 被清零，欠账回到整个 prompt 加已生成部分。三个状态在调度器眼里都是同一个减法。

#### 代码

```python
class Request:
    def __init__(self, prompt_tokens: list[int], max_tokens: int) -> None:
        self.prompt_token_ids = prompt_tokens
        self._output: list[int] = []
        self.num_computed_tokens = 0          # 已算完的 token 数
        self.spec_token_ids: list[int] = []   # 草稿 token

    @property
    def num_tokens_with_spec(self) -> int:
        return len(self.prompt_token_ids) + len(self._output) + len(self.spec_token_ids)

    def owed(self) -> int:                    # 每步需要补算的 token 数
        return self.num_tokens_with_spec - self.num_computed_tokens
```

`owed()` 就是源码里 `num_new_tokens` 的骨架。decode 请求 `owed()==1`，未开始的 prefill 请求 `owed()==len(prompt)`，已抢占的请求 `owed()==len(prompt)+len(output)`。

#### 本章结论

统一预算把「prefill 还是 decode」降维成「还欠多少 token」，这是 V1 调度语义的唯一不变量。

### schedule() 主路径：running 优先，预算逐请求扣减

kicker: "03 · SOURCE"

源码主路径分两轮。第一轮遍历 `self.running`：对每个请求算出 `num_new_tokens`，依次被长 prefill 阈值、`token_budget`、`max_model_len` 钳制，然后调 `kv_cache_manager.allocate_slots` 为新 token 分配 KV 块；分配失败说明显存不足，进入抢占分支（本课第三课展开）。分配成功就扣减 `token_budget` 并继续下一个。

第二轮处理 waiting：新请求逐个出队，`num_new_tokens = request.num_tokens - num_computed_tokens`（这里用 `num_tokens` 而不是 `num_prompt_tokens`，因为被抢占恢复的请求已经带了一部分输出 token），同样受 `token_budget` 约束。值得注意的边界是：如果 `enable_chunked_prefill=False` 且新请求需要的 token 数超过剩余预算，调度器直接 `break`——它宁可浪费剩余预算，也不把一个 prefill 切成两半，这是旧行为的残留开关。

#### 本章结论

running 先于 waiting、同一预算共享扣减、块分配失败触发抢占，是 `schedule()` 的三条主路径事实。

### chunked prefill：预算不够时如何切分

kicker: "04 · CHUNK"

当一个新请求的 prompt 有 3000 token 而剩余预算只有 800 时，调度器不会拒绝它：`num_new_tokens = min(3000, 800) = 800`，先算前 800 个，该请求留在 running（`is_prefill_chunk` 标记为 True），下一步继续追平剩余部分。这就是 chunked prefill——它不需要任何阶段切换代码，只是「欠账没还完就接着还」。

代价是切分点破坏整段 prefill 的并行性：一个 3000 token 的 prefill 拆成 4 块，每块都是一次独立的 forward，中间要重新加载权重、重新启动 kernel，尾块的实际吞吐低于一次性 prefill。因此 vLLM 提供 `long_prefill_token_threshold`（默认 0 关闭）把超长 prompt 的每次分配钳制在阈值内，配合 `max_long_partial_prefills` 控制同时进行的部分 prefill 数量，避免一个超大 prompt 反复切块拖垮吞吐。

#### 本章结论

切分是统一预算的自然结果；`enable_chunked_prefill` 是旧开关，`long_prefill_token_threshold` 是新阈值，两者共同决定「一块切多大」。

### max_model_len 与位置钳制：decode 的隐形上限

kicker: "05 · LIMIT"

统一预算还有一个容易忽略的钳制：`num_new_tokens = min(num_new_tokens, max_model_len - num_computed_tokens - num_sampled_tokens_per_step)`。decode 请求即使预算充足，一旦当前位置达到 `max_model_len`，欠账也不允许继续增长——`owed()` 永远为 0，调度器不再给它分配 token，请求只能走向 finish。

这条钳制解释了为什么「统一预算」不等于「无限生成长度」：模型长度是架构硬约束，调度器只负责在约束内分配。spec decode 场景下草稿 token 会临时抬高 `num_tokens_with_spec`，让欠账出现「负值修正」，但位置钳制始终以 `num_computed_tokens` 为参照，保证不会越界。

#### 本章结论

统一预算之上仍有 `max_model_len` 位置硬边界；decode 的欠账被钳制为 0 时请求进入收尾。

### 取消阶段划分获得的能力与代价

kicker: "06 · ENGINEERING"

获得的能力：chunked prefill、prefix caching、speculative decoding 全部落到同一个「追平计数器」模型里，调度器不再为每种特性写一套 `if prefill then ... else ...` 分支；`{request_id: num_tokens}` 的输出也让前端（model runner）可以一次性把不同长度的序列打包进同一 kernel 批次。

付出的代价：调度语义与执行细节解耦后，「prefill 还是 decode」的信息仍需要传给 kernel 层（例如 FlashAttention 仍按是否满序列优化），所以调度器用 `is_prefill_chunk` 等标记保留阶段信息；另外，统一预算要求每次 forward 都重新组装输入序列，无法像旧实现那样对纯 decode 批做固定的 CUDA graph 复用，需要额外的 graph capture 机制兜底。工程取舍是：调度层简单化，执行层用标记与编译缓存补偿。

#### 本章结论

统一预算是调度层的简化，不是执行层的删除；阶段信息以标记形式继续存在，供 kernel 与编译优化使用。

## 核心机制

- 每个请求只有两个计数器：`num_computed_tokens` 与 `num_tokens_with_spec`，欠账 = 二者之差。
- 每步共享 `token_budget`（默认回落 `max_num_batched_tokens`），running 先于 waiting，逐请求扣减。
- chunked prefill 是「欠账没还完就继续还」的自然结果，不需要阶段切换代码。
- `max_model_len` 位置钳制让 decode 欠账归零并收尾；`long_prefill_token_threshold` 控制单块大小。

## 常见误区

- 认为「取消阶段划分」意味着 kernel 也不再区分 prefill 与 decode；实际上调度层统一，执行层仍用 `is_prefill_chunk` 等标记区分。
- 把 `num_tokens_with_spec` 当成 prompt 长度；它是 prompt + output + spec 的总和，decode 阶段恒比 `num_computed_tokens` 大 1（无草稿时）。
- 以为 `max_num_batched_tokens` 是「每步最多几个请求」；它是 token 数上限，请求数上限是 `max_num_seqs`，两者独立。
- 认为 chunked prefill 永远更快；切块会牺牲整段 prefill 的并行性，长 prompt 需要阈值与部分 prefill 数量配合。

## 实现变体

### 变体 A：传统两阶段调度（V0 风格）

useWhen: "不需要混合长短请求，或目标是把实现固定在 prefill-only / decode-only 的严格批次上。"
tradeoff: "获得：批次边界简单、容易做固定图优化；牺牲：长 prefill 与 decode 互相阻塞，chunked prefill 需要额外分支，延迟公平性差。"

#### 代码

```python
def schedule_v0_style(phase: str, pending: list[Request], budget: int) -> dict[str, int]:
    out: dict[str, int] = {}
    if phase == "decode":
        for req in pending[:budget]:          # 每个 decode 请求只给 1 个 token
            out[req.id] = 1
    else:
        for req in pending:                   # prefill 阶段整段给完
            if req.num_prompt_tokens <= budget:
                out[req.id] = req.num_prompt_tokens
                budget -= req.num_prompt_tokens
    return out
```

### 变体 B：V1 统一预算

useWhen: "在线混合负载，长 prompt 与流式输出同时存在，需要延迟公平与通用调度。"
tradeoff: "获得：prefill 与 decode 共享预算、chunked prefill 零成本表达；牺牲：调度与 kernel 需要解耦、每次 forward 重新组装输入。"

#### 代码

```python
def schedule_v1_style(running: list[Request], waiting: list[Request],
                      budget: int) -> dict[str, int]:
    out: dict[str, int] = {}
    for req in running + waiting:             # 统一队列，只看欠账
        if budget <= 0:
            break
        owed = min(req.owed(), budget)
        if owed:
            out[req.id] = owed
            budget -= owed
    return out
```

## 可运行示例

```python
class Request:
    """模拟 vllm/v1/request.py 的计数器：computed 追平 total。"""

    def __init__(self, rid: str, prompt: int, max_tokens: int = 8) -> None:
        self.id = rid
        self.num_prompt_tokens = prompt
        self.max_tokens = max_tokens
        self.num_computed_tokens = 0   # 已完成 forward 的 token 数
        self.num_output_tokens = 0     # 已生成的输出 token 数（prefill 结束时为 1）
        self.is_prefill_chunk = False

    def owed(self) -> int:
        # 与 Request.num_tokens_with_spec - num_computed_tokens 等价（无 spec 时）
        return (self.num_prompt_tokens + self.num_output_tokens
                ) - self.num_computed_tokens


def schedule_step(running: list[Request], waiting: list[Request],
                  budget: int, chunked: bool = True) -> dict[str, int]:
    """复刻 schedule() 的两轮结构：running 优先，waiting 消耗剩余预算。"""
    out: dict[str, int] = {}
    for req in list(running):
        if budget <= 0:
            break
        n = min(req.owed(), budget)
        if n > 0:
            out[req.id] = n
            budget -= n
    for req in list(waiting):
        if budget <= 0:
            break
        n = min(req.owed(), budget)
        if n == 0:
            continue
        if not chunked and n < req.owed():
            break   # 关闭 chunked：剩余预算装不下整个 prompt，整批停止接纳
        out[req.id] = n
        budget -= n
    return out


def step(running: list[Request], waiting: list[Request],
         budget: int = 32, chunked: bool = True) -> dict[str, int]:
    """执行一步调度并推进计数器。"""
    assigned = schedule_step(running, waiting, budget, chunked)
    for rid, n in assigned.items():
        req = next(r for r in running + waiting if r.id == rid)
        req.num_computed_tokens += n
        if req in running:
            if req.num_computed_tokens >= req.num_prompt_tokens:
                # 只有 prefill 已完成的请求才是 decode：每步采样 1 个输出 token
                req.num_output_tokens += 1
                if req.num_output_tokens >= req.max_tokens:
                    running.remove(req)     # 达到 max_tokens，收尾
        else:
            waiting.remove(req)
            if req.num_computed_tokens < req.num_prompt_tokens:
                req.is_prefill_chunk = True     # 欠账未还完，切块留在 running
            else:
                req.is_prefill_chunk = False    # prefill 完成，同时得到首个输出 token
                req.num_output_tokens = 1
            running.append(req)
    return assigned


d1 = Request("d1", prompt=4, max_tokens=6)
d1.num_computed_tokens = 4
d1.num_output_tokens = 1                        # 首个 token 已在 prefill 收尾步采样
d2 = Request("d2", prompt=4, max_tokens=6)
d2.num_computed_tokens = 4
d2.num_output_tokens = 1
long_prefill = Request("p1", prompt=200, max_tokens=1)

# 一个长 prefill 与两个 decode 在同一预算内共存（chunked 开启）
r, w = [d1, d2], [long_prefill]
first = step(r, w, budget=32)
assert first["d1"] == 1 and first["d2"] == 1    # decode 每步仍只补 1 个 token
assert first["p1"] == 30                        # 其余预算全部给了 prefill 第一块
assert d1.num_computed_tokens == 5 and long_prefill.num_computed_tokens == 30
assert long_prefill.is_prefill_chunk is True    # 没还完，留在 running

# 累计多步：prefill 被切块逐步追平，decode 全程不被饿死
steps = [first]
for _ in range(6):
    steps.append(step(r, [], budget=32))
assert long_prefill.num_computed_tokens == 200  # 欠账全部追平
assert d1 not in r and d2 not in r              # 两个 decode 都已收尾
assert all(s["d1"] == 1 for s in steps[1:4])    # decode 每步 1 token，从未间断

# 关闭 chunked：预算不足时新 prefill 整批被拒，剩余预算被浪费
d3 = Request("d3", prompt=4, max_tokens=3)
d3.num_computed_tokens = 4
d3.num_output_tokens = 1
p2 = Request("p2", prompt=40, max_tokens=1)
assign = schedule_step([d3], [p2], budget=16, chunked=False)
assert assign == {"d3": 1}                      # p2 未被接纳，budget 只给了 decode
assert p2.num_computed_tokens == 0              # p2 仍在等待队列
```

## 搭积木复现

### 积木 1：定义两个计数器与欠账

先实现 `Request` 的 `num_computed_tokens`、`num_tokens_with_spec` 与 `owed()`，用一个只有 1 个请求的最小用例验证 decode 欠账恒为 1。

### 积木 2：实现 running 优先的预算扣减

按源码第一轮逻辑写循环：running 在前、逐请求 `min(owed, budget)`、扣减预算。断言「running 耗尽预算后 waiting 拿到 0」。

### 积木 3：加入 waiting 接纳与 chunked 切块

第二轮处理 waiting，`num_new_tokens` 超预算时切成块并打 `is_prefill_chunk` 标记。断言切块后请求留在 running 且下一步继续追平。

### 积木 4：加入 max_model_len 钳制与 decode 收尾

当 `num_computed_tokens` 到达上限时欠账归零，decode 请求不再被调度并走向完成。断言收尾请求从 running 移除。

### 积木 5：对照上游源码

把积木 2–4 与 `scheduler.py` 的 `schedule()` 逐行对照，列出删除的 encoder 预算、spec 记账、KV 连接器分支分别会丢失哪些生产保证（多模态预算、草稿 token 追平、远端 KV 加载）。

## 自检

### 问题

一个 3000 token 的新请求与 30 个正在 decode 的请求（每步 1 token）同时存在，`max_num_batched_tokens=1024`。第一轮 running 结束后新请求能拿到多少 token？它在调度器眼中与一个 decode 请求的本质区别是什么？`enable_chunked_prefill=False` 时行为如何变化？

### 站内答案

结论：running 轮先给 30 个 decode 各 1 token，消耗 30；新请求拿 `min(3000, 1024-30)=994`，`is_prefill_chunk=True` 留在 running，下一步继续追平剩余 2006。机制：调度器不区分阶段，只看 `num_tokens_with_spec - num_computed_tokens` 的欠账；decode 欠账恒为 1，新 prefill 欠账 3000，两者在同一个 `token_budget` 内按序扣减。源码证据是 `vllm/v1/core/sched/scheduler.py` v0.26.0 `schedule()`（L425-530）：running 循环在前（L473 起）、`num_new_tokens = min(num_new_tokens, token_budget)`（L509）、waiting 循环在 `if not preempted_reqs` 之后（L664 起）且共享同一 `token_budget`；`Request.num_tokens_with_spec` 定义在 `vllm/v1/request.py` L271。可运行验证：把本课示例的 `step()` 用 30 个 decode 请求重跑，断言第一轮 `p1` 得到 994、随后多步逐步追平。工程取舍：切块牺牲整段 prefill 并行性，所以生产环境对超长 prompt 设 `long_prefill_token_threshold` 并限制 `max_long_partial_prefills`；如果 `enable_chunked_prefill=False`，waiting 循环在 `num_new_tokens > token_budget` 时直接 `break`（scheduler.py L868-871），剩余预算被浪费、新请求整批等待，decode 不再被阻塞但长 prompt 的 TTFT 会显著劣化。适用边界：本结论针对纯文本生成；多模态 encoder 输入有独立的 encoder 预算，spec decode 会把草稿 token 计入 `num_tokens_with_spec`，这些场景的精确预算要另算。
