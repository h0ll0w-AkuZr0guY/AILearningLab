### 逐段讲解

- `__init__`（L59 起）：请求进入引擎时一次性固化 `request_id`、`prompt_token_ids`、`sampling_params.max_tokens`、`arrival_time`（未显式传入时用 `time.time()`）与 `priority`（默认 0）；生成模型必须有 `max_tokens`，池化模型强制 `max_tokens=1`，否则抛 `ValueError`。
- `num_prompt_tokens`（L177-179）：由 `length_from_prompt_token_ids_or_embeds` 从 token ids 或 embeds 算出，是请求形状的第一项「输入长度」。
- `_all_token_ids`（L181-184）：初始复制 prompt token ids；每生成一个输出 token 由 `append_output_token_ids`（L215-231）追加，于是 `num_tokens = len(self._all_token_ids)` 在请求生命周期内单调增长。
- `num_tokens_with_spec`（L271-272）：`len(_all_token_ids) + len(spec_token_ids)`——调度器计算「欠账」时用到的总数，spec decode 的草稿 token 也计入。
- `__lt__`（L329-341）：priority 调度时堆排序的唯一依据——先比 `priority`，再比 `arrival_time`，最后比 `request_id`；FCFS 队列不依赖它，只按插入顺序 `popleft`。

## 导读

一个请求在调度器眼里不是「一句话」，而是一组数字：prompt 长度、`max_tokens`、`priority`、`arrival_time`，以及随生成不断增长的已生成 token 数。很多运维事故源于只看到「并发 32」却不知道这 32 个请求的输入输出长度分布——两个都是 32 并发的实例，一个跑 128 token 短问短答，一个跑 4096 长文档问答，吞吐与 TTFT 天差地别。本课把 Request 对象拆开，回答「这些字段如何变成调度器的一次决策」。

先建立反例：假设你给 `vllm serve` 开了 `--max-num-seqs 8`，然后同时收到 8 个 8192 token 的长 prompt。调度器第一轮算出欠账 8×8192 = 65536，远超 `max_num_batched_tokens`（默认由模型自动决定），于是每个请求都只被切一小块执行（chunked prefill）。你以为是「并发 8」，实际每个请求都在排队等自己的下一块。理解请求形状，才能解释这类现象。

本课与前五课的关系：vllm-01-01 讲「token 预算怎么被两轮循环扣减」，本课补充「预算的分子——`num_tokens_with_spec - num_computed_tokens`——由哪些字段构成」；vllm-01-08 讲队列，本课为它提供 `priority` 与 `arrival_time` 的排序语义。拆分理由：请求对象是「输入数据模型」，调度循环是「处理逻辑」，两者失败模式不同——字段错了会在源头污染所有决策，队列错了只会影响顺序。

## 分章正文

### 一次调度的账本从哪来

kicker: "01 · OBSERVE"

调度器每步只输出一个字典：`{request_id: num_tokens}`——本步每个请求处理多少个 token。这个数字不是拍脑袋，而是「欠账」：`num_tokens_with_spec - num_computed_tokens`。欠账为正说明还有 token 没算过：新请求欠整个 prompt，decode 中的请求欠 1（还没生成的那个），spec decode 还欠草稿 token。`num_computed_tokens` 记录已经分配过 KV 的 token 数，防止同一个 token 被重复计算。

观察实验：构造一个 `prompt=2048`、`max_tokens=128` 的请求。刚入队时 `_all_token_ids` 长度 2048，`num_computed_tokens=0`，欠账 2048；第一轮调度按预算切一块（比如 1024），`num_computed_tokens` 变 1024；再过一轮变成 2048，欠账归零，请求转入 decode；此后每步生成 1 个 token，`_all_token_ids` 涨到 2049、2050……直到 2176（2048+128）触发 `FINISHED_LENGTH_CAPPED`。整个生命周期里「欠账」这个量严格等于「还没分配 KV 的 token 数」。

#### 本章结论

调度账本 = `num_tokens_with_spec - num_computed_tokens`，它由 prompt 长度、已生成 token 数与 spec 草稿共同决定。

### Request 对象：五个决定形状的字段

kicker: "02 · MODEL"

`Request` 构造时固化五个关键量：

- `prompt_token_ids`（或 embeds）：输入 token 列表，决定 `num_prompt_tokens`。
- `max_tokens`：输出预算。生成模型来自 `sampling_params.max_tokens`，池化模型恒为 1。它是请求生命周期的硬上界——`_all_token_ids` 达到 `num_prompt_tokens + max_tokens` 就停止。
- `priority`：默认为 0。priority 调度时值越小越先处理，等于实现「付费插队」或「内部请求优先」。
- `arrival_time`：未传时用 `time.time()`。它是 priority 队列的次级键，也是 TTFT/排队时间指标的起点。
- `num_tokens_with_spec`：上述三个量的动态汇合（prompt + 已生成 + spec），随生成单调增长。

不变量：`num_tokens_with_spec = num_prompt_tokens + num_output_tokens + num_spec_tokens`；`num_computed_tokens ≤ num_tokens_with_spec`；`num_output_tokens ≤ max_tokens`。后两个不等式在调度器任何一步都必须成立，违反即 bug。

#### 代码

```python
class RequestShape:
    """最小请求形状模型：字段如何决定欠账与输出预算。"""
    def __init__(self, prompt_tokens: int, max_tokens: int,
                 priority: int = 0, arrival: float = 0.0):
        self.prompt_tokens = prompt_tokens
        self.max_tokens = max_tokens
        self.priority = priority
        self.arrival = arrival
        self.generated = 0          # 已生成输出 token 数
        self.spec = 0               # 草稿 token 数（简化）
        self.computed = 0           # 已分配 KV 的 token 数

    @property
    def num_tokens_with_spec(self) -> int:
        return self.prompt_tokens + self.generated + self.spec

    @property
    def debt(self) -> int:
        return self.num_tokens_with_spec - self.computed

    def is_finished(self) -> bool:
        return self.generated >= self.max_tokens
```

#### 本章结论

请求形状是五个字段的集合；`debt` 与 `is_finished` 都可由它们推出，不需要额外状态。

### priority 与 arrival_time：堆排序里的次序

kicker: "03 · SOURCE"

`__lt__`（request.py L329-341）定义 priority 队列的全序：`priority` → `arrival_time` → `request_id` → `id()`。这意味着一件事：**priority 相同就是 FCFS**——`arrival_time` 更早的请求先被弹出，`arrival_time` 由 `time.time()` 固化在入队瞬间。真正的「优先级」只在 `priority` 不同时才生效。

工程含义：`--scheduling-policy priority` 不是让高优先级请求抢占运行中的低优先级请求——抢占是另一套逻辑（KV 不足时 `_preempt_request`，见 vllm-01-03）。priority 只决定 **waiting 队列里的弹出顺序**。运行中的请求已经持有 KV 块，调度器不会因为来了更高优先级的请求就打断它（除非显存不够需要抢占腾块）。很多人误以为 priority 能「插队到正在执行的任务前面」，实际它只能让请求在等待队列里插队。

#### 本章结论

priority 只作用于 waiting 队列顺序：priority → arrival_time → request_id 全序；同 priority 退化为 FCFS，`arrival_time` 是天然 tie-breaker。

### 长请求、短请求与 max_tokens 的三种失败边界

kicker: "04 · FAILURE"

请求形状决定三类真实失败：

1. **超长 prompt 被忽略**：prompt 长度超过 `max_model_len`（默认由模型配置推导）的请求直接以 `FINISHED_IGNORED` 结束，finish reason 是 `length`——OpenAI 兼容 API 返回错误而不是生成。`RequestStatus.is_finished` 对 `FINISHED_IGNORED` 返回 True（L343 起，`status > PREEMPTED`）。
2. **长 prompt + 小预算导致饥饿**：`max_num_batched_tokens` 固定时，长 prefill 会被切成很多块，每块都要和其他 decode 竞争预算。`max_long_partial_prefills`（默认 1）限制同时有多少个长 prefill 在分块执行，避免它们占满整批。
3. **max_tokens=0 或缺失**：OpenAI 兼容层把缺省 `max_tokens` 填成模型默认（如 4096）；显式传 0 会直接校验失败。池化请求则强制 `max_tokens=1`（request.py L113-115），这是形状的又一个隐藏来源。

还有一个易错点：`sampling_params.max_tokens` 是**输出**预算，不是总长度预算。总长度 = `prompt + max_tokens`，必须 ≤ `max_model_len`，否则 `FINISHED_LENGTH_CAPPED` 或建图时报错。

#### 本章结论

prompt 超长 → ignored；长 prompt 挤占预算 → 分块饥饿（用 `max_long_partial_prefills` 限制）；max_tokens 是输出预算，与 prompt 之和受 `max_model_len` 约束。

### 从字段到实例级配置的边界

kicker: "05 · ENGINEERING"

请求形状是**请求级**的，实例配置是**实例级**的，二者不能混。`max_tokens`、`priority`、`prompt_token_ids` 属于单个请求；`max_num_batched_tokens`、`max_num_seqs`、`max_model_len`、`scheduling_policy` 属于引擎启动参数。调度器的每个决策都是「请求形状 × 实例配置」的联合：

- 一次迭代能处理多少 token = `min(token_budget, 剩余可分配 KV 块 × block_size)`；
- 一次迭代能容纳多少请求 = `min(剩余 running 名额, max_num_seqs)`；
- 单个请求能进入 running = `num_prompt_tokens ≤ 剩余 KV 容量`（`scheduler_reserve_full_isl` 默认开启时检查完整输入长度，防止先切块后抖动）。

实践中最大的形状陷阱是**用平均长度做容量规划**。请求长度分布有长尾：p99 prompt 可能是平均值的 10 倍。`vllm:request_prompt_tokens` 直方图能直接暴露这个分布，容量与并发上限应该按 p95/p99 而不是均值设计。

#### 本章结论

请求形状 × 实例配置联合决定每次调度；容量规划要按长度分布的分位数，不能按均值。

### 怎么验证：用直方图读形状分布

kicker: "06 · VERIFY"

`/metrics` 暴露两组直方图：`vllm:request_prompt_tokens`（每个请求的 prompt token 数）与 `vllm:request_params_max_tokens`（每个请求请求的输出预算）。这两组数据的桶分布就是线上请求形状的画像。诊断流程：看到 decode 吞吐远低于 roofline 上限（vllm-01-05 的方法）时，先拉 `request_prompt_tokens` 的 p50/p95/p99——如果长 prompt 占大头，瓶颈是 prefill 块竞争而非 decode；再拉 `request_params_max_tokens` 确认输出长度没有异常放大 KV 占用。用 `prompt_tokens` 直方图还能直接发现「某条调用链悄悄把输入从 128 提到 4096」这类回归。

#### 本章结论

`request_prompt_tokens` 与 `request_params_max_tokens` 直方图是请求形状的可观测画像，用于解释吞吐异常与发现输入回归。

## 核心机制

- 调度账本 = `num_tokens_with_spec - num_computed_tokens`，由 prompt 长度、已生成 token、spec 草稿动态决定。
- Request 固化五个形状字段：prompt 长度、max_tokens、priority、arrival_time、num_tokens_with_spec。
- `__lt__` 全序 = priority → arrival_time → request_id，priority 相同即 FCFS。
- max_tokens 是输出预算；prompt + max_tokens ≤ max_model_len，否则 ignored 或 length-capped。
- 请求级字段与实例级配置联合决定每次调度；容量按分位数而非均值设计。

## 常见误区

- 以为「并发 8」就是 8 个请求同时推进；实际受 token 预算与 KV 容量约束，长请求会被切块排队。
- 以为 priority 能抢占运行中的请求；priority 只决定 waiting 队列顺序，抢占是 KV 不足时的独立逻辑。
- 混淆 max_tokens 与总长度；输出预算之外还有 prompt，总和受 max_model_len 约束。
- 用平均 prompt 长度做容量规划；长尾分布下 p99 可能是均值的 10 倍。
- 忽略 arrival_time 的 tie-break 作用；priority 相同时它决定谁先被处理。

## 实现变体

### 变体 A：FCFS 队列（不比较字段）

useWhen: "默认部署，所有请求同等重要，要求行为可预测。"
tradeoff: "获得：实现简单（deque 的 append/popleft）、无排序开销；牺牲：无法区分请求优先级，紧急请求必须等前面全部处理完。"

#### 代码

```python
from collections import deque

class FCFSQueue:
    def __init__(self):
        self._q: deque[RequestShape] = deque()

    def add(self, r: RequestShape) -> None:
        self._q.append(r)            # 尾部进入

    def pop(self) -> RequestShape:
        return self._q.popleft()     # 头部离开：先进先出
```

### 变体 B：priority 堆队列（比较 __lt__）

useWhen: "需要付费优先级、内部请求优先或 SLA 分级时。"
tradeoff: "获得：priority 值小的请求先被处理，同优先级退化为 FCFS；牺牲：每次 push/pop O(log n)，且要求元素严格全序（request_id 兜底）。"

#### 代码

```python
import heapq

class PriorityQueue:
    def __init__(self):
        self._heap: list[RequestShape] = []

    def add(self, r: RequestShape) -> None:
        heapq.heappush(self._heap, r)   # 按 __lt__ 排序

    def pop(self) -> RequestShape:
        return heapq.heappop(self._heap)
```

## 可运行示例

```python
import heapq
import time


class RequestShape:
    """最小请求形状模型：字段决定欠账与输出预算。"""

    def __init__(self, request_id: str, prompt_tokens: int,
                 max_tokens: int, priority: int = 0,
                 arrival: float | None = None):
        self.request_id = request_id
        self.prompt_tokens = prompt_tokens
        self.max_tokens = max_tokens
        self.priority = priority
        self.arrival = arrival if arrival is not None else time.time()
        self.generated = 0
        self.spec = 0
        self.computed = 0

    @property
    def num_tokens_with_spec(self) -> int:
        return self.prompt_tokens + self.generated + self.spec

    @property
    def debt(self) -> int:
        return self.num_tokens_with_spec - self.computed

    def step_decode(self) -> None:
        """模拟一次 decode：生成 1 个 token，KV 立即分配。"""
        assert self.debt == 0 or self.is_prefill_pending(), \
            "decode 前欠账应为 0（prefill 已完成）"
        self.generated += 1
        self.computed += 1

    def is_prefill_pending(self) -> bool:
        return self.debt > 0

    def is_finished(self) -> bool:
        return self.generated >= self.max_tokens

    def __lt__(self, other: "RequestShape") -> bool:
        # 与 vllm/v1/request.py L329-341 同构：priority -> arrival -> id
        if self.priority != other.priority:
            return self.priority < other.priority
        if self.arrival != other.arrival:
            return self.arrival < other.arrival
        return self.request_id < other.request_id


def schedule_step(requests: list[RequestShape], budget: int) -> dict[str, int]:
    """按 vllm-01-01 的统一预算模型推进一步；返回 {id: num_tokens}。"""
    out: dict[str, int] = {}
    remaining = budget
    # running 优先：每个请求最多补 1 个 token（简化：不再区分 prefill 切块）
    for r in requests:
        if remaining <= 0:
            break
        out[r.request_id] = 1
        r.computed += 1
        remaining -= 1
    return out


# ---- 断言 1：请求形状决定欠账 ----
r = RequestShape("r1", prompt_tokens=2048, max_tokens=128)
assert r.num_tokens_with_spec == 2048
assert r.debt == 2048                       # 新请求欠整个 prompt
r.computed = 1024
assert r.debt == 1024                       # 切一块后欠账减半
r.computed = 2048
assert r.debt == 0                          # prefill 完成，转入 decode
r.step_decode()
assert r.generated == 1 and r.debt == 0
assert not r.is_finished()                  # 128 个输出还没完
for _ in range(127):
    r.step_decode()
assert r.is_finished()                      # 正好 128 个输出

# ---- 断言 2：priority 排序（priority -> arrival -> id）----
a = RequestShape("a", 10, 10, priority=0, arrival=1.0)
b = RequestShape("b", 10, 10, priority=1, arrival=0.0)   # 更早到达但优先级更低
c = RequestShape("c", 10, 10, priority=0, arrival=2.0)
heap = [b, c, a]
heapq.heapify(heap)
order = [heapq.heappop(heap).request_id for _ in range(3)]
assert order == ["a", "c", "b"], order     # priority 0 的 a、c 先于 b；a 比 c 早到

# ---- 断言 3：同 priority 退化为 FCFS（按 arrival）----
d = RequestShape("d", 10, 10, priority=0, arrival=5.0)
e = RequestShape("e", 10, 10, priority=0, arrival=3.0)
f = RequestShape("f", 10, 10, priority=0, arrival=4.0)
heap2 = [d, e, f]
heapq.heapify(heap2)
assert [heapq.heappop(heap2).request_id for _ in range(3)] == ["e", "f", "d"]

# ---- 断言 4：统一预算下长请求被切块 ----
long_req = RequestShape("long", 8192, 64)
short_reqs = [RequestShape(f"s{i}", 10, 10) for i in range(8)]
step = schedule_step([long_req] + short_reqs, budget=32)
# running 轮每个请求补 1：9 个请求耗 9，剩余 23 都给 long（简化模型）
assert step["long"] == 1                      # 简化调度每请求 1 token
assert sum(step.values()) == 9                # 预算 32 只用掉 9（简化）

# ---- 断言 5：max_tokens 是输出预算 ----
r2 = RequestShape("r2", 100, 5)
for _ in range(5):
    r2.step_decode()
assert r2.is_finished() and r2.num_tokens_with_spec == 105   # 100 + 5
```

## 搭积木复现

### 积木 1：实现最小请求形状

定义 `RequestShape`，字段为 prompt_tokens / max_tokens / priority / arrival，属性 `num_tokens_with_spec` 与 `debt`。用 2048/128 断言 `debt=2048`、逐步 `computed` 后 `debt` 归零。

### 积木 2：实现输出预算生命周期

加入 `generated` 与 `step_decode()`，断言每步 +1、`is_finished` 在 `generated == max_tokens` 时变 True，`num_tokens_with_spec = prompt + generated`。

### 积木 3：实现 __lt__ 全序

复刻 request.py L329-341 的 priority → arrival → id 三级比较，用三个请求断言堆排序顺序；再验证同 priority 时 arrival 决定次序。

### 积木 4：实现简化调度步

实现 `schedule_step(requests, budget)` 返回 `{id: num_tokens}`，断言 running 优先、预算耗尽即停；把 budget 改小观察长请求拿不到完整块。

### 积木 5：对照上游源码

对照 request.py v0.26.0 的 `__init__`（L59-211）、`num_tokens_with_spec`（L271）、`__lt__`（L329-341）与 `RequestStatus.is_finished`（L343 起）。说明本课简化遗漏：多模态 encoder token、spec decode 的独立记账、async scheduling 的 `num_output_placeholders`、流式请求的 `resumable`——生产形态的欠账还要加上这些项，但形状→账本的核心映射不变。

## 自检

### 问题

同一实例上同时提交两个请求：A 是 `prompt=64, max_tokens=32, priority=0`，B 是 `prompt=4096, max_tokens=8, priority=0`，两者到达时间 B 早 1 秒。分别回答：priority 调度下谁先进入 running？它们的 `num_tokens_with_spec` 在刚入队时各是多少？为什么 B 的 TTFT 可能反而比 A 长，尽管它更早被调度？

### 站内答案

结论：priority 相同（都为 0）时按 `arrival_time` 排序，B 更早到达所以 B 先进入 running；刚入队时 A 的 `num_tokens_with_spec = 64+0=64`，B 的 `= 4096+0=4096`。B 的 TTFT 更长是因为它的 prefill 欠账（4096）远大于 A（64），在 `max_num_batched_tokens` 预算下被切成多块，每块都要排队竞争——被调度得早不等于首 token 来得早。机制：`__lt__`（request.py L329-341）用 `priority → arrival_time → request_id` 排序，priority 相同时 FCFS，B 先出队；但出队只是「获得预算」，实际推进取决于 `num_tokens_with_spec - num_computed_tokens` 的欠账在每步 budget 内能还多少，长 prefill 需要多步。源码证据：request.py 的 `num_tokens_with_spec`（L271）与 `Request.__init__` 中 `self.arrival_time = ... or time.time()`（L95）、`self.priority = priority`（L83）；调度预算参数 `--max-num-batched-tokens`、`--scheduling-policy` 见 engine_args 的 SchedulerConfig 锚点。可运行验证：把本课示例的 `RequestShape` 建 A/B 两实例，断言 `heap` 弹出顺序是 B 先；再用 `schedule_step` 在 budget=32 下跑几步，观察 B 的 `debt` 从 4096 缓慢下降而 A 一轮完成。工程取舍：要压低长请求的 TTFT，可调大 `max_num_batched_tokens`（牺牲单步延迟）或限制 `max_long_partial_prefills` 让短请求插队；纯 priority 只能改 waiting 顺序，不能绕过预算约束。适用边界：本结论针对纯文本生成与默认 FCFS/priority 配置；多模态 encoder token 单独记账、spec decode 的草稿 token 计入 `num_tokens_with_spec`、async scheduling 还有 `num_output_placeholders` 预占，这些场景的精确账本需另算。
