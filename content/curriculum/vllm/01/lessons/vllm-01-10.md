### 逐段讲解

- `get_kv_cache_configs`（L2036 起）：根据 `kv_cache_memory_bytes`（显式指定时忽略 gpu_memory_utilization）或 `gpu_memory_utilization × 可用显存 - 模型权重与激活开销` 计算可分配给 KV cache 的总字节。
- 单块字节 = `block_size × 每 token KV 字节`（`num_layers × num_kv_heads × head_dim × dtype 字节 × 2`）；`num_gpu_blocks = kv_cache_bytes // 单块字节`——块数由可用字节与块大小共同决定。
- 块数被 `max_num_batched_tokens` 的推导反向影响：`max_num_batched_tokens = min(max_num_seqs, num_gpu_blocks)` 的估算逻辑保证单步 batch 不会超出 KV 容量。
- `watermark`（默认 0.0）：接入等待/抢占请求时要求保留 `watermark × num_gpu_blocks` 的空闲块，避免内存紧张时频繁驱逐与抢占——它不减少总块数，只降低「可用调度容量」的有效上界。
- `scheduler_reserve_full_isl`（默认 True）：调度器接纳新请求前检查完整输入序列长度能否放进剩余 KV，而不是只看第一个分块，防止「先接进来、再抖动」的过度接纳。

## 导读

「这台机器能跑多少并发」不是一句口号，而是一个可计算的容量方程：KV cache 字节 = `gpu_memory_utilization × 可用显存 - 权重与激活`，块数 = 字节 ÷ 块大小，可调度 token = 块数 × block_size（再扣 watermark 余量），最终并发上限还要受 `max_num_seqs` 与每个请求的 `max_model_len` 约束。本课把这个方程拆开，让你能回答「加一块 H100 能多服务多少请求」这种容量规划问题。

先建立反例：`--gpu-memory-utilization 0.92` 不等于「92% 显存都能给 KV cache」——它先把模型权重、CUDA graph、激活等开销从可用显存里扣掉，剩下的才乘 0.92。一台 80GB 的 H100 跑 70B 模型（权重约 140GB 需要多卡），单卡场景权重本身就可能占掉大头，KV cache 实际只有几个 GB。不理解这个扣减链，容量计算会高估数倍。

本课与前课的关系：vllm-01-04 讲了 `gpu_memory_utilization` 的基数（以什么为基数），本课把它推进到「块数 → 可调度 token → 并发上限」的完整方程；vllm-01-03 讲抢占，本课解释抢占为什么会发生（容量不足）+ watermark 如何缓解。拆分理由：容量方程（本课）与「抢占触发条件」（01-03）是「静态预算」与「动态冲突」两个独立失败面。

## 分章正文

### 一个容量不足的现场

kicker: "01 · OBSERVE"

单卡跑 8B 模型，`max_num_seqs=64`，长文档问答负载下 `kv_cache_usage_perc` 打到 0.99，`num_preemptions` 持续增长，TTFT 飙到秒级。直觉反应是「并发 64 太大了」，但把 `max_num_seqs` 降到 16 后 TTFT 反而更差——因为容量不足的根本原因是每个请求的 KV 占用太大（长 prompt + 长输出），不是请求数量本身。正确动作是压缩每请求 KV（降低 max_model_len、KV 量化、MLA）或加显存。

这个现象说明：容量模型必须同时看「块数 × 每请求块需求 × 并发」三个量，只看并发不看请求长度分布（vllm-01-06 的形状画像）就会误诊。

#### 本章结论

容量不足的根源是「每请求 KV × 并发 > 块容量」，降低并发不一定对症，压缩每请求 KV 或加显存才对症。

### 从可用显存到 KV 字节的扣减链

kicker: "02 · MODEL"

容量方程第一步：`kv_cache_bytes = 可用显存 - 权重 - CUDA graph - 激活 - 其余开销`，再乘 `gpu_memory_utilization`。vLLM 在 profile 阶段实测各模型权重与 graph 的实际占用，剩余空间才按利用率折算给 KV cache。`kv_cache_memory_bytes` 显式指定时跳过这条链（文档明确「手动设置后会忽略 gpu_memory_utilization」）。

不变量：`kv_cache_bytes ≤ gpu_memory_utilization × 可用显存`；`num_gpu_blocks = kv_cache_bytes // (block_size × bytes_per_token)`；`每请求最大 KV = max_model_len × bytes_per_token`。

#### 代码

```python
def kv_cache_capacity(available_bytes: float, weights_bytes: float,
                      graph_bytes: float, utilization: float,
                      block_size: int, bytes_per_token: float) -> dict:
    """可用显存 → KV 字节 → 块数 → 可调度 token 的完整链。"""
    kv_bytes = (available_bytes - weights_bytes - graph_bytes) * utilization
    kv_bytes = max(kv_bytes, 0.0)
    num_blocks = int(kv_bytes // (block_size * bytes_per_token))
    schedulable_tokens = num_blocks * block_size
    return {"kv_bytes": kv_bytes, "num_blocks": num_blocks,
            "schedulable_tokens": schedulable_tokens}
```

#### 本章结论

KV 容量 = 扣掉权重/图/激活后的显存 × 利用率；块数 = KV 字节 ÷ 块大小；可调度 token = 块数 × block_size。

### 从块数到并发上限的三重钳制

kicker: "03 · SOURCE"

并发上限不是单一数字，而是三重约束的最小值：

1. **KV 容量**：running 中所有请求的已分配 KV 块 ≤ `num_gpu_blocks - watermark 块`。`watermark` 默认 0.0，设 0.1 就保留 10% 块不参与接入。
2. **`max_num_seqs`**：running 请求数 ≤ `max_num_seqs`（单次迭代的序列硬上限）。
3. **`max_num_batched_tokens`**：单步 token 数 ≤ `min(max_num_seqs, 可分配块对应 token)`——chunked prefill 时它同时约束 batch 大小与 prefill 切块粒度。

`get_kv_cache_configs` 里 `max_num_batched_tokens = min(max_num_seqs, num_gpu_blocks // ...)` 正是把 1 与 3 联动：没有 KV 容量的 batch 上限是空话。`scheduler_reserve_full_isl`（默认 True）进一步要求「新请求的完整 prompt 必须放得进剩余容量」——这是第四重隐藏钳制，防止长请求先接入再抖动。

#### 本章结论

并发上限 = min(KV 容量 - watermark、max_num_seqs、max_num_batched_tokens、完整 ISL 可容纳)；四重钳制缺一不可。

### 失败路径：watermark=0 的抖动与容量高估

kicker: "04 · FAILURE"

容量模型有三个典型失败边界：

1. **watermark=0（默认）的抖动**：不保留余量时，短请求可以刚好填满所有块；下一个长请求接入失败触发抢占（vllm-01-03 的重算代价），被抢占请求回队后又要块——来回驱逐，`num_preemptions` 飙升、TTFT 剧烈抖动。生产负载有长度分布时建议设 watermark 0.05-0.1。
2. **容量高估**：用 `gpu_memory_utilization × 总显存` 估算 KV 容量，忽略权重/graph/激活扣减——高估 2-5 倍。`--num-gpu-blocks-override` 可以手动覆盖 profile 结果，但只用于测试抢占，生产用它掩盖容量错误会适得其反。
3. **max_num_batched_tokens 与 KV 不同步**：显式设了很大的 `--max-num-batched-tokens` 但 KV 块数不够，调度器按块数截断预算，配置看起来生效实际没生效——观测 `iteration_tokens_total` 直方图的桶顶是否达到设定值即可识破。

#### 本章结论

watermark=0 在高负载下引发抢占抖动；容量估算必须走完整扣减链；max_num_batched_tokens 受 KV 块数反向钳制。

### 容量模型的工程取舍

kicker: "05 · ENGINEERING"

容量规划的正确顺序：先按模型算 `bytes_per_token`（架构固定）与 `kv_cache_bytes`（显存与利用率决定），得到 `num_gpu_blocks`；再按目标负载的 p95 请求长度（vllm-01-06 直方图）算「每请求平均块需求」，两者相除得到理论并发；最后乘以安全系数（应对突发与抢占）。三个可调杠杆：`gpu_memory_utilization`（提高 → KV 更多但激活余量更少）、`block_size`（增大 → 单块容量大但内碎片多）、`watermark`（提高 → 更稳但峰值并发降）。不要用 `max_num_seqs` 硬顶并发——它只是上限，真实并发由 KV 容量决定。

#### 本章结论

容量规划 = 块数 ÷ 每请求块需求 × 安全系数；调利用率/块大小/watermark 三个杠杆，max_num_seqs 只是上限不是目标。

### 怎么验证：用指标反推容量状态

kicker: "06 · VERIFY"

`/metrics` 提供三个容量观测点：`vllm:kv_cache_usage_perc`（当前使用率）、`vllm:num_requests_running`（运行中请求数）、`vllm:num_preemptions`（累计抢占）。诊断流程：usage 持续 >90% 且 preemption 增长 → 容量触顶，压缩每请求 KV 或加显存；usage 低但 TTFT 差 → 不是容量问题，查队列与调度（vllm-01-08）；usage 波动剧烈 → watermark 不足，提高余量。启动日志里的 `GPU KV cache size` 与 `num_gpu_blocks` 是容量方程的实测值，先核对这些数字再调参数。本课示例离线复现扣减链与三重钳制，作为容量方程的离线验证。

#### 本章结论

用 kv_cache_usage_perc / num_requests_running / num_preemptions 三指标定位容量状态；启动日志的块数是方程实测值。

## 核心机制

- KV 容量 = 扣掉权重/图/激活后的显存 × gpu_memory_utilization。
- 块数 = KV 字节 ÷ (block_size × 每 token KV 字节)；可调度 token = 块数 × block_size。
- 并发上限受 KV 容量、max_num_seqs、max_num_batched_tokens、完整 ISL 四重钳制。
- watermark 保留空闲块缓解抢占抖动，默认 0.0。
- 容量高估源于跳过扣减链；max_num_batched_tokens 受块数反向钳制。
- 用 kv_cache_usage_perc / running / preemptions 三指标验证容量状态。

## 常见误区

- 用 `gpu_memory_utilization × 总显存` 估算 KV 容量，忽略权重/图/激活扣减。
- 容量不足时只降 `max_num_seqs`；真实瓶颈可能是每请求 KV 太大。
- 把 `max_num_seqs` 当并发目标；它是上限，真实并发由 KV 容量决定。
- 忽略 watermark；默认 0 在高负载下引发抢占抖动。
- 显式设 `--num-gpu-blocks-override` 掩盖容量错误；它只用于测试抢占。

```python
                                  blocks_per_request: float) -> int:
    usable = num_blocks * (1.0 - watermark)
    return int(usable // blocks_per_request)
```

## 可运行示例

```python
def kv_capacity(available_bytes: float, weights_bytes: float,
                graph_bytes: float, utilization: float,
                block_size: int, bytes_per_token: float) -> dict[str, float]:
    """可用显存 → KV 字节 → 块数 → 可调度 token。"""
    kv_bytes = max((available_bytes - weights_bytes - graph_bytes)
                   * utilization, 0.0)
    num_blocks = int(kv_bytes // (block_size * bytes_per_token))
    return {"kv_bytes": kv_bytes, "num_blocks": num_blocks,
            "schedulable_tokens": num_blocks * block_size}


def effective_concurrency(num_blocks: float, watermark: float,
                          max_num_seqs: int, blocks_per_request: float,
                          max_batched_tokens: int,
                          tokens_per_block: int) -> int:
    """四重钳制：KV 容量(扣 watermark)、max_num_seqs、batched tokens。"""
    kv_limit = int(num_blocks * (1.0 - watermark) // blocks_per_request)
    batch_limit = max_batched_tokens // tokens_per_block
    return max(0, min(kv_limit, max_num_seqs, batch_limit))


# ---- 断言 1：扣减链（忽略权重会高估）----
H100_80G = 80e9
weights_8b_fp16 = 8.03e9 * 2          # 8B × 2 字节 ≈ 16GB
graph_activ = 2e9                     # CUDA graph + 激活估算
# 8B 模型每 token KV 字节：32 层 × 8 kv heads × 128 dim × 2 字节 × 2
bytes_per_token_8b = 32 * 8 * 128 * 2 * 2  # 131072 字节/token

c = kv_capacity(H100_80G, weights_8b_fp16, graph_activ, 0.92, 16,
                bytes_per_token_8b)
naive = kv_capacity(H100_80G, 0, 0, 0.92, 16, bytes_per_token_8b)
assert c["kv_bytes"] < naive["kv_bytes"] * 0.8     # 扣权重后明显变小
assert c["num_blocks"] > 0 and c["num_blocks"] < naive["num_blocks"]

# ---- 断言 2：watermark 降低有效容量 ----
blocks = c["num_blocks"]
assert int(blocks * 0.9) < blocks                  # watermark 0.1 保留 10%

# ---- 断言 3：四重钳制取最小值（KV 为主约束：放开 seqs/batch 上限）----
conc = effective_concurrency(
    num_blocks=blocks, watermark=0.0, max_num_seqs=10000,
    blocks_per_request=64, max_batched_tokens=10_000_000,
    tokens_per_block=16)
conc_wm = effective_concurrency(
    num_blocks=blocks, watermark=0.1, max_num_seqs=10000,
    blocks_per_request=64, max_batched_tokens=10_000_000,
    tokens_per_block=16)
assert conc >= conc_wm                               # watermark 降低并发
assert conc == int(blocks // 64)                     # KV 容量主导

# ---- 断言 4：每请求块需求放大则并发下降 ----
conc_small = effective_concurrency(
    num_blocks=blocks, watermark=0.0, max_num_seqs=10000,
    blocks_per_request=256, max_batched_tokens=10_000_000,
    tokens_per_block=16)
assert conc_small < conc                             # 长请求块需求大 → 并发降
assert conc_small == int(blocks // 256)

# ---- 断言 5：max_num_batched_tokens 被 KV 反向钳制 ----
assert effective_concurrency(
    num_blocks=8, watermark=0.0, max_num_seqs=64,
    blocks_per_request=1, max_batched_tokens=100000,
    tokens_per_block=16) <= 128                      # 8 块 × 16 token 的上限

# ---- 断言 6：启动日志核验方程 ----
# vLLM 启动日志输出 GPU KV cache size 与 num_gpu_blocks；用方程反推验证
expected_blocks = c["num_blocks"]
assert 0 < expected_blocks < 10_000_000             # 数量级合理（约数千块）
```

## 搭积木复现

### 积木 1：实现扣减链

实现 `kv_capacity`（可用显存 - 权重 - 图/激活）× 利用率，用 8B/H100 断言扣权重后容量显著小于 naive。

### 积木 2：实现块数与可调度 token

加入 `num_blocks = kv_bytes // (block_size × bytes_per_token)` 与 `schedulable_tokens = num_blocks × block_size`，断言块数 > 0 且在合理量级。

### 积木 3：实现 watermark

加入 `num_blocks × (1 - watermark)` 的有效块数，断言 watermark 0.1 降低有效容量。

### 积木 4：实现四重钳制

实现 `effective_concurrency`（KV 容量、max_num_seqs、batched tokens 取 min），断言各钳制分别生效、每请求块需求放大则并发下降。

### 积木 5：对照上游源码

对照 `kv_cache_utils.py` v0.26.0 的 `get_kv_cache_configs`（L2036-2175）：说明本课省略了 per-layer KV 配置、混合注意力块分配、prefix cache 预留与 TP/PP 分片；再对照 engine_args 的 `--gpu-memory-utilization`（默认 0.92）、`--watermark`（[0,1)）、`--num-gpu-blocks-override` 文档，说明生产验证要以启动日志的实测块数为准。

## 自检

### 问题

单卡 H100（80GB）跑 8B fp16 模型，启动日志显示 `num_gpu_blocks = 4096`、`block_size = 16`。负载画像 p95 请求需要 64 块 KV。请计算：理论并发上限是多少？watermark 设 0.1 后变成多少？为什么此时把 `max_num_seqs` 从 64 调到 128 不会提升实际并发？

### 站内答案

结论：理论并发 = 4096 × (1-0) ÷ 64 = 64；watermark 0.1 后 = 4096 × 0.9 ÷ 64 = 57（取整）。`max_num_seqs` 调到 128 不会提升实际并发，因为 KV 容量钳制是更紧的约束：可用块数 ÷ 每请求块需求 = 64（或 57），running 中所有请求的块需求总和已经占满 KV，`max_num_seqs` 只是「最多能同时进 running 的请求数」上限，不是「一定能让 128 个都跑起来」的保证——调度器在接纳时受 `num_gpu_blocks` 限制，超出的请求留在 waiting。机制：`num_gpu_blocks = kv_cache_bytes // (block_size × bytes_per_token)`，每请求块需求 = 请求长度 × bytes_per_token ÷ block_size 向上取整；并发 = min(KV 容量扣 watermark、max_num_seqs、max_num_batched_tokens 折算、完整 ISL 可容纳)。源码证据：`get_kv_cache_configs`（kv_cache_utils.py L2036-2175）的块数推导与 watermark 逻辑；`--watermark` 语义「接入等待/抢占请求时需保留的空闲块比例」见 engine_args SchedulerConfig 锚点；`kv_cache_usage_perc` 指标（1 = 100% 使用）见 Usage Metrics。可运行验证：把本课示例的 `effective_concurrency` 用 4096 块/64 块每请求跑一遍，断言 watermark 0/0.1 分别得 64/57，且 `conc <= 64` 即使 `max_num_seqs=128`。工程取舍：要提升并发只能增加块数（加显存/降权重精度/压缩 KV）或降低每请求块需求（KV 量化、MLA、限制 max_model_len）；`max_num_seqs` 应设为「容量推导值的 1.2-1.5 倍」作为接纳余量，而不是相反；watermark 在生产负载下建议 0.05-0.1 防抖动。适用边界：本结论针对稠密 MHA 模型与单卡；MoE 的每 token KV 可能不同（专家并行）、MLA 大幅压缩 KV、TP/PP 分片改变每卡块数、prefix cache 命中请求复用块——这些场景的每请求块需求需按对应公式重算，启动日志的实测值始终是最终权威。
