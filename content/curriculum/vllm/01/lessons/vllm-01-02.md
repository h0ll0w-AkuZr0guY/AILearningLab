[Production Metrics](https://docs.vllm.ai/en/latest/usage/metrics/#general-metrics) 的 General Metrics 表声明了 `vllm:time_to_first_token_seconds`（TTFT 直方图）、`vllm:request_time_per_output_token_seconds`（TPOT 直方图）、`vllm:inter_token_latency_seconds`（ITL）、`vllm:request_queue_time_seconds` / `request_prefill_time_seconds` / `request_decode_time_seconds` / `request_inference_time_seconds` / `e2e_request_latency_seconds` 等服务端聚合指标；[Per-Request Metrics](https://docs.vllm.ai/en/latest/features/per_request_metrics/#response-format) 则给出单请求口径的 `time_to_first_token_ms`、`generation_time_ms`、`queue_time_ms`、`mean_itl_ms`、`tokens_per_second`。两个页面口径并不完全一致，这正是本课要拆开的差异。版本边界 v0.26.0。

### 逐段讲解

- `update_from_output` 在每步模型输出后被调用：若 `is_prefilling` 为真，`first_token_latency = time_since(req_stats.arrival_time)` 被记录为 TTFT，并保存 `first_token_ts`；否则用 `engine_core_timestamp - last_token_ts` 累计 ITL。
- 引擎事件（QUEUED / SCHEDULED / PREEMPTED）通过 `update_from_events` 写入 `queued_ts` 与 `scheduled_ts`；`scheduled_ts` 只在第一次 SCHEDULED 时写入，以忽略抢占重排。
- `update_from_finished_request` 在请求结束时计算四个区间：`queued_time = scheduled_ts - queued_ts`、`prefill_time = first_token_ts - scheduled_ts`、`decode_time = last_token_ts - first_token_ts`、`inference_time = last_token_ts - scheduled_ts`。
- TPOT 取 `decode_time / (num_generation_tokens - 1)`：分母减 1 是因为 prefill 收尾步已经采样了第一个输出 token，它不属于 decode 区间的「间隔」。
- `e2e_latency = time_since(arrival_time)` 覆盖完整生命周期；所有区间都以 `monotonic` 时钟的事件时间戳相减得到，不依赖墙钟对齐。

### 源码节选

```python
def update_from_output(
    self,
    engine_core_timestamp: float,
    is_prefilling: bool,
    req_stats: RequestStateStats,
    ...
):
    num_new_generation_tokens = len(output.new_token_ids)
    self.num_generation_tokens += num_new_generation_tokens
    if is_prefilling:
        # prefill 收尾步：首个输出 token 已经产生，TTFT 从 arrival 起算
        first_token_latency = self._time_since(req_stats.arrival_time)
        self.time_to_first_tokens_iter.append(first_token_latency)
        req_stats.first_token_latency = first_token_latency
    req_stats.num_generation_tokens += num_new_generation_tokens

    if is_prefilling:
        req_stats.first_token_ts = engine_core_timestamp
    else:
        # decode 步：与上一个输出 token 的时间差就是 ITL
        itl = engine_core_timestamp - req_stats.last_token_ts
        self.inter_token_latencies_iter.append(itl)
    req_stats.last_token_ts = engine_core_timestamp

def update_from_finished_request(self, ...):
    e2e_latency = self._time_since(req_stats.arrival_time)

    # 四个区间：全部由事件时间戳相减，抢占造成的停顿被计入所属区间
    queued_time = req_stats.scheduled_ts - req_stats.queued_ts
    prefill_time = req_stats.first_token_ts - req_stats.scheduled_ts
    decode_time = req_stats.last_token_ts - req_stats.first_token_ts
    inference_time = req_stats.last_token_ts - req_stats.scheduled_ts

    # TPOT：decode 区间除以「间隔数」，而不是输出 token 总数
    mean_time_per_output_token = (
        decode_time / (req_stats.num_generation_tokens - 1)
        if req_stats.num_generation_tokens - 1 > 0
        else 0
    )
    finished_req = FinishedRequestStats(
        finish_reason=finish_reason,
        request_id=request_id,
        e2e_latency=e2e_latency,
        queued_time=queued_time,
        prefill_time=prefill_time,
        inference_time=inference_time,
        decode_time=decode_time,
        mean_time_per_output_token=mean_time_per_output_token,
        ...
    )
```

## 导读

运维同学在 Grafana 上看到 `p50 TTFT = 80ms`，但客户报告「第一个字等了 300ms」。查了半天发现两个数字的起点不同：服务端直方图的 TTFT 从请求**到达**引擎的时刻起算，而 per-request metrics 里的 `time_to_first_token_ms` 文档定义是从**被调度**到首 token 的时长。这不是 bug，是两套口径并存。

要读懂 vLLM 的延迟指标，关键是接受一个事实：TTFT、TPOT、ITL 都不是被「测量」的单一事件时长，而是由一组**事件时间戳**（QUEUED、SCHEDULED、first NEW_TOKEN、last NEW_TOKEN）相减得到的**区间**。prefill 期间被抢占、decode 期间排队，都会被并进对应区间。本课把这些时间戳与公式逐一拆开，第三课的抢占代价、第五课的带宽分析都会复用这里的区间概念。

## 分章正文

### 两个 TTFT：从 arrival 起算 vs 从 scheduled 起算

kicker: "01 · OBSERVE"

vLLM 里「TTFT」有至少两个官方定义。服务端 Prometheus 直方图 `vllm:time_to_first_token_seconds` 记录的是 `time_since(arrival_time)`，即从请求到达引擎到首个输出 token 的完整时长，包含排队等待。per-request metrics 的 `time_to_first_token_ms` 文档描述为「Time from when the request was scheduled until the first output token was generated」，从被调度起算，不含排队。

当队列为空时两者几乎相等；当排队超过 prefill 本身时，arrival 口径可以比 scheduled 口径大一个数量级。生产里看 SLO 用哪个口径取决于 SLA 定义：客户感知延迟必须用 arrival 口径，引擎内部 prefill 优化效果的评估应该用 scheduled 口径。

#### 本章结论

同一名字、两个起点；区分「是否包含排队」是读懂 TTFT 的第一步。

### 事件时间戳：延迟指标的原始材料

kicker: "02 · EVENTS"

区间公式依赖四类事件：请求进入 waiting 时记录 `QUEUED`（`request.record_event(QUEUED)`），第一次被调度时记录 `SCHEDULED`，prefill 收尾步产出第一个输出 token 时记录 `first_token_ts`，之后每步刷新 `last_token_ts`，请求结束时计算区间。全部使用单调时钟（monotonic）的事件时间戳，避免系统时钟跳变污染差值。

注意 `scheduled_ts` 只在第一次 SCHEDULED 时写入（`if req_stats.scheduled_ts == 0.0: # ignore preemptions`），因此「被抢占后重新调度」不会重置排队区间的起点；抢占造成的停顿会完整落入 prefill 或 decode 区间，这保证了「区间之和 = 总时长」的守恒。

#### 本章结论

区间由单调事件时间戳相减而来；抢占只影响区间内部，不重置区间起点。

### update_from_output：TTFT 与 ITL 的记账点

kicker: "03 · ACCUMULATE"

每步模型输出到达时，`update_from_output` 判断当前请求是否仍在 prefill：是，则记录 `first_token_latency`（arrival 口径 TTFT）并写入 `first_token_ts`；否，则把 `engine_core_timestamp - last_token_ts` 追加为一次 ITL 观测。`last_token_ts` 每步都刷新，所以 ITL 是相邻两个输出 token 之间的间隔，单个请求产生 `num_generation_tokens - 1` 个 ITL 样本。

这里有个隐含约定：prefill 收尾步产生的第一个输出 token 同时满足两个身份——它是 TTFT 的终点，也是 decode 区间的起点。因此「输出 token 总数」永远比「token 间隔数」多 1，这个 1 在 TPOT 分母里必须被扣掉。

#### 本章结论

TTFT 在 prefill 收尾步记账，ITL 在 decode 每步记账；首 token 同时是两个区间的分界点。

### 四个区间：queued / prefill / decode / inference

kicker: "04 · INTERVALS"

请求结束时一次性算出四个区间：`queued_time = scheduled_ts - queued_ts`（排队）、`prefill_time = first_token_ts - scheduled_ts`（prefill）、`decode_time = last_token_ts - first_token_ts`（decode）、`inference_time = last_token_ts - scheduled_ts`（推理总时长）。加上 `e2e = arrival → finish`，五个数字之间存在明确守恒：`queued + inference = e2e - (finish 到 last_token 的收尾段)`，而 `inference = prefill + decode`。

每个区间都可能有抢占噪声：prefill 期间被抢占，停顿计入 `prefill_time`；decode 期间被抢占，停顿计入 `decode_time`。所以这四个区间回答的是「时间花在了哪个阶段」，而不是「GPU 真正算了几毫秒」。评估模型性能前先看 `num_preemptions`，否则会把排队和重算当成模型变慢。

#### 本章结论

queued + prefill + decode 三段守恒；区间含抢占停顿，读延迟前先查抢占计数。

### TPOT 的分母为什么是 N-1

kicker: "05 · TPOT"

`mean_time_per_output_token = decode_time / (num_generation_tokens - 1)`。直觉上 TPOT 应该是「总 decode 时间 ÷ 输出 token 数」，但 vLLM 用的是间隔数。原因就是首 token 已经算进了 prefill：一个生成 10 个 token 的请求，区间结构是 TTFT（含首 token）+ 9 个 decode 间隔，decode 区间的端点恰好覆盖 9 个间隔。若分母用 10，TPOT 会被系统性低估 10%。

这个定义还解释了另一个现象：`request_time_per_output_token_seconds` 与 `inter_token_latency_seconds` 数值非常接近但不等——前者是请求级平均（先除后聚合），后者是逐间隔观测（直接聚合），单请求的 TPOT 就是其 ITL 的均值。当只有一个输出 token（`N-1 = 0`）时 TPOT 记为 0，这是文档明确的分母保护。

#### 本章结论

TPOT 分母是间隔数 N-1；单 token 响应 TPOT 记 0，不与 ITL 混淆。

### 口径差异的生产教训

kicker: "06 · OPS"

把口径差异落到生产决策上：第一，告警阈值必须写清楚起点，arrival 口径的 TTFT 包含排队，适合 SLA，scheduled 口径适合引擎调优；第二，`n > 1`（并行采样）的请求 metrics 为 null，因为底层计时只对应一条序列，归因不可信，服务端直方图不受影响；第三，`tokens_per_second = 生成 token 数 ÷ inference_time`，它包含 prefill 时间，因此低于「纯 decode 速度」，不要把两者混用；第四，开启 `--enable-per-request-metrics` 有 CPU 开销，官方文档明确提示高并发下需评估。

#### 本章结论

读指标先问起点与分母；不同页面与字段服务不同目的，混用口径会得出错误结论。

## 核心机制

- 延迟指标由单调事件时间戳相减得到：QUEUED、SCHEDULED、first NEW_TOKEN、last NEW_TOKEN。
- 服务端 TTFT 从 arrival 起算；per-request 文档口径从 scheduled 起算，两者相差一个排队时长。
- 四个区间 queued / prefill / decode / inference 满足守恒；抢占停顿计入所属阶段。
- TPOT 分母是间隔数 `N-1`，单 token 响应记为 0。

## 常见误区

- 以为 TTFT 只有一个定义；实际 arrival 口径与 scheduled 口径并存且都有官方文档支撑。
- 用输出 token 总数当 TPOT 分母，导致 TPOT 被系统性低估。
- 把 prefill_time 当成「GPU 计算 prefill 的时间」；其中包含抢占重算与排队停顿。
- 在 `n > 1` 请求上读 per-request metrics 的延迟字段；该场景字段为 null。
- 混淆 `tokens_per_second`（含 prefill）与 TPOT 的倒数（纯 decode）。

## 实现变体

### 变体 A：arrival 起算的端到端 TTFT（服务端直方图）

useWhen: "用于 SLA 与客户可感知延迟，队列压力必须计入指标。"
tradeoff: "获得：单一数字反映完整等待体验；牺牲：无法区分排队与模型性能，排队风暴会让 TTFT 与 TPOT 一起失真。"

#### 代码

```python
def ttft_arrival(arrival_ts: float, first_token_ts: float) -> float:
    return first_token_ts - arrival_ts   # stats.py: time_since(req_stats.arrival_time)
```

### 变体 B：scheduled 起算的引擎内 TTFT（per-request metrics）

useWhen: "评估调度与 prefill kernel 本身的性能，把队列效应排除在外。"
tradeoff: "获得：prefill 纯时长，便于横向对比；牺牲：与用户感知存在偏差，SLA 告警不宜直接采用。"

#### 代码

```python
def ttft_scheduled(scheduled_ts: float, first_token_ts: float) -> float:
    return first_token_ts - scheduled_ts   # 对应 prefill_time 的官方定义
```

## 可运行示例

```python
class FinishedRequestStats:
    """复刻 stats.py 的 FinishedRequestStats 字段。"""

    def __init__(self, **kw: float) -> None:
        for k, v in kw.items():
            setattr(self, k, v)


def finish_request(
    arrival_ts: float, queued_ts: float, scheduled_ts: float,
    first_token_ts: float, last_token_ts: float, num_generation_tokens: int,
) -> FinishedRequestStats:
    """按 stats.py 的公式从事件时间戳计算全部区间与 TPOT。"""
    e2e = last_token_ts - arrival_ts
    queued_time = scheduled_ts - queued_ts
    prefill_time = first_token_ts - scheduled_ts
    decode_time = last_token_ts - first_token_ts
    inference_time = last_token_ts - scheduled_ts
    tpot = (decode_time / (num_generation_tokens - 1)
            if num_generation_tokens - 1 > 0 else 0.0)
    return FinishedRequestStats(
        e2e_latency=e2e, queued_time=queued_time, prefill_time=prefill_time,
        decode_time=decode_time, inference_time=inference_time,
        mean_time_per_output_token=tpot,
        num_generation_tokens=num_generation_tokens,
    )


# 时间轴：到达 0ms，排队 10ms，调度 20ms 后出首 token，随后每 30ms 一个 token
s = finish_request(
    arrival_ts=0.0, queued_ts=0.5, scheduled_ts=10.5,
    first_token_ts=30.5, last_token_ts=150.5, num_generation_tokens=5,
)
assert s.queued_time == 10.0                 # scheduled - queued
assert s.prefill_time == 20.0                # first_token - scheduled
assert s.decode_time == 120.0                # last_token - first_token
assert s.inference_time == 140.0             # last_token - scheduled
assert s.e2e_latency == 150.5                # last_token - arrival
assert s.prefill_time + s.decode_time == s.inference_time   # 守恒

# TPOT 分母是 N-1 = 4，而不是 5
assert abs(s.mean_time_per_output_token - 30.0) < 1e-9
wrong = s.decode_time / s.num_generation_tokens
assert wrong == 24.0 and wrong < 30.0        # 用 N 做分母会低估 20%

# 单 token 响应：分母保护，TPOT 记 0
one = finish_request(0.0, 0.5, 10.5, 30.5, 30.5, 1)
assert one.decode_time == 0.0 and one.mean_time_per_output_token == 0.0

# 两种 TTFT 口径：相差一个排队时长
ttft_arrival = s.prefill_time + s.queued_time      # arrival 口径
ttft_scheduled = s.prefill_time                    # scheduled 口径
assert ttft_arrival == 30.0 and ttft_scheduled == 20.0
assert ttft_arrival - ttft_scheduled == s.queued_time

# 抢占落入所属区间：prefill 中插入 5ms 停顿，prefill_time 变大
preempted = finish_request(0.0, 0.5, 10.5, 35.5, 150.5, 5)
assert preempted.prefill_time == 25.0              # 20ms 计算 + 5ms 抢占停顿
```

## 搭积木复现

### 积木 1：定义事件时间戳模型

用一个字典记录 QUEUED / SCHEDULED / first NEW_TOKEN / last NEW_TOKEN 四个单调时钟戳，并断言四个戳单调不减。

### 积木 2：实现三个基本相减

实现 `queued_time`、`prefill_time`、`decode_time` 与 `inference_time`，验证 `prefill + decode == inference` 恒成立。

### 积木 3：实现 TPOT 与分母保护

按 `decode_time / (N-1)` 实现，处理 `N-1 <= 0` 时记 0；用 N=1 与 N=2 两个用例断言。

### 积木 4：加入抢占事件

在 prefill 区间中间插入一次 PREEMPTED 重调度，断言停顿完整计入 prefill_time 且 `scheduled_ts` 不被重置。

### 积木 5：对照上游源码

对照 `stats.py` 的 `update_from_events` 与 `update_from_finished_request`，列出省略的 LoRA 状态、per-engine 维度与 NaN 检测分别影响哪些观测（多模型并存、分引擎监控、损坏请求过滤）。

## 自检

### 问题

一个请求：到达 0ms、进队 2ms、第一次被调度 12ms、prefill 收尾在 32ms 产出首 token、随后 3 个 token 间隔均为 20ms、末 token 在 92ms。求 queued、prefill、decode、inference、e2e 与 TPOT；并说明服务端直方图 TTFT 与该请求 per-request `time_to_first_token_ms` 各是多少、为什么不同。

### 站内答案

结论：queued=10ms、prefill=20ms、decode=60ms、inference=80ms、e2e=92ms、TPOT=20ms；服务端 TTFT=32ms（arrival→首 token），per-request 口径 TTFT=20ms（scheduled→首 token）。机制：全部区间由事件时间戳相减：`queued=scheduled_ts-queued_ts=12-2`、`prefill=first_token_ts-scheduled_ts=32-12`、`decode=last_token_ts-first_token_ts=92-32`；输出 token 数 N=4（首 token + 3 个间隔），TPOT=decode/(N-1)=60/3=20ms。源码证据：`vllm/v1/metrics/stats.py` v0.26.0 `update_from_finished_request`（L457-495）的四区间公式与 `mean_time_per_output_token`（L479-483），以及 `update_from_output`（L393-395）里 `first_token_latency = time_since(req_stats.arrival_time)` 证明服务端 TTFT 从 arrival 起算；per-request 文档（features/per_request_metrics 的 response-format 表）定义 `time_to_first_token_ms` 为「from when the request was scheduled」。可运行验证：把本课示例的时间轴参数代入 `finish_request`，断言各字段等于上述数值，并验证 `ttft_arrival - ttft_scheduled == queued_time`。工程取舍：SLA 告警应选 arrival 口径（含排队，反映用户感知），引擎调优用 scheduled 口径；两者差的就是排队时间，若差值为负说明事件记录异常（时钟或事件顺序错误）。适用边界：`n>1` 请求 per-request 字段为 null；抢占停顿按归属计入 prefill/decode；单调时钟下公式成立，墙钟跳变会让差值失真。
