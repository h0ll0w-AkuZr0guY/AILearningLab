### 逐段讲解

- `get_num_flops_breakdown` 按注意力层拆 FLOPs：`qkv_proj = 2·T·D·(q+2kv)·d·L`、`attn_qk = 2·q·TC·d·L`、`attn_av = 2·q·TC·d·L`、`out_proj = 2·T·D·q·d·L`，其中 T 是本步 token 数、TC 是 token×context 乘积、L 是层数。
- `get_read_bytes_breakdown` 把读取分成权重与激活两类：`qkv_weight = D·(q+2kv)·d·weight_byte_size·L` 与 `out_weight` 每步都要从 HBM 读一遍；decode 分支额外读 KV cache：`2·decode_context_len·kv·d·cache_byte_size·L`，随 context 线性增长。
- decode 时 `T=1`：FLOPs 只有权重矩阵乘一个 token 的量（约 `2·N`，N 为参数量），而字节数包含**全部权重**——于是每步的「FLOP/字节」比值极小，roofline 上落在内存受限区。
- prefill 时 `T` 很大：FLOPs 按 `2·N·T` 增长，字节主要是权重一次读入加激活与 KV 写入，比值随 T 变大，最终进入计算受限区。
- 这两组估算被 `--enable-mfu-metrics` 输出为 `estimated_flops_per_gpu_total` 与 `estimated_read_bytes_per_gpu_total`，是「解码为什么算不满 GPU」的官方可观测证据。

### 源码节选

```python
def get_num_flops_breakdown(
    self, ctx: ExecutionContext, per_gpu: bool = True
) -> dict[str, int]:
    L, D, q, kv, d = (
        self.num_hidden_layers, self.hidden_size,
        self.num_attention_heads, self.num_key_value_heads, self.head_dim,
    )
    T = ctx.total_num_tokens()              # 本步 token 总数
    TC = ctx.total_token_context_product()  # token x context 乘积
    return {
        "qkv_proj": 2 * T * D * (q + 2 * kv) * d * L,
        "attn_qk": 2 * q * TC * d * L,
        "attn_av": 2 * q * TC * d * L,
        "out_proj": 2 * T * D * q * d * L,
    }

def get_read_bytes_breakdown(
    self, ctx: ExecutionContext, per_gpu: bool = True
) -> dict[str, int]:
    T = ctx.total_num_tokens()
    read_bytes = {}
    # 每步都要从 HBM 读一遍全部权重：与 T 无关，只与模型大小有关
    read_bytes["qkv_weight"] = int(D * (q + 2 * kv) * d * self.weight_byte_size * L)
    read_bytes["out_weight"] = int(q * d * D * self.weight_byte_size * L)
    # decode：读 Q 激活 + 从 KV cache 读 K、V，后者随 context 线性增长
    if ctx.decode_num_tokens > 0:
        read_bytes["attn_input"] = (
            ctx.decode_num_tokens * q * d * self.activation_byte_size * L
            + 2 * ctx.decode_context_len * kv * d * self.cache_byte_size * L
        )
    return read_bytes
```

删减说明：这里省略了 FFN（MLP）的 FLOPs/字节项、MLA 注意力变体与 TP/PP 分片折算；保留的是 MHA 注意力的核心结构，足以说明「decode 每步 FLOPs 随 T=1 缩小、权重字节固定」这一对比，但精确的模型级预算（含 FFN 与 MLA）需回到完整实现。

## 导读

把「算力」和「带宽」想象成「厨师」和「上菜口」。厨师（GPU 的 Tensor Core）每秒能做 989 万亿次乘法加法，但每道菜都要先从上菜口（HBM3，3.35TB/s）把食材端进来。decode 每一步只生成 1 个 token，需要端进来的食材却是**整份模型权重**——一个 8B 模型 fp16 有约 16GB，按 3.35TB/s 算，光端食材就要 4.8ms，而真正炒菜（16 GFLOP 的矩阵乘）只要 16 微秒。厨师大部分时间在等菜，这就是「decode 算不满 GPU」的实质。

本课用 vLLM 自己的 MFU 估算源码（`perf.py`）给出 FLOPs 与字节的公式，再落到 roofline 模型上算出「上限在哪边」：decode 是带宽受限，prefill 是算力受限。看懂这条线，就能回答模块 01 的面试问题「为什么 decode 常常受 memory bandwidth 限制」，也能解释为什么小模型、低精度、长上下文会改变瓶颈位置。

## 分章正文

### 一个「算不满」的现场

kicker: "01 · OBSERVE"

单卡 H100 上跑 Llama-3-8B，`max_num_seqs=1`（只处理一个请求）测 decode 吞吐，得到约 150–250 token/s。同时 `nvidia-smi` 显示 GPU 利用率 90%+，`MFU`（模型 FLOPs 利用率）却不到 10%——两个数字看似矛盾：GPU 明明很忙，算力却没被用满。

谜底在「忙什么」：decode 步的 GPU 大部分时间在等 HBM 把 16GB 权重搬进片上缓存，矩阵乘本身只占一小部分。nvidia-smi 的利用率统计的是 SM 是否空闲，而 SM 在等数据时也算「占用」；MFU 统计的是「实际 FLOPs ÷ 峰值 FLOPs」，带宽受限时这个比值天然很低。所以「利用率高」与「算力利用率低」可以同时成立。

#### 本章结论

decode 的 GPU 时间主要花在等权重从 HBM 到达，SM 忙但算力利用率低。

### 算术强度与 roofline：瓶颈由比值决定

kicker: "02 · MODEL"

roofline 模型把性能上限画成两条线：计算线 `peak_flops` 与带宽线 `peak_bw`，交点叫 ridge point，数值等于 `peak_flops / peak_bw`。对 H100：`989e12 / 3.35e12 ≈ 295 FLOP/byte`。一个算子的「算术强度」`AI = FLOPs / bytes`：AI 大于 ridge 由算力决定上限，小于 ridge 由带宽决定上限。

LLM 每 token 的 FLOPs 约 `2N`（N 为参数量，前向），权重字节约 `N × bytes_per_param`，所以 decode 的 `AI ≈ 2N / (N×2) = 1`（fp16），远小于 295。结论很直接：decode 每一步都稳稳落在带宽线以下，加算力（换更高 FLOPs 的卡）几乎不涨 token 率，加带宽才涨。这是「decode 是带宽问题」的完整论证。

#### 本章结论

`AI = FLOPs / bytes`，decode 的 AI≈1 远低于 H100 ridge≈295，瓶颈是带宽。

### 每步读什么：perf.py 的字节公式

kicker: "03 · SOURCE"

vLLM 的 MFU 估算把 decode 每步的读取拆成三块：全部权重（`qkv_weight + out_weight`，与 token 数无关）、本 token 的 Q 激活、以及随 context 线性增长的 KV cache 读取 `2·decode_context_len·kv·d·cache_byte_size·L`。FLOPs 只有 `2·T·D·(q+2kv)·d·L` 等四项，T=1 时整体约 `2N`。

代入 8B 模型：权重 16GB；KV 每 token 约 128KB（32 层 × 8 kv heads × 128 head dim × 2 字节 × 2），4K context 时 KV 读 512MB，131K context 时约 16GB——与权重同量级。所以 decode 的字节数 = 权重 + KV 读，两者都随模型/上下文变大，而 FLOPs 只按 token 算。这解释了「为什么 decode 算不满」在数学上必然成立。

#### 本章结论

decode 每步读全部权重 + 全部历史 KV；字节与模型和 context 成正比，FLOPs 只与 token 数成正比。

### prefill 与 decode 的算术强度分水岭

kicker: "04 · CONTRAST"

prefill 一次处理 T 个 token：FLOPs ≈ `2N·T`，字节 ≈ 权重一次读入（`N×b`）+ 激活 + KV 写入。AI ≈ `2N·T / (N·b + ...)`，T 越大比值越高。8B 模型、T=2048：AI ≈ 2048，高于 ridge 295，落入计算受限区——所以 prefill 吞吐的上限由 FLOPs 决定，增大 batch 能线性吃到算力。

同一条链的两端：prefill 用「把 T 个 token 打包成一个矩阵乘」把 AI 抬到 2000+，decode 每次 T=1 把 AI 压到 1。这也正是第一课「统一 token 预算」的性能含义：预算内多塞 prefill token 能提升整体算力利用率，纯 decode 批则注定带宽受限。chunked prefill 之所以有用，本质上是在带宽受限的 decode 步之间插入高 AI 的 prefill 块。

#### 本章结论

prefill 的 AI 随 T 升高进入算力受限区，decode 恒为 AI≈1 带宽受限；混合调度就是两类算子的配比。

### 为什么小模型与低精度更受带宽压制

kicker: "05 · SCALING"

带宽受限的 decode 上限约等于 `peak_bw / bytes_per_token`。字节由两部分组成：权重 `N×b`（b 为每参数字节，fp16=2、fp8=1）与 KV 读。模型越小 N 越小，理论上限越高，但小模型的实际 token 率往往达不到理论值——因为 CUDA graph、kernel 启动与 CPU 调度开销占比变大，模型小到一定程度后「每步固定开销」成了新的瓶颈。低精度则直接减半权重字节：8B 从 fp16 换 fp8，decode 带宽上限从约 209 提到约 418 token/s（仅权重项）。

长上下文是另一面：KV 读随 context 线性增长，当 KV 读接近权重字节时，decode 上限进一步下降。所以「长上下文 + decode」是带宽压力最重的组合，这也解释了 vLLM 为什么推出 KV 量化（fp8 cache）、MLA（压缩 KV）与 P/D 分离等特性——它们都是在削减「每步必须从 HBM 读的字节数」。

#### 本章结论

带宽上限 = 带宽 ÷ 每 token 字节；小模型受固定开销限制，低精度与 KV 压缩直接削减字节。

### 怎么验证：MFU 指标与 bench latency

kicker: "06 · VERIFY"

官方验证路径有两条。第一条是运行时观测：`vllm serve --enable-mfu-metrics` 后，`/metrics` 输出 `vllm:estimated_read_bytes_per_gpu_total` 与 `vllm:estimated_flops_per_gpu_total`，两者相除即实测 AI；对比 ridge（约 295）就能判断当前负载受限在哪边。第二条是离线上限估算：用本课公式手算 `peak_bw / (weights + KV)` 得到理论上限，再用 `vllm bench latency` 实测，二者差距暴露的是 kernel 效率与调度开销。

诊断流程：实测 token/s 远低于带宽上限 → 查固定开销（batch 太小、graph 未捕获、CPU 组装）；接近带宽上限但 MFU 很低 → 这是 decode 的正常形态，不是 bug；MFU 很高（>50%）→ 负载已进入算力受限区，可以加并发进一步吃算力。任何「解码太慢」的投诉，先算这条分界线，再决定加卡还是加并发。

#### 本章结论

用 MFU 指标实测 AI、用 roofline 公式算上限，先定位受限边再决定优化方向。

## 核心机制

- decode 每步 FLOPs≈2N（T=1），字节=全部权重+全部历史 KV，AI≈1，恒带宽受限。
- H100 ridge≈295 FLOP/byte（989 TFLOPS / 3.35TB/s），decode AI 远低于它。
- prefill 的 AI≈2T/b 随 T 升高进入算力受限区；混合调度是两类算子的配比。
- 带宽上限≈peak_bw÷每 token 字节；低精度、KV 量化、MLA 都在削减字节。
- `--enable-mfu-metrics` 输出 estimated FLOPs/read bytes，是官方观测入口。

## 常见误区

- 用 nvidia-smi 利用率判断算力是否用满；SM 等待数据也算占用，利用率与 MFU 是两回事。
- 认为「加算力卡就涨 decode 吞吐」；带宽受限时换高 FLOPs 卡几乎无收益。
- 以为 decode 慢是模型实现问题；AI≈1 是数学必然，任何实现都在带宽线以下。
- 忽略 KV 读：长上下文下 KV 字节逼近权重字节，decode 上限进一步下降。
- 把 `tokens_per_second`（含 prefill 的 inference_time 口径）与纯 decode 上限直接对比。

## 实现变体

### 变体 A：权重驻留 HBM 的逐步全量读

useWhen: "标准的稠密权重加载路径，权重每次 decode 步都要从 HBM 读入片上缓存。"
tradeoff: "获得：实现简单、与 kernel 无关；牺牲：decode 带宽上限被权重字节锁死（8B fp16 ≈ 209 token/s/GPU）。"

#### 代码

```python
def decode_bound_weights(peak_bw: float, num_params: int, bytes_per_param: float) -> float:
    return peak_bw / (num_params * bytes_per_param)   # 仅权重项的上限
```

### 变体 B：削减每步字节（KV 量化 / 权重量化 / MLA）

useWhen: "长上下文或多实例部署，需要把 decode 上限往上抬。"
tradeoff: "获得：每 token 字节下降，带宽上限成比例提升；牺牲：量化精度损失、实现复杂度与 kernel 兼容性约束。"

#### 代码

```python
def decode_bound_budgeted(peak_bw: float, weight_bytes: float,
                          kv_bytes_per_token: float, context_len: int) -> float:
    return peak_bw / (weight_bytes + kv_bytes_per_token * context_len)
```

## 可运行示例

```python
def roofline_classify(peak_flops: float, peak_bw: float,
                      num_params: int, bytes_per_param: float,
                      tokens: int, kv_bytes_per_token: float = 0.0,
                      context_len: int = 0) -> dict[str, float]:
    """按 perf.py 的结构估算 AI 并判断受限边。FLOPs≈2N·T，字节=权重+KV。"""
    flops = 2.0 * num_params * tokens
    bytes_read = (num_params * bytes_per_param
                  + kv_bytes_per_token * context_len * tokens)
    ai = flops / bytes_read
    ridge = peak_flops / peak_bw
    bound = "compute" if ai >= ridge else "memory"
    limit = (peak_flops / flops if bound == "compute"
             else peak_bw / bytes_read)
    return {"flops": flops, "bytes": bytes_read, "ai": ai,
            "ridge": ridge, "bound": bound, "limit": limit}


H100_FLOPS = 989e12        # FP16 dense Tensor Core
H100_BW = 3.35e12          # HBM3
LLAMA8B = 8.03e9
FP16 = 2.0
KV_BYTES_PER_TOKEN = 128e3  # Llama-3-8B 量级：32 层 x 8 kv heads x 128 dim x 2B x 2

# decode：T=1，AI 远低于 ridge，带宽受限
d = roofline_classify(H100_FLOPS, H100_BW, LLAMA8B, FP16, tokens=1)
assert d["ai"] < d["ridge"] and d["bound"] == "memory"
assert abs(d["limit"] - H100_BW / (LLAMA8B * FP16)) < 1e3  # 约 209 token/s

# prefill：T=2048，AI 高于 ridge，算力受限
p = roofline_classify(H100_FLOPS, H100_BW, LLAMA8B, FP16, tokens=2048)
assert p["ai"] > p["ridge"] and p["bound"] == "compute"

# 长上下文：KV 读使 decode 上限进一步下降
d_4k = roofline_classify(H100_FLOPS, H100_BW, LLAMA8B, FP16, 1,
                         KV_BYTES_PER_TOKEN, 4096)
d_128k = roofline_classify(H100_FLOPS, H100_BW, LLAMA8B, FP16, 1,
                           KV_BYTES_PER_TOKEN, 131072)
assert d_4k["limit"] < d["limit"] and d_128k["limit"] < d_4k["limit"]

# 低精度：权重字节减半，带宽上限约翻倍
d_fp8 = roofline_classify(H100_FLOPS, H100_BW, LLAMA8B, 1.0, tokens=1)
assert d_fp8["limit"] > 1.9 * d["limit"]          # fp16 -> fp8 接近两倍

# 加算力不加带宽：decode 上限几乎不变（带宽受限的推论）
d_b200_flops = roofline_classify(2 * H100_FLOPS, H100_BW, LLAMA8B, FP16, tokens=1)
assert d_b200_flops["limit"] == d["limit"]        # 算力翻倍无收益

# KV 字节与权重字节对比：131K context 时 KV 读约等于权重
kv_bytes_131k = KV_BYTES_PER_TOKEN * 131072
assert 0.8 < kv_bytes_131k / (LLAMA8B * FP16) < 1.2
```

## 搭积木复现

### 积木 1：实现 FLOPs 与字节的估算函数

按 `2N·T` 与 `权重字节 + KV×context` 实现两个函数，用 8B/T=1 断言 AI≈1。

### 积木 2：实现 ridge 与受限边判断

实现 `ridge = peak_flops / peak_bw` 与 `AI ≥ ridge` 判定，用 H100 数值断言 decode 落内存区、prefill 落算力区。

### 积木 3：实现两条上限线

计算线与带宽线各返回 `limit`，断言 decode 的 `limit = peak_bw / bytes`，prefill 的 `limit = peak_flops / flops`。

### 积木 4：加入 KV 与精度参数

加入 `kv_bytes_per_token × context` 与 `bytes_per_param`，断言长上下文压低上限、fp8 抬高上限。

### 积木 5：对照上游源码

对照 `perf.py` 的 `get_num_flops_breakdown` / `get_read_bytes_breakdown`（L445-513），列出省略的 FFN 项与 MLA 变体，说明本课估算对稠密 MHA 模型成立、对 MoE 与 MLA 模型需要按对应公式重算。

## 自检

### 问题

单卡 H100 跑 8B 模型 decode，实测约 180 token/s，`nvidia-smi` 利用率 95% 而 MFU 只有 8%。请解释这三个数字为何可以同时成立，写出 decode 的算术强度与带宽上限公式，并说明为什么「换一张算力翻倍的卡」几乎不涨 token 率，而「权重换 fp8」可以。

### 站内答案

结论：利用率统计 SM 忙碌、MFU 统计算力利用率，decode 带宽受限时两者必然背离；decode 的 AI≈1，上限由 `peak_bw / (权重字节 + KV 字节)` 决定，算力翻倍不改变上限，fp8 减半权重字节所以上限约翻倍。机制：decode 每步 FLOPs≈2N（T=1），而每步必须从 HBM 读全部权重（`N×b`）与全部历史 KV（`2·context·kv·d·cache_bits·L`），AI≈1 远低于 H100 ridge≈295（989 TFLOPS / 3.35TB/s），落在带宽线以下；实测 180 token/s 接近理论 209 token/s（仅权重项）说明主要开销就是搬权重，剩余差距来自 KV 读与固定开销。源码证据：`vllm/v1/metrics/perf.py` v0.26.0 的 `get_read_bytes_breakdown`（L471-513）明确列出 decode 分支读 `qkv_weight`、`out_weight` 与 `2·decode_context_len·kv·d·cache_byte_size·L`；`--enable-mfu-metrics` 输出的 `estimated_flops_per_gpu_total` / `estimated_read_bytes_per_gpu_total`（usage/metrics 的 MFU 一节）可直接观测。可运行验证：把本课示例的 `roofline_classify` 跑一遍，断言 decode `bound=="memory"`、`limit≈209`、`d_b200_flops["limit"] == d["limit"]`、`d_fp8["limit"] > 1.9×d["limit"]`。工程取舍：decode 优化只有两条路——削减每步字节（权重/ KV 量化、MLA、P/D 分离、batch 内复用）或提升有效带宽（更大的 L2/片上缓存命中）；加算力对带宽受限负载无效，加并发则把多个请求的权重读取合并进同一次搬运、摊薄固定开销。适用边界：本课的 2N FLOP 规则针对稠密前向；MoE 每 token 只激活部分专家、MLA 大幅压缩 KV，二者的 AI 与上限需按对应公式重算；实测还会受 CUDA graph、kernel 启动与 CPU 组装开销影响，理论值是上界而非承诺值。
