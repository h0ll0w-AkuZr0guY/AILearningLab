### 逐段讲解

- `SchedulingPolicy`（L13-18）：枚举只有 FCFS 与 PRIORITY 两个值，字符串分别是 "fcfs" 与 "priority"——调度策略的合法输入集，`--scheduling-policy` 只接受这两个。
- `RequestQueue`（L20-73）：抽象基类定义九种操作（add/pop/peek/prepend/remove 等）。`prepend_request` 与 `prepend_requests` 的存在本身说明「回队」是调度器的一等操作——抢占的请求要放回队列头部。
- `FCFSRequestQueue`（L75-129）：继承 `deque[Request]`，`add` 是 `append`（尾部进）、`pop` 是 `popleft`（头部出）、`prepend_request` 是 `appendleft`（头部回）——FCFS 的插入/弹出/回队都是 O(1)。
- `PriorityRequestQueue`（L131-199）：内部是 `heapq` 堆，`add`/`pop` 各 O(log n)；`prepend_request` 语义被注释明确为「priority 队列没有队头概念，按 (priority, arrival_time) 重新插入」——**抢占回队后次序由字段重新决定，而不是回到原来位置**。
- `create_request_queue`（L201-207）：按 policy 工厂分发，非法值抛 `ValueError`——策略与实现的一一映射在这里落定。

### 源码节选

```python
class FCFSRequestQueue(deque[Request], RequestQueue):
    """A first-come-first-served queue that supports deque operations."""

    def add_request(self, request: Request) -> None:
        self.append(request)                       # 尾部进

    def pop_request(self) -> Request:
        return self.popleft()                      # 头部出：先到先服务

    def prepend_request(self, request: Request) -> None:
        self.appendleft(request)                   # 抢占回队头


class PriorityRequestQueue(RequestQueue):
    """A priority queue that supports heap operations.

    Respects the ordering defined in the Request class, where
    requests with a smaller value of `priority` are processed first.
    If multiple requests have the same priority, the one with the earlier
    `arrival_time` is processed first.
    """

    def __init__(self) -> None:
        self._heap: list[Request] = []

    def add_request(self, request: Request) -> None:
        heapq.heappush(self._heap, request)        # 按 __lt__ 排序

    def pop_request(self) -> Request:
        return heapq.heappop(self._heap)           # priority -> arrival

    def prepend_request(self, request: Request) -> None:
        # priority 队列没有「队头」概念：按 (priority, arrival_time) 重新插入
        self.add_request(request)
```

删减说明：省略了 remove/remove_requests/__iter__/__bool__/__len__ 等与调度主路径关系较弱的操作，保留 add/pop/prepend 三个决定队列语义的核心方法。`extendleft` 在 `prepend_requests` 里会反转顺序（注释已说明），这是 FCFS 队列回队一批请求时容易写错的点。

## 导读

调度器的等待队列不是「一个队列」，而是两个数据结构的抽象：FCFS 用 deque（头部出、尾部进），priority 用 heap（按 `priority → arrival_time → request_id` 全序）。选错模型会导致一类典型故障：你设置了 `--scheduling-policy priority` 并给付费用户请求设了高优先级，却发现在线突发时「低优先级老请求」和「高优先级新请求」交错执行——因为抢占后请求要回队，而 priority 队列的回队不是回原位置，而是按字段重新排序。

先建立反例：FCFS 模式下抢占请求用 `appendleft` 回到队头，保证「被赶走的请求恢复后最先再被接纳」；priority 模式下同一个操作变成 `heappush`，被抢占的请求可能排到一堆新请求后面——两种模式对「回队」的语义完全不同，直接套用会误解调度顺序。

本课与前课的关系：vllm-01-06 讲了 Request 对象的 `priority`/`arrival_time` 字段与 `__lt__` 排序，本课把这些字段放进队列实现与调度循环；vllm-01-03 讲了抢占的触发条件与代价，本课补「被抢占的请求去哪、按什么顺序回来」。拆分理由：队列数据结构（本课）与抢占决策（01-03）是两个独立失败面——前者错在次序，后者错在触发条件。

## 分章正文

### 两个队列模型的行为差异

kicker: "01 · OBSERVE"

FCFS 队列：`add` 尾部进、`pop` 头部出、`prepend` 头部回——顺序完全由到达次序决定，任何时刻弹出来的一定是「最早还在等」的请求。priority 队列：堆按 `__lt__` 维护，弹出来的一定是「priority 最小；同 priority 时 arrival 最早」的请求——顺序由字段决定，与「进队先后」无关。

观察实验：往两个队列各放三个请求（优先级不同、到达时间交错），FCFS 恒按到达顺序弹出；priority 恒按 priority 升序弹出、同优先级再按 arrival。相同的插入序列，两种模型给出不同弹出顺序——这是全课第一个必须钉死的直觉。

#### 本章结论

FCFS 由到达次序决定顺序（O(1) 进出）；priority 由字段全序决定顺序（O(log n) 进出）。

### 回队语义：appendleft 与 heappush 的差别

kicker: "02 · MODEL"

调度器需要「回队」因为抢占：KV 不足时运行中的请求被 `_preempt_request` 移出，等待下一轮再进。回队的落点决定恢复后的服务顺序：

- FCFS：`appendleft` 回到队头，被抢占的请求优先于所有还在等的新请求——「老请求恢复优先」。
- priority：`heappush` 按 (priority, arrival_time) 重插——**arrival_time 还是最初到达时间**（Request 构造时固化），所以被抢占的老请求在相同 priority 下仍然排在后面到达的新请求前面；但如果它 priority 低，就可能被高优先级新请求越过。

一个隐蔽差异：FCFS 的 `prepend_requests` 用 `extendleft`，一批请求回队时**顺序反转**（注释原文 "The requests will be prepended in reverse order"）。调度器把多个被抢占请求批量放回时，队内次序与调用参数相反——不读源码很容易写反。

#### 本章结论

回队落点决定恢复顺序：FCFS 回队头（批量回队顺序反转），priority 按字段重插（arrival_time 保持初始值）。

### 调度循环怎么用队列

kicker: "03 · SOURCE"

`scheduler.py` v0.26.0 里队列的使用有三处关键：

- 初始化（L183-185）：`self.waiting = create_request_queue(self.policy)` 与 `self.skipped_waiting = create_request_queue(self.policy)`——**两个队列**，不是一个大队列。
- waiting 循环（L667-706）：`step_skipped_waiting` 每轮新建，`_select_waiting_queue_for_scheduling()`（L1974-1986）在 waiting 与 skipped_waiting 之间选择：两个队都有请求时比较 `peek` 的 `__lt__`，取更小的那个；`peek_request()` 先看不取出，满足预算与 KV 条件才 `pop_request()`。
- 抢占回队（L1233）：`self.waiting.prepend_request(request)`——被抢占请求放回 waiting，而不是 skipped_waiting。

`num_requests_waiting` 指标 = `len(waiting) + len(skipped_waiting)`（L2118），`num_requests_waiting_by_reason` 的 capacity 标签对应「等待调度容量」的请求。skipped_waiting 的存在是为了**延迟**某些请求（LoRA 预算、KV 传输、blocked 状态），它们从 waiting 被挪到 skipped_waiting，等约束解除再回来——所以 `num_requests_waiting` 的两种来源要分开看。

#### 本章结论

调度器维护 waiting + skipped_waiting 双队列；peek 先看后取，抢占回队用 prepend；skipped_waiting 装被延迟的请求（容量之外的原因）。

### 失败路径：空队列、低优先级饥饿与顺序反转

kicker: "04 · FAILURE"

队列操作有四个真实失败边界：

1. **空队列 peek 抛错**：`FCFSRequestQueue.peek_request` 与 `PriorityRequestQueue.peek_request` 都对空队列抛 `IndexError`（"peek from an empty queue"）——调度循环必须在 peek 前判空。
2. **priority 饥饿**：高优先级请求源源不断时，低优先级 waiting 请求可能长期得不到服务。vLLM 没有内置 aging 机制——`arrival_time` 只在同 priority 内比较，低 priority 请求不会随时间「升级」。这是 priority 策略需要外部治理（限流、配额）的原因。
3. **remove 的 O(n)**：`FCFSRequestQueue.remove_request` 与 `PriorityRequestQueue.remove_request`（heap 用 `remove + heapify`）都是 O(n)——请求取消/中止密集时成为调度器热点。
4. **prepend_requests 反转**：FCFS 批量回队顺序反转，多请求恢复时队内次序与预期相反。

#### 本章结论

空队列 peek 抛错须先判空；priority 无 aging 会饥饿低优先级；remove 是 O(n) 热点；批量回队顺序反转。

### 双队列的工程取舍

kicker: "05 · ENGINEERING"

用两个队列而不是一个「可排序的大队列」是工程决策：waiting 队列只装「现在就绪」的请求，skipped_waiting 装「被延迟」的请求，`_select_waiting_queue_for_scheduling` 每次比较两个队头即可，避免在插入时给每个请求打时间戳标记。代价是「一个请求为什么在等待」需要查 `num_requests_waiting_by_reason` 的标签才能区分 capacity 与 deferred——两个原因混在一个指标里是监控上的坑。priority 队列的 O(log n) 在万级 waiting 时依旧亚毫秒，不是热点；真正的热点是 remove（取消风暴）与 `__lt__` 的比较开销（每次 heap 操作都读 priority/arrival_time/id）。

#### 本章结论

双队列分离「就绪」与「延迟」两类等待，peek 比较队头即可；监控上 capacity/deferred 两个标签分开看。

### 怎么验证：观测队列深度与等待原因

kicker: "06 · VERIFY"

`/metrics` 提供三个观测点：`vllm:num_requests_waiting`（总深度）、`vllm:num_requests_waiting_by_reason`（capacity/deferred 分标签）、`vllm:request_queue_time_seconds`（排队时间直方图，对应 per-request metrics 的 `queue_time_ms`）。诊断：排队时间飙升但 `num_requests_waiting` 不大 → 个别长请求卡住（查 `request_prompt_tokens` 长尾）；`waiting_by_reason{reason="capacity"}` 持续高 → 容量不足（vllm-01-10 的容量模型）；`deferred` 高 → LoRA 预算或 KV 传输阻塞。本课示例离线复现双队列的 peek/pop/prepend 语义与顺序反转，作为调度顺序的离线验证。

#### 本章结论

用 num_requests_waiting / by_reason / queue_time 三组指标区分等待原因；离线用示例复现队列语义。

## 核心机制

- FCFS = deque：add 尾部、pop 头部、prepend 头部回队，全 O(1)。
- priority = heap：按 (priority, arrival_time, request_id) 全序，add/pop O(log n)。
- 抢占回队：FCFS 用 appendleft 回队头，priority 用 heappush 按字段重插。
- 调度循环维护 waiting + skipped_waiting 双队列，peek 先看后取。
- FCFS 批量回队 `extendleft` 顺序反转；priority 无 aging，低优先级可能饥饿。
- num_requests_waiting = waiting + skipped_waiting，by_reason 分 capacity/deferred。

## 常见误区

- 以为 priority 队列回队会回到原位置；它按字段重新排序，arrival_time 保持初始值。
- 以为两个队列的 prepend 语义相同；FCFS 回队头，priority 重插堆。
- 忽略 `extendleft` 的顺序反转；批量回队时队内次序与调用参数相反。
- 把 `num_requests_waiting` 当单一指标；capacity 与 deferred 两种等待原因要分开。
- 以为 priority 有老化机制；vLLM 无 aging，低优先级可能长期饥饿。

## 实现变体

### 变体 A：FCFS deque 实现

useWhen: "默认部署，请求无优先级差异，要求顺序可预测。"
tradeoff: "获得：O(1) 进出队、实现最简单、顺序严格由到达决定；牺牲：无法插队，紧急请求必须等待。"

#### 代码

```python
from collections import deque


class FCFSQueue:
    def __init__(self) -> None:
        self._q: deque[str] = deque()

    def add(self, item: str) -> None:
        self._q.append(item)

    def pop(self) -> str:
        return self._q.popleft()

    def prepend(self, item: str) -> None:
        self._q.appendleft(item)
```

### 变体 B：priority 堆实现

useWhen: "需要 SLA 分级、付费优先级或内部请求优先。"
tradeoff: "获得：priority 小的先处理，同优先级退化为 FCFS；牺牲：O(log n) 开销、无 aging、需外部治理防饥饿。"

#### 代码

```python
import heapq


class PriorityQueue:
    def __init__(self) -> None:
        self._heap: list[tuple[int, float, str]] = []

    def add(self, priority: int, arrival: float, item: str) -> None:
        heapq.heappush(self._heap, (priority, arrival, item))

```

## 可运行示例

```python
import heapq
from collections import deque


class FCFSQueue:
    """复刻 request_queue.py 的 FCFSRequestQueue 语义（deque）。"""

    def __init__(self) -> None:
        self._q: deque[str] = deque()

    def add(self, item: str) -> None:
        self._q.append(item)

    def pop(self) -> str:
        return self._q.popleft()

    def prepend(self, item: str) -> None:
        self._q.appendleft(item)

    def prepend_all(self, items: list[str]) -> None:
        self._q.extendleft(items)      # 注意：顺序反转（与上游一致）

    def peek(self) -> str:
        return self._q[0]

    def __len__(self) -> int:
        return len(self._q)


class PriorityQueue:
    """复刻 PriorityRequestQueue 语义：priority -> arrival -> id。"""

    def __init__(self) -> None:
        self._heap: list[tuple[int, float, str]] = []

    def add(self, priority: int, arrival: float, item: str) -> None:
        heapq.heappush(self._heap, (priority, arrival, item))

    def pop(self) -> str:
        return heapq.heappop(self._heap)[2]

    def peek(self) -> str:
        return self._heap[0][2]

    def __len__(self) -> int:
        return len(self._heap)


# ---- 断言 1：FCFS 顺序严格由到达决定 ----
fcfs = FCFSQueue()
for r in ["r1", "r2", "r3"]:
    fcfs.add(r)
assert [fcfs.pop() for _ in range(3)] == ["r1", "r2", "r3"]

# ---- 断言 2：priority 顺序由字段决定（priority -> arrival）----
pq = PriorityQueue()
pq.add(priority=1, arrival=0.0, item="low-priority-early")
pq.add(priority=0, arrival=5.0, item="high-priority-late")
pq.add(priority=0, arrival=3.0, item="high-priority-earlier")
assert pq.pop() == "high-priority-earlier"     # priority 0 且 arrival 最早
assert pq.pop() == "high-priority-late"
assert pq.pop() == "low-priority-early"

# ---- 断言 3：抢占回队——FCFS 回队头 ----
fcfs2 = FCFSQueue()
for r in ["a", "b", "c"]:
    fcfs2.add(r)
fcfs2.pop()                                     # 处理 a
fcfs2.prepend("a")                              # a 被抢占回队头
assert fcfs2.pop() == "a"                       # 恢复优先于 b、c

# ---- 断言 4：priority 回队按字段重插，arrival 保持初始值 ----
pq2 = PriorityQueue()
pq2.add(priority=0, arrival=1.0, item="x")
pq2.add(priority=0, arrival=2.0, item="y")
pq2.add(priority=0, arrival=3.0, item="z")
pq2.pop()                                       # 弹出 x
pq2.add(priority=0, arrival=1.0, item="x")      # x 被抢占后按原 arrival 重插
assert pq2.pop() == "x"                         # 仍然最早（同 priority）

# ---- 断言 5：低优先级被高优先级越过（饥饿风险）----
pq3 = PriorityQueue()
pq3.add(priority=5, arrival=0.0, item="old-low")
pq3.add(priority=0, arrival=1.0, item="new-high")
assert pq3.pop() == "new-high"                  # 高优先级插队
assert pq3.pop() == "old-low"                   # 低优先级永远最后

# ---- 断言 6：extendleft 顺序反转 ----
fcfs3 = FCFSQueue()
for r in ["p", "q"]:
    fcfs3.add(r)
fcfs3.prepend_all(["p", "q"])                   # 两个请求被抢占后批量回队
# deque 原有 p,q；extendleft(["p","q"]) 后队首为 q、p
assert fcfs3.pop() == "q", "extendleft 顺序反转：先 pop 出 q"
assert fcfs3.pop() == "p"
```

## 自检

### 问题

FCFS 模式下三个请求 r1、r2、r3 依次入队，r1 被调度后因 KV 不足被抢占回队；随后 r4 到达。请画出此时队列内容与弹出顺序。再说明如果换成 priority 模式（r1-r4 的 priority 分别为 0、0、0、1，arrival 依次为 1、2、3、4），回队后弹出顺序会怎样，以及 priority 模式为什么可能让 r3 长期饥饿。

### 站内答案

结论：FCFS 下 r1 回队头，队列为 [r1, r2, r3, r4]，弹出顺序 r1→r2→r3→r4（r1 恢复优先）。priority 模式下堆按 (priority, arrival) 排序，r4（priority=1）在最后，回队的 r1 按原 arrival=1 重插仍最先，弹出顺序 r1→r2→r3→r4——但若持续有 priority=0 且 arrival 更早的新请求加入，r3 因 arrival 较晚会被不断越过，且 priority 队列没有 aging 机制，低优先级（如 priority=5 的请求）在持续高优先级流量下可能长期得不到服务。机制：FCFS 用 `appendleft` 回队头（request_queue.py L75-129），priority 用 `heappush` 按字段重插且 `arrival_time` 在 Request 构造时固化（request.py L95），所以「回队」不会重置排序键；`Request.__lt__`（L329-341）定义 priority → arrival → id 全序。源码证据：`FCFSRequestQueue.prepend_request` 的 `appendleft`、`PriorityRequestQueue.prepend_request` 的注释「There is no concept of prepending to the front... ordered by (priority, arrival_time)」（request_queue.py L158-165）、调度循环的 `peek_request` 先看后取与 `prepend_request`（scheduler.py L1233）。可运行验证：本课示例断言 3 与 5 分别验证 FCFS 回队头与 priority 越过低优先级；断言 6 验证批量回队顺序反转。工程取舍：priority 策略必须配合外部限流/配额防止饥饿，vLLM 自身无 aging；FCFS 简单可预测但无法插队；双队列（waiting/skipped_waiting）把「就绪」与「延迟」分开，监控上要用 `num_requests_waiting_by_reason` 区分 capacity 与 deferred。适用边界：本结论针对 V1 调度器默认配置；async scheduling（`--async-scheduling`）会引入 `num_output_placeholders` 预占与并发调度，队列语义相同但时序更复杂；spec decode 与多模态请求的入队细节需另查对应分支。
