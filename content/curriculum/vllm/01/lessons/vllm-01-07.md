[Per-Request Metrics](https://docs.vllm.ai/en/latest/features/per_request_metrics/#response-format) 声明 `--enable-per-request-metrics` 后，API 响应携带 `metrics` 对象，含 `time_to_first_token_ms`、`generation_time_ms`、`queue_time_ms`、`mean_itl_ms`、`tokens_per_second` 五个字段——这是逐请求 SLO 观测的官方入口；[Benchmark CLI · Load Pattern Configuration](https://docs.vllm.ai/en/latest/benchmarking/cli/#load-pattern-configuration) 定义 `--request-rate`（每秒请求数，inf 表示同时打满）、`--burstiness`（1.0 为泊松、0.1 为突发、5.0 为均匀）与 `--max-concurrency`（并发上限）——这是验收负载的生成契约。`vllm bench serve --goodput ttft:800 tpot:80 e2el:25000` 把三个 SLO 阈值编码进命令（goodput 概念源自 DistServe 论文 arxiv 2401.09670，vLLM 以 CLI 参数落地，不属于核心引擎承诺）。版本边界 v0.26.0。

### 逐段讲解

- `IterationStats`（L349 起）：每次 engine core 迭代收集的统计容器，字段有 `num_generation_tokens`、`prompt_token_stats`、`time_to_first_tokens_iter`、`inter_token_latencies_iter` 等——它们是 TTFT/TPOT 直方图的原始样本。
- `update_from_output`（L377-426）：每个输出到达时累计生成 token 数；`is_prefilling` 时用 `self._time_since(req_stats.arrival_time)` 记录首 token 延迟（TTFT），并把 `first_token_ts` 固化；否则用 `engine_core_timestamp - req_stats.last_token_ts` 记一次 inter-token latency（ITL/TPOT 样本），并推进 `last_token_ts`。
- `update_from_events`（L428-450）：消费 QUEUED / SCHEDULED / PREEMPTED 事件；`queued_ts` 取 QUEUED 时间戳，`scheduled_ts` 只在首次 SCHEDULED 时写入（抢占不覆盖）。
- `update_from_finished_request`（L452-529）：请求结束时计算 `queued_time = scheduled_ts - queued_ts`、`prefill_time = first_token_ts - scheduled_ts`、`decode_time = last_token_ts - first_token_ts`、`inference_time = last_token_ts - scheduled_ts`、`mean_time_per_output_token = decode_time / (num_generation_tokens - 1)`——这就是 per-request metrics 五字段的来源。
- `RequestStateStats`（L218-263）：保存 `arrival_time`（前端墙钟）、`queued_ts/scheduled_ts/first_token_ts/last_token_ts`（引擎核单调时间）与 `num_generation_tokens`；TTFT 用 arrival 与 first token 的墙钟差，其余区间用单调时间，二者混用是设计事实而非 bug。

class IterationStats:
    def __init__(self) -> None:
        self.num_generation_tokens = 0
        self.prompt_token_stats = PromptTokenStats()
        self.max_num_generation_tokens_iter: list[int] = []
        self.inter_token_latencies_iter: list[float] = []   # ITL/TPOT 样本
        self.time_to_first_tokens_iter: list[float] = []    # TTFT 样本

    def update_from_output(self, output, engine_core_timestamp,
                           is_prefilling, req_stats, ...) -> None:
        num_new_generation_tokens = len(output.new_token_ids)
        self.num_generation_tokens += num_new_generation_tokens
        if is_prefilling:
            # 首 token：相对前端 arrival_time 计算 TTFT
            first_token_latency = self._time_since(req_stats.arrival_time)
            self.time_to_first_tokens_iter.append(first_token_latency)
            req_stats.first_token_latency = first_token_latency
            req_stats.first_token_ts = engine_core_timestamp
        else:
            # 非首 token：相邻输出时间差 = ITL/TPOT
            itl = engine_core_timestamp - req_stats.last_token_ts
            self.inter_token_latencies_iter.append(itl)
        req_stats.num_generation_tokens += num_new_generation_tokens
        req_stats.last_token_ts = engine_core_timestamp

    def update_from_finished_request(self, finish_reason, request_id,
                                     num_prompt_tokens, max_tokens_param,
                                     req_stats, ...) -> None:
        e2e_latency = self._time_since(req_stats.arrival_time)
        queued_time = req_stats.scheduled_ts - req_stats.queued_ts
        prefill_time = req_stats.first_token_ts - req_stats.scheduled_ts
        decode_time = req_stats.last_token_ts - req_stats.first_token_ts
        inference_time = req_stats.last_token_ts - req_stats.scheduled_ts
        mean_time_per_output_token = (
            decode_time / (req_stats.num_generation_tokens - 1)
            if req_stats.num_generation_tokens - 1 > 0 else 0
        )

## 导读

SLO（Service Level Objective）不是「快就行」，而是「在给定时间窗口内，多少个百分位的请求达标」。vLLM 提供了完整链路：`--enable-per-request-metrics` 让每个响应带上 TTFT/生成时间/排队时间/ITL/每秒 token 五个字段，`vllm bench serve --goodput ttft:800 tpot:80 e2el:25000` 在验收时直接算出「达标请求的比例」（goodput）。看懂这条链路，才能回答「这个服务的延迟好不好」这种看似简单的问题。

先建立一个反例：某团队上报「平均 TTFT 180ms，性能优秀」。但把直方图拉出来，p99 TTFT 是 2.4s——长尾请求全部超时。平均值被短请求稀释，掩盖了排队与长 prompt 带来的尾部劣化。SLO 的正确姿势是「p99 TTFT ≤ 800ms，28 天窗口，error budget 2%」，用分位数而不是均值做契约。

本课与前课的关系：vllm-01-02 讲了 TTFT/TPOT 四段区间从事件时间戳怎么算，本课把同一套区间放进「SLO 目标 × 负载生成 → goodput 判定」的验收流程；vllm-01-06 讲请求形状，本课讨论「形状分布如何影响达标率」。拆分理由：计算区间（01-02）与「用区间做目标管理」（本课）的失败模式不同——前者错在公式，后者错在统计口径与负载设计。

## 分章正文

### 平均延迟为什么骗人

kicker: "01 · OBSERVE"

构造一组 TTFT 样本：90 个请求各 100ms，10 个请求 20s。平均值 = (90×0.1 + 10×20) / 100 ≈ 2.1s——看起来「平均 2.1 秒，勉强可接受」。但 p95 = 20s，即 10% 的请求比中位数慢 200 倍。任何基于平均值的告警都会漏掉这个尾部。SLO 的正确形态是分位数契约：「p99 TTFT ≤ 800ms」意味着只有 1% 的请求可以超过 800ms——这 1% 就是 error budget。

一个常犯的反例：99 个 100ms + 1 个 20s 的分布里 p99 是 100ms（第 99 个值），平均值却被拉到 300ms——此时「平均慢」但「p99 快」，两者同样会误导。分位数的意义在于暴露你选择的尾部：p99 暴露 1% 尾部，p95 暴露 5% 尾部，选哪个取决于业务能容忍多少比例的慢请求。

vLLM 的直方图指标（`vllm:time_to_first_token_seconds` 等）天然支持分位数查询：PromQL 用 `histogram_quantile(0.99, rate(vllm:time_to_first_token_seconds_bucket[5m]))` 直接得到 p99。平均值只是直方图的一种退化视角，不该作为 SLO 指标。

#### 本章结论

SLO 用分位数契约（如 p99 TTFT ≤ 800ms），平均值会掩盖长尾；vLLM 直方图直接支持分位数查询。

### 五个 per-request 字段的口径

kicker: "02 · MODEL"

`--enable-per-request-metrics` 后每个响应带 `metrics` 对象，五个字段口径必须精确理解：

- `time_to_first_token_ms`：从**调度开始**（scheduled）到首 token。注意官方文档说 "Time from when the request was scheduled until the first output token was generated"——不含排队时间。要「用户感知的 TTFT」需另加 `queue_time_ms`。
- `generation_time_ms`：decode 阶段（首 token 到末 token），不含排队与 prefill。
- `queue_time_ms`：在调度器等待队列中停留的时间。
- `mean_itl_ms`：decode 期间相邻输出 token 的平均间隔；单 token 响应为 null。
- `tokens_per_second`：`生成 token 数 / inference 区间`（scheduled 到末 token），**包含 prefill 时间**——官方明确它与 `generation_time_ms` 不同，反映的是端到端生成速度而非纯 decode 速度。

陷阱：用 `tokens_per_second` 当 decode 吞吐会系统性偏低（长 prefill 稀释）；要看纯 decode 用 `mean_itl_ms` 的倒数。

#### 本章结论

五个字段对应五个不同区间：TTFT（scheduled→首 token）、generation（首→末）、queue（queued→scheduled）、ITL（相邻输出）、tokens/s（scheduled→末，含 prefill）。

### SLO 目标与 goodput 判定

kicker: "03 · SOURCE"

`vllm bench serve --goodput ttft:800 tpot:80 e2el:25000` 的含义：ttft ≤ 800ms、tpot ≤ 80ms、e2el ≤ 25s 同时达标才算 goodput 请求。goodput 是「达标请求数 / 总请求数」或「达标吞吐」，源自 DistServe 论文（arxiv 2401.09670）——它把「服务质量」从「总吞吐」里分离出来：一个系统可以吞吐很高，但大部分请求超时；goodput 直接度量「合格的服务」。

bench 的负载参数决定达标率怎么波动：`--request-rate 4 --burstiness 1 --max-concurrency 16` 用泊松到达模拟在线流量；`burstiness 0.1` 制造突发（CV≈3.16），`5.0` 制造均匀流（CV≈0.45）。验收时必须同时报告 p50/p95/p99 与 goodput，只看「最高分」会掩盖达标率。

#### 本章结论

goodput = 全部指定 SLO 同时达标的请求占比；负载参数（request-rate/burstiness/max-concurrency）决定达标率的压力场景。

### 三种失败：排队、prefill 竞争与 decode 膨胀

kicker: "04 · FAILURE"

SLO 违约有三种不同机制，诊断方向完全不同：

1. **TTFT 劣化而 TPOT 稳定**：排队或 prefill 竞争。查 `queue_time_ms` 与 `num_requests_waiting`——长 prompt 挤占预算（vllm-01-06），或 `request-rate` 超过处理能力。
2. **TPOT 劣化而 TTFT 稳定**：decode 批次过大或 KV 压力。查 `num_requests_running` 与 `kv_cache_usage_perc`——`max_num_seqs` 太大让 decode 批算不过来。
3. **两者同时劣化**：显存或实例级瓶颈。查 `kv_cache_usage_perc > 90%`、`num_preemptions` 增长——抢占导致重算（vllm-01-03 的代价模型）。

还有一类隐蔽失败：`--max-concurrency` 与 `--request-rate` 的相互作用。`request-rate` 高于服务能力时，实际执行速率被并发上限截断，此时报告的 TTFT 只是「能进去的请求」的延迟，被挡住的请求不在样本里——验收结果虚高。必须同时报告请求成功率与拒绝率。

#### 本章结论

TTFT/TPOT 分开劣化指向不同机制（排队 vs decode 批）；并发上限会截断样本，验收必须带成功率。

### 从指标到 error budget 的工程闭环

kicker: "05 · ENGINEERING"

生产化 SLO 要闭环：定义 SLI（p99 TTFT）→ 设目标（800ms）→ 开 `--enable-per-request-metrics` 采集 → 用直方图算分位数 → 与目标比对 → 触发扩容或限流。vLLM 侧可操作的三件事：调 `max_num_seqs`/`max_num_batched_tokens` 控制 decode 批大小；用 `--scheduling-policy priority` 给核心请求插队；用 `--max-concurrency` 在网关层做背压保护。注意 error budget 是「窗口内的违约额度」不是「每请求许可」——28 天窗口 99.9% 达标意味着每天最多 86 秒可以全部违约，告警要看 burn rate 而不是瞬时值。

#### 本章结论

SLO 是定义 → 采集 → 比对 → 动作的闭环；error budget 按窗口管理，用 burn rate 告警。

### 怎么验证：一次完整的 goodput 验收

kicker: "06 · VERIFY"

官方验证路径：`vllm serve --enable-per-request-metrics` 起服务，另开终端 `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --num-prompts 1000 --request-rate 4 --burstiness 1 --percentile-metrics ttft,tpot,e2el --metric-percentiles 50,90,95,99 --goodput ttft:800 tpot:80 e2el:25000`。输出会给出各分位数与 goodput。判读：goodput 低于目标 → 降低接入速率或扩容；TTFT 分位劣化 → 查排队；TPOT 劣化 → 查 decode 批。离线无法起服务时，本课示例用合成的样本分布复现 p99 稀释效应与 goodput 判定逻辑，作为统计口径的离线验证。

#### 本章结论

用 `bench serve` + `--goodput` 做验收，分位数与 goodput 一起判读；离线用合成分布验证口径。

## 核心机制

- SLO 是分位数契约（p99 TTFT ≤ 阈值），平均值掩盖长尾。
- per-request metrics 五个字段对应五个不同区间，tokens/s 含 prefill。
- goodput = 所有指定 SLO 同时达标的请求占比（DistServe 概念，CLI 落地）。
- 负载参数 request-rate / burstiness / max-concurrency 决定验收压力场景。
- TTFT 劣化查排队，TPOT 劣化查 decode 批；并发上限会截断样本。
- error budget 按窗口管理，用 burn rate 告警。

## 常见误区

- 用平均 TTFT 当 SLO 指标；尾部劣化被平均值稀释。
- 把 `tokens_per_second` 当 decode 吞吐；它含 prefill，偏低于纯 decode。
- 以为 `--goodput` 是 vLLM 引擎承诺；它是 bench CLI 的验收计算，源自 DistServe 论文。
- 只报告 p99 不报告成功率；被 max-concurrency 挡住的请求不在样本里。
- 忽略 TTFT 与 TPOT 的分开劣化模式，统一归因为「负载高」。

## 实现变体

### 变体 A：分位数阈值判定（直方图离线）

useWhen: "只有聚合直方图、无逐请求明细时，快速判定达标率。"
tradeoff: "获得：无需逐请求数据，PromQL 直接算；牺牲：分位数是估计值，桶边界内均匀假设在长尾下误差大。"

#### 代码

```python
def quantile_from_histogram(percentile: float,
                            buckets: dict[float, int]) -> float:
    """从累计桶计数近似分位数（桶内线性插值）。"""
    total = sum(buckets.values())
    target = percentile * total
    acc = 0
    prev_bound, prev_acc = 0.0, 0
    for bound, count in sorted(buckets.items()):
        acc += count
        if acc >= target:
            frac = (target - prev_acc) / (acc - prev_acc) if count else 0
            return prev_bound + frac * (bound - prev_bound)
        prev_bound, prev_acc = bound, acc
    return prev_bound
```

### 变体 B：逐请求 goodput 判定

useWhen: "开了 --enable-per-request-metrics，有逐请求五字段时。"
tradeoff: "获得：精确到请求的达标判定，可复现可审计；牺牲：需要逐请求明细，高并发下计算开销不可忽略（官方文档已提示）。"

#### 代码

```python
def goodput_ratio(requests: list[dict[str, float]],
                  ttft_ms: float, tpot_ms: float,
                  e2el_ms: float) -> float:
    """统计同时满足三个 SLO 的请求占比。"""
    passed = 0
    for r in requests:
        ok = (r["ttft_ms"] <= ttft_ms and r["tpot_ms"] <= tpot_ms
              and r["e2el_ms"] <= e2el_ms)
        passed += int(ok)
    return passed / len(requests)
```

## 可运行示例

```python
def quantile_from_histogram(percentile, buckets):
    total = sum(buckets.values())
    target = percentile * total
    acc = 0
    prev_bound, prev_acc = 0.0, 0
    for bound, count in sorted(buckets.items()):
        acc += count
        if acc >= target:
            frac = (target - prev_acc) / (acc - prev_acc) if count else 0
            return prev_bound + frac * (bound - prev_bound)
        prev_bound, prev_acc = bound, acc
    return prev_bound


def goodput_ratio(requests, ttft_ms, tpot_ms, e2el_ms):
    passed = 0
    for r in requests:
        if (r["ttft_ms"] <= ttft_ms and r["tpot_ms"] <= tpot_ms
                and r["e2el_ms"] <= e2el_ms):
            passed += 1
    return passed / len(requests)


def synthetic_ttft(n_fast=90, n_slow=10, fast_ms=100, slow_ms=20000):
    """构造 90 个 100ms + 10 个 20s 的样本，复现平均值的稀释效应。"""
    return [fast_ms] * n_fast + [slow_ms] * n_slow


# ---- 断言 1：平均值 vs p95 的稀释效应 ----
samples = synthetic_ttft()
mean = sum(samples) / len(samples)
# 桶化（1s 步长）后近似 p95
buckets: dict[float, int] = {}
for s in samples:
    b = (s // 1000 + 1) * 1000.0
    buckets[b] = buckets.get(b, 0) + 1
p95 = quantile_from_histogram(0.95, buckets)
assert mean < 3000, f"平均被稀释到 {mean:.0f}ms"
assert p95 > 10000, f"p95 应接近 20s，实际 {p95:.0f}ms"
assert p95 > 3 * mean                        # p95 远超平均值

# ---- 断言 2：goodput 判定 ----
reqs = [
    {"ttft_ms": 100, "tpot_ms": 30, "e2el_ms": 3000},   # 全达标
    {"ttft_ms": 900, "tpot_ms": 30, "e2el_ms": 3000},   # TTFT 超标
    {"ttft_ms": 100, "tpot_ms": 90, "e2el_ms": 3000},   # TPOT 超标
    {"ttft_ms": 100, "tpot_ms": 30, "e2el_ms": 26000},  # E2EL 超标
    {"ttft_ms": 100, "tpot_ms": 30, "e2el_ms": 3000},   # 全达标
]
ratio = goodput_ratio(reqs, ttft_ms=800, tpot_ms=80, e2el_ms=25000)
assert abs(ratio - 0.4) < 1e-9                # 5 个里 2 个达标

# ---- 断言 3：全部达标时 goodput = 1 ----
all_ok = [{"ttft_ms": 50, "tpot_ms": 20, "e2el_ms": 2000}] * 100
assert goodput_ratio(all_ok, 800, 80, 25000) == 1.0

# ---- 断言 4：tokens_per_second 含 prefill（口径验证）----
def tokens_per_second(generated: int, inference_seconds: float) -> float:
    return generated / inference_seconds


tps_with_prefill = tokens_per_second(256, 2.5)   # 含 2s prefill + 0.5s decode
tps_decode_only = 256 / 0.5
assert tps_with_prefill < tps_decode_only        # 含 prefill 明显更低

# ---- 断言 5：max-concurrency 截断样本（模拟被挡请求不入样本）----
def reported_vs_true(request_rate: float, capacity: float,
                     concurrency: int) -> dict[str, float]:
    """request_rate 高于 capacity 时，实际速率被并发上限截断。"""
    admitted = min(request_rate, capacity)
    dropped = max(request_rate - admitted, 0.0)
    return {"admitted": admitted, "dropped": dropped,
            "loss_ratio": dropped / request_rate if request_rate else 0.0}


r = reported_vs_true(request_rate=10.0, capacity=4.0, concurrency=16)
assert r["admitted"] == 4.0 and r["loss_ratio"] == 0.6   # 60% 请求未入样本
```

## 搭积木复现

### 积木 1：构造长尾样本

生成 90×100ms + 10×20s 的 TTFT 样本，计算平均值并断言其远低于 p95——建立「平均骗人」的直觉。

### 积木 2：实现直方图分位数

实现 `quantile_from_histogram`（桶内线性插值），用同一批样本断言 p95 接近 20s 而均值 <3s。

### 积木 3：实现 goodput 判定

实现 `goodput_ratio`（三个 SLO 同时达标计数），用五个合成请求断言 40% 达标；全部达标时返回 1.0。

### 积木 4：加入口径对比

对比 `tokens_per_second`（含 prefill）与 decode-only 的数值，断言前者更低——理解五字段口径差异。

### 积木 5：模拟并发截断

实现 admitted/dropped 计算，断言 `request_rate > capacity` 时 60% 请求被挡在样本外——解释验收虚高的来源；再对照官方文档 `--max-concurrency` 与 `--request-rate` 的说明，说明本课省略了 burstiness 的 Gamma 分布细节，验收时两者必须联用。

## 自检

### 问题

某服务用 `vllm bench serve --goodput ttft:800` 验收，结果 goodput 98% 但线上客户仍频繁投诉首 token 慢。请指出验收口径可能漏掉的三种情况，并写出正确的验收命令要点。

### 站内答案

结论：98% goodput 可能因为三个口径问题——只设了 `ttft:800` 没设 tpot/e2el（其他指标无目标不算违约，goodput 判定只在声明过的指标上生效）；`--request-rate` 超过服务能力被 `--max-concurrency` 截断，被挡请求不入样本；负载是泊松平稳流（burstiness=1），没有覆盖真实突发场景。机制：goodput 是「声明过的 SLO 同时达标」的占比，未声明的指标不参与判定；`request-rate > capacity` 时实际执行速率被并发上限截断，延迟样本只含「能进去的请求」；`burstiness` 控制到达分布，平稳流下的 p99 不代表突发下的 p99。源码证据：`--goodput` 参数语义（ttft/tpot/e2el 毫秒阈值，同时达标才计 goodput）见 Benchmark CLI 文档；`--request-rate`（默认 inf）、`--burstiness`（默认 1.0）、`--max-concurrency` 的说明见 Load Pattern Configuration 一节；per-request 五字段口径见 features/per_request_metrics 的 Response Format。可运行验证：用本课示例的 `goodput_ratio` 只传 ttft 阈值重跑，断言 tpot/e2el 超标的请求仍计为达标（因为未声明）；再用 `reported_vs_true(10, 4, 16)` 断言 60% 请求被截断。工程取舍：验收应同时声明 ttft/tpot/e2el 三个阈值、报告 p50/p95/p99 与成功率、至少加一组突发负载（burstiness 0.1-0.5）；生产监控用 PromQL `histogram_quantile(0.99, rate(vllm:time_to_first_token_seconds_bucket[5m]))` 持续跟踪而不是一次性 bench。适用边界：goodput 是验收工具不是引擎行为，vLLM 运行期不强制 SLO；多模态与流式请求的 per-request metrics 存在字段差异（n>1 时 metrics 为 null），这些场景的 SLO 采集需另做适配。
