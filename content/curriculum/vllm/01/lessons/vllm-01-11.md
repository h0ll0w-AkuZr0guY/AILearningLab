### 逐段讲解

- `BenchmarkMetrics`（L321-354）：dataclass 定义一份基线的全部字段——`completed/failed`（成功/失败请求数）、`total_input/total_output`（输入/输出 token 总数）、`request_throughput`（req/s）、`request_goodput`（达标 req/s）、`output_throughput`（输出 token/s）、`total_token_throughput`（总 token/s），以及 TTFT/TPOT/ITL/E2EL 的 `mean/median/std/percentiles`——这是结果 JSON 的字段蓝图。
- `calculate_metrics`（L556-735）：遍历请求输出，`outputs[i].success` 的请求计入 `completed` 并收集 `ttfts`/`tpots`/`itls`/`e2els` 样本；`completed / dur_s` 得 request_throughput，`(total_input + sum(actual_output_lens)) / dur_s` 得 total_token_throughput。
- goodput 判定（L622-645）：`goodput_config_dict` 里的 `ttft/tpot/e2el` 阈值（毫秒）除以 1000 转秒后与每个请求的三个指标比较，`is_good_req = all(s >= r for s, r in zip(slo_values, req_metric))`——三个 SLO 全部满足才算达标请求，`good_completed / dur_s` 得 request_goodput。
- 结果输出与 JSON（L1140-1250）：终端打印各字段，同时组装 `result` dict（`duration/completed/failed/total_input_tokens/...`）——`--save-result` 时写盘，`--save-detailed` 追加 `ttfts/itls/generated_texts/errors` 等原始明细。
- `save_to_pytorch_benchmark_format`（L1400-1433）：从 result 抽取 `median/mean/std/p99_ttft_ms` 等 12 个指标转成 PyTorch benchmark 格式，`.pytorch.json` 后缀——这是 CI 回归对比的机器可读基线格式。

## 导读

「服务基线」就是一份可复现的性能快照：在固定的负载形态（请求速率、突发性、并发上限）下，用 `vllm bench serve` 跑出一组吞吐与延迟分位数，保存成 JSON，下次改动后再跑一次对比。没有基线，任何「优化」都只是感觉——你说快了 20%，拿什么证明？本课把 bench serve 从「一个能跑的命令」拆成「数据是怎么算出来的」，让你能看懂基线报告、能判断基线是否可信、能把它接进回归流程。

先建立反例：有人跑 `vllm bench serve --dataset-name random --num-prompts 1000`（`--request-rate` 默认 inf），报告「request throughput 178 req/s」。这个数字几乎无意义——`request-rate=inf` 表示 1000 个请求在同一瞬间全部发出，测的是「无背压饱和吞吐」，不代表任何真实负载形态。换 `--request-rate 4 --burstiness 1`，同一实例可能只有 3.9 req/s。基线必须连同负载参数一起记录，否则就是一次性的、不可比的数字。

本课与前课的关系：vllm-01-07 讲了 per-request metrics 五字段与 goodput 的统计口径，vllm-01-09 讲了 /metrics 的 Counter/直方图口径——本课把这些指标放进 `vllm bench serve` 的**一次性基准测试**流程里，解释 `BenchmarkMetrics` 如何聚合它们、结果如何落盘；vllm-01-10 的容量模型为基线提供「为什么会是这些数」的解释。拆分理由：指标口径（01-07/01-09）是「持续观测」，服务基线（本课）是「离散验收+回归对比」——前者错在换算，后者错在负载不可比与基线不可复现。

## 分章正文

### 一份基线报告长什么样

kicker: "01 · OBSERVE"

`vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --num-prompts 1000 --request-rate 4` 的输出（官方文档示例结构）：

```
Successful requests:                     10
Benchmark duration (s):                  5.78
Total input tokens:                      1369
Total generated tokens:                  2212
Request throughput (req/s):              1.73
Output token throughput (tok/s):         382.89
Total token throughput (tok/s):          619.85
---------------Time to First Token----------------
Mean TTFT (ms):                          71.54
Median TTFT (ms):                        73.88
P99 TTFT (ms):                           79.49
-----Time per Output Token (excl. 1st token)------
Mean TPOT (ms):                          7.91
Median TPOT (ms):                        7.96
P99 TPOT (ms):                           8.03
```

读法：`Request throughput` 是请求级吞吐，`Output/Total token throughput` 是 token 级吞吐；TTFT/TPOT/ITL 各给 Mean/Median/P99。一份可信基线必须同时记录：负载参数（request-rate/burstiness/max-concurrency）、数据集（输入输出长度分布）、模型与硬件标识——三者缺一，数字就无法与其他运行对比。

#### 本章结论

基线报告 = 负载形态 + 数据集 + 吞吐/延迟分位数；缺负载参数的数字不可比。

### BenchmarkMetrics：一份基线的字段蓝图

kicker: "02 · MODEL"

`BenchmarkMetrics` dataclass 把一份基线固化成一组字段（serve.py L321-354）：`completed/failed` 是请求计数，`total_input/total_output` 是 token 计数，`request_throughput`/`output_throughput`/`total_token_throughput` 是三个不同粒度的吞吐，TTFT/TPOT/ITL/E2EL 各带 `mean/median/std/percentiles`。四个延迟指标、三个吞吐、两组计数——它们全部由 `calculate_metrics` 从请求输出聚合而来。

不变量：`request_throughput = completed / dur_s`；`total_token_throughput = (total_input + 实际输出总长) / dur_s`；`output_throughput = 总输出 / dur_s`；TTFT 样本只来自成功请求的 `ttft` 字段。`dur_s` 是 bench 的实际运行时长（含所有请求完成时间），不是 `num_prompts / request_rate` 的理论值。

#### 代码

```python
@dataclass
class Baseline:
    """一份服务基线的字段模型（对应 BenchmarkMetrics）。"""
    completed: int
    failed: int
    total_input: int
    total_output: int
    duration_s: float

    @property
    def request_throughput(self) -> float:
        return self.completed / self.duration_s

    @property
    def total_token_throughput(self) -> float:
        return (self.total_input + self.total_output) / self.duration_s
```

#### 本章结论

基线由计数、三个吞吐、四个延迟分位数组装；吞吐都以实际 `dur_s` 为分母。

### 从请求输出到指标：calculate_metrics 的主路径

kicker: "03 · SOURCE"

`calculate_metrics`（L556-735）是聚合核心：对每个 `outputs[i]`，`outputs[i].success` 为真则 `completed += 1` 并追加 `outputs[i].ttft`、`outputs[i].itl` 等样本到对应列表；失败请求只把 `actual_output_lens` 记为 0，不进入延迟统计。全部请求处理后：`request_throughput = completed / dur_s`，`total_token_throughput = (total_input + sum(actual_output_lens)) / dur_s`。`sum(actual_output_lens)` 用 tokenizer 统计实际输出长度（多个 token 可能被打包在一个响应里，`len(itl)` 会低估）。

关键语义：**吞吐分母是 `dur_s`（包含排队与请求间隙），不是单请求延迟的倒数**。`request-rate=4` 且无并发上限时，请求按泊松到达分布在一个时间窗口内，`completed` 是被窗口截住的完成数——所以「配置 4 req/s」与「实测 1.73 req/s」可以同时成立（请求还在排队/执行，窗口结束时未完成的不计入）。

#### 本章结论

成功请求贡献计数与延迟样本，失败请求只占 completed=0 的槽位；吞吐 = 完成数/实际时长。

### goodput：把 SLO 阈值编进基线

kicker: "04 · FAILURE"

`--goodput ttft:800 tpot:80 e2el:25000` 时，`calculate_metrics` 进入 L622-645 的判定分支：把三个阈值（毫秒）转秒后与每个请求的三个指标比较，`all(s >= r)` 全满足才算达标请求，`request_goodput = good_completed / dur_s`。四个失败边界：

1. **未声明指标不参与判定**：只声明 `ttft:800` 时，tpot/e2el 超标的请求仍算达标——goodput 只在你声明的 SLO 上生效（与 vllm-01-07 结论一致）。
2. **失败请求永远不算达标**：`outputs[i].success` 为假时样本根本不进 `ttfts` 列表，goodput 只统计成功且达标的请求。
3. **`completed == 0` 告警**：全部请求失败时 `calculate_metrics` 发 `UserWarning`（"All requests failed..."）——基线全红时 bench 不会崩溃，但结果不可信。
4. **`dur_s` 同时缩小吞吐与 goodput 分母**：`request-rate` 高于处理能力时，窗口内大量请求未完成，`request_throughput` 与 `request_goodput` 一起被拉低——两个数字联动，读报告时不能只看 goodput。

#### 本章结论

goodput = 成功且全 SLO 达标的请求速率；未声明指标不判定、失败请求不计入、全失败时告警。

### 基线落盘：JSON 与 pytorch 格式

kicker: "05 · ENGINEERING"

`--save-result` 把 result dict（`duration/completed/failed/total_input_tokens/.../p99_ttft_ms/...`）写成 JSON；`--save-detailed` 额外保存 `ttfts/itls/generated_texts/errors` 原始明细（注释说「raw data are useful but rather big」，默认省略）。`save_to_pytorch_benchmark_format`（L1400-1433）再抽 12 个核心指标（`median/mean/std/p99_ttft_ms`、`mean_tpot_ms` 等）转成 `.pytorch.json`，供 CI 的 benchmark 对比工具消费——这是「回归对比」的机器可读接口：两次运行各存一份，diff 分位数就能自动发现性能回退。

工程取舍：JSON 全量保存（可审计、体积大），pytorch 格式精简（可对比、缺明细）。`compute_result_filename` 用 `label-request_rateqps-model-time.json` 命名，让同负载同模型的历史基线按文件名即可归档。

#### 本章结论

--save-result 存全量 JSON、--save-detailed 加原始明细、pytorch 格式供 CI 对比；文件名编码负载与模型标识。

### 怎么验证：跑一份可复现基线

kicker: "06 · VERIFY"

官方验证路径：`vllm serve` 起服务，另开终端 `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --num-prompts 1000 --request-rate 4 --burstiness 1 --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,95,99 --goodput ttft:800 tpot:80 e2el:25000 --save-result --save-detailed --result-filename baseline.json`。判读：先看 `Successful requests` 与 `Failed requests`（成功率），再看 goodput 与各分位数；把 `request-rate`/`burstiness`/数据集长度写进报告标题或注释，否则基线不可比。回归流程：改配置后重跑同命令，diff 两份 JSON 的分位数字段（或 pytorch 格式）——TTFT p99 上升 >30% 即触发回退告警。本课示例离线复现 calculate_metrics 的聚合与 goodput 判定，作为基线计算的离线验证。

#### 本章结论

用带负载参数与 goodput 的 bench serve 生成基线并保存 JSON；回归对比 diff 分位数；离线用示例验证聚合逻辑。

## 核心机制

- 基线 = 负载参数 + 数据集 + BenchmarkMetrics（计数/三吞吐/四延迟分位数）。
- request_throughput = completed / dur_s；total_token_throughput = (输入+输出) / dur_s。
- 成功请求贡献延迟样本，失败请求只占 completed=0 槽位；全失败发 UserWarning。
- goodput = 成功且全部声明 SLO 达标的请求速率，未声明指标不判定。
- --save-result 存全量 JSON、--save-detailed 加明细、pytorch 格式供 CI 对比。
- 基线必须连同 request-rate/burstiness/max-concurrency 与数据集一起记录。

## 常见误区

- 用 `--request-rate inf` 的报告当「服务吞吐」；inf 是无背压饱和值，不代表任何真实负载。
- 把配置的 request-rate 当实测吞吐；`dur_s` 窗口内未完成请求不计入 completed。
- 只报 goodput 不报成功率；失败请求不算达标，全失败时只有告警没有崩溃。
- 基线不记录负载参数；同模型两次运行负载不同，数字不可比。
- 用终端打印当审计依据；`--save-result` 的 JSON 才是可归档、可 diff 的基线。

### 变体 A：饱和吞吐基线（request-rate=inf）

useWhen: "评估单实例的吞吐上限（容量规划上界，vllm-01-10 的实测口径）。"
tradeoff: "获得：一次打满并发，暴露峰值吞吐与最坏延迟；牺牲：不代表在线负载形态，TTFT/TPOT 分位数不可用于 SLO 验收。"

#### 代码

```python
def saturated_baseline(completed: int, duration_s: float) -> float:
    """request-rate=inf 时的请求吞吐（饱和值）。"""
    return completed / duration_s
```

### 变体 B：受控负载基线（有限 request-rate + goodput）

useWhen: "SLO 验收与回归对比，需要可复现的在线形态。"
tradeoff: "获得：负载可控、goodput 可判定、结果可归档 diff；牺牲：需要真实服务与更长运行时间，单次跑出的数字对 burstiness 敏感。"

#### 代码

```python
def goodput_rate(good_completed: int, duration_s: float) -> float:
    """声明 goodput 时：达标请求的速率（req/s）。"""
    return good_completed / duration_s
```

## 可运行示例

```python
from dataclasses import dataclass


@dataclass
class ReqOutput:
    """单个请求的 bench 输出（对应 serve.py 的 RequestFuncOutput）。"""
    success: bool
    ttft_s: float = 0.0
    itl_s: list[float] | None = None      # 相邻 token 间隔（不含首 token）
    e2el_s: float = 0.0
    output_tokens: int = 0


def calculate_metrics(outputs: list[ReqOutput], dur_s: float,
                      goodput_ms: dict[str, float] | None = None) -> dict:
    """复刻 serve.py calculate_metrics 的核心聚合（L556-735）。"""
    completed = failed = total_input = 0
    total_output = sum(o.output_tokens for o in outputs)
    ttfts: list[float] = []
    e2els: list[float] = []
    all_tpots: list[float] = []
    good_completed = 0
    for o in outputs:
        total_input += 0  # 输入长度由数据集决定，此处仅计数成功请求
        if o.success:
            completed += 1
            ttfts.append(o.ttft_s)
            e2els.append(o.e2el_s)
            if o.itl_s:
                all_tpots.extend(o.itl_s)
        else:
            failed += 1

    if goodput_ms:
        slo_values, valid_metrics = [], []
        if "ttft" in goodput_ms:
            valid_metrics.append(ttfts)
            slo_values.append(goodput_ms["ttft"] / 1000.0)
        if "tpot" in goodput_ms:
            valid_metrics.append(all_tpots)
            slo_values.append(goodput_ms["tpot"] / 1000.0)
        if "e2el" in goodput_ms:
            valid_metrics.append(e2els)
            slo_values.append(goodput_ms["e2el"] / 1000.0)
        if valid_metrics:
            for req_metric in zip(*valid_metrics):
                if all(s >= r for s, r in zip(slo_values, req_metric)):
                    good_completed += 1

    result = {
        "completed": completed,
        "failed": failed,
        "request_throughput": completed / dur_s if dur_s else 0.0,
        "total_token_throughput": (total_input + total_output) / dur_s if dur_s else 0.0,
        "request_goodput": good_completed / dur_s if dur_s else 0.0,
    }
    if completed:
        result["mean_ttft_ms"] = sum(ttfts) / len(ttfts) * 1000
        result["p99_ttft_ms"] = sorted(ttfts)[int(0.99 * (len(ttfts) - 1))] * 1000
        result["mean_tpot_ms"] = (sum(all_tpots) / len(all_tpots) * 1000
                                  if all_tpots else 0.0)
    return result


def percentile(values: list[float], p: float) -> float:
    s = sorted(values)
    return s[int(p * (len(s) - 1))]


# ---- 断言 1：吞吐 = completed / dur_s ----
outputs = [
    ReqOutput(success=True, ttft_s=0.05, itl_s=[0.01, 0.01], e2el_s=0.2, output_tokens=64),
    ReqOutput(success=True, ttft_s=0.08, itl_s=[0.02], e2el_s=0.3, output_tokens=48),
    ReqOutput(success=True, ttft_s=0.07, itl_s=[0.01, 0.02], e2el_s=0.25, output_tokens=72),
]
r1 = calculate_metrics(outputs, dur_s=1.5)
assert r1["completed"] == 3 and r1["failed"] == 0
assert abs(r1["request_throughput"] - 3 / 1.5) < 1e-9        # 2.0 req/s
assert abs(r1["total_token_throughput"] - (0 + 184) / 1.5) < 1e-9  # 184 tokens

# ---- 断言 2：失败请求计入 failed、不进延迟样本 ----
mixed = outputs + [ReqOutput(success=False, e2el_s=9.9)]
r2 = calculate_metrics(mixed, dur_s=2.0)
assert r2["failed"] == 1 and r2["completed"] == 3
assert r2["request_throughput"] == 3 / 2.0                    # 失败不算完成

# ---- 断言 3：goodput 只在声明指标上判定 ----
slow = [
    ReqOutput(success=True, ttft_s=0.1, itl_s=[0.05, 0.05], e2el_s=30.0, output_tokens=64),
    ReqOutput(success=True, ttft_s=0.2, itl_s=[0.05, 0.05], e2el_s=31.0, output_tokens=64),
]
rg_all = calculate_metrics(slow, 1.0, goodput_ms={"ttft": 800, "tpot": 80, "e2el": 25000})
rg_ttft_only = calculate_metrics(slow, 1.0, goodput_ms={"ttft": 800})
assert rg_all["request_goodput"] == 0.0                      # e2el 30s > 25s，全不达标
assert rg_ttft_only["request_goodput"] == 2.0                # 只声明 ttft：2 个全达标

# ---- 断言 4：p99 与 mean 分离（长尾）----
tail = [ReqOutput(success=True, ttft_s=0.05, itl_s=[0.01], e2el_s=0.2, output_tokens=8) for _ in range(90)]
tail += [ReqOutput(success=True, ttft_s=10.0, itl_s=[0.01], e2el_s=11.0, output_tokens=8) for _ in range(10)]
rt = calculate_metrics(tail, 5.0)
assert rt["mean_ttft_ms"] < 1500                             # 均值被短请求稀释
assert rt["p99_ttft_ms"] > 9000                              # p99 暴露 10s 长尾

# ---- 断言 5：all_tpots 聚合多 token 间隔 ----
multi = [ReqOutput(success=True, ttft_s=0.05, itl_s=[0.01, 0.02, 0.03], e2el_s=0.2, output_tokens=4)]
rm = calculate_metrics(multi, 0.5)
assert abs(rm["mean_tpot_ms"] - 20.0) < 1e-9                # (10+20+30)/3 ms
```

## 搭积木复现

### 积木 1：定义 ReqOutput 与 Baseline 字段

定义 `ReqOutput`（success/ttft/itl/e2el/output_tokens）与 `Baseline` 的计数字段，用 3 个成功请求断言 completed=3。

### 积木 2：实现吞吐聚合

实现 `calculate_metrics` 的 completed/failed 计数与 `request_throughput = completed/dur_s`，断言失败请求计入 failed、吞吐分母为实际时长。

### 积木 3：实现延迟样本收集

成功请求的 ttft/itl/e2el 进列表，失败请求不进；实现 mean 与 p99（`sorted()[int(0.99*(n-1))]`），断言长尾下 p99 远大于 mean。

### 积木 4：实现 goodput 判定

实现 `all(s >= r)` 的逐请求三 SLO 判定，断言只声明 ttft 时 tpot/e2el 超标仍达标、全声明时 e2el 超标全不达标。

## 自检

### 问题

某团队用 `vllm bench serve --request-rate inf --num-prompts 1000 --save-result` 跑出 request_throughput=178 req/s 并写进周报，声称「服务性能优秀」。请指出这份基线的三个问题，并写出可复现基线的正确命令要点（含 goodput 与保存）。

### 站内答案

结论：三个问题——(1) `--request-rate inf` 是无背压饱和测试，178 req/s 不代表任何在线负载形态，与真实请求到达率无关；(2) 基线没有记录数据集长度分布与负载参数，其他运行无法与之对比；(3) 只存了 `--save-result` 全量 JSON 但没声明 SLO，无法判断请求是否达到业务目标（goodput 为 None）。机制：`calculate_metrics` 的 `request_throughput = completed / dur_s`，`request-rate=inf` 时全部请求在时间 0 发出、`dur_s` 是全部请求跑完的时长，测得的是「单实例饱和吞吐上界」而非服务吞吐；goodput 分支（L622-645）只在 `--goodput` 声明时计算，未声明则 `request_goodput=None`。源码证据：`BenchmarkMetrics`（serve.py L321-354）的 `request_throughput/request_goodput` 字段、`calculate_metrics`（L556-735）的 completed/dur_s 与 goodput 判定、`parse_goodput`/`check_goodput_args`（L1362-1398）；官方输出结构见 Benchmark CLI 的 Online Benchmark 一节。可运行验证：把本课示例的 `calculate_metrics` 用 `dur_s=5.78`、completed=10 跑一遍，断言 `request_throughput≈1.73`；再对慢请求用 `goodput_ms={"ttft":800,"tpot":80,"e2el":25000}` 断言 e2el 超标时 goodput=0。工程取舍：正确基线应固定负载形态——`--request-rate 4 --burstiness 1 --max-concurrency 16` 模拟在线泊松流量，`--random-input-len 1024 --random-output-len 256` 固定长度分布，`--percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,95,99 --goodput ttft:800 tpot:80 e2el:25000 --save-result --save-detailed --result-filename baseline.json`；回归时重跑同命令 diff 分位数字段，TTFT p99 上升超过阈值即回退。适用边界：饱和吞吐（inf）适合容量上界评估（配合 vllm-01-10 的容量方程），受控负载适合 SLO 验收与回归；burstiness 影响 p99 形状（0.1 突发 vs 5.0 均匀），报告必须标注；多模态/embedding 基线有独立指标分支，本课结论针对文本生成任务。
