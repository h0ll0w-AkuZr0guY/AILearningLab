[Usage Metrics · General Metrics](https://docs.vllm.ai/en/latest/usage/metrics/#general-metrics) 列出三类指标：Counter（`vllm:generation_tokens`、`vllm:prompt_tokens`、`vllm:request_success`）、Gauge（`vllm:num_requests_running`、`vllm:num_requests_waiting`、`vllm:kv_cache_usage_perc`）、Histogram（`vllm:time_to_first_token_seconds`、`vllm:inter_token_latency_seconds`、`vllm:e2e_request_latency_seconds`、`vllm:request_queue_time_seconds` 等）——这是指标口径的官方定义；[Design · Metrics](https://docs.vllm.ai/en/latest/design/metrics/) 的 Interval Calculations 一节声明五个区间（queue/prefill/decode/inference/inter-token）由引擎核记录 QUEUED/SCHEDULED/NEW_TOKENS 事件时间戳计算，前端无法自行推算——这是「为什么需要引擎核埋点」的权威解释。累计实现见 `vllm/v1/metrics/stats.py` 的 `IterationStats`。版本边界 v0.26.0。

### 逐段讲解

- `IterationStats`（L349-375）：每次 engine core 迭代的统计容器，字段 `num_generation_tokens`、`prompt_token_stats`、`time_to_first_tokens_iter`、`inter_token_latencies_iter`、`max_num_generation_tokens_iter`——分别对应 generation tokens 累计、prompt tokens 累计、TTFT 样本列表、ITL 样本列表与每步最大生成数。
- `update_from_events`（L428-450）：消费 QUEUED/SCHEDULED/PREEMPTED 事件：QUEUED 写 `queued_ts`，首次 SCHEDULED 写 `scheduled_ts`（`if req_stats.scheduled_ts == 0.0` 防止抢占覆盖），PREEMPTED 累计 `num_preempted_reqs`——区间计算的时间锚点都在这里固化。
- `update_from_output`（L377-426）：`num_new_generation_tokens = len(output.new_token_ids)` 累加到 `num_generation_tokens`；`is_prefilling` 时记录 TTFT（`_time_since(arrival_time)`）并固化 `first_token_ts`；否则记录 `itl = engine_core_timestamp - last_token_ts` 到 `inter_token_latencies_iter`，并推进 `last_token_ts`。
- `update_from_finished_request`（L452-529）：请求结束时计算 `e2e_latency = _time_since(arrival_time)`、`queued_time = scheduled_ts - queued_ts`、`prefill_time = first_token_ts - scheduled_ts`、`decode_time = last_token_ts - first_token_ts`、`inference_time = last_token_ts - scheduled_ts`、`mean_time_per_output_token = decode_time / (num_generation_tokens - 1)`——五个区间与 TPOT 均值一次算出。
- `PromptTokenStats`（L301-347）：按来源拆分 prompt token（computed/cached/local_cache_hit/external），`total` 对应 `vllm:prompt_tokens` 计数器——前缀缓存命中与重算的 token 分开统计。

### 源码节选

```python
class IterationStats:
    def __init__(self) -> None:
        self.num_generation_tokens = 0                 # 本次迭代生成 token 数
        self.prompt_token_stats = PromptTokenStats()   # prompt token 按来源拆分
        self.max_num_generation_tokens_iter: list[int] = []
        self.inter_token_latencies_iter: list[float] = []   # ITL/TPOT 样本
        self.time_to_first_tokens_iter: list[float] = []    # TTFT 样本

    def update_from_events(self, events, req_stats) -> None:
        for event in events:
            if event.type == EngineCoreEventType.QUEUED:
                req_stats.queued_ts = event.timestamp
            elif event.type == EngineCoreEventType.SCHEDULED:
                if req_stats.scheduled_ts == 0.0:      # 首次 SCHEDULED 才写
                    req_stats.scheduled_ts = event.timestamp
            elif event.type == EngineCoreEventType.PREEMPTED:
                self.num_preempted_reqs += 1

    def update_from_output(self, output, engine_core_timestamp,
                           is_prefilling, req_stats, ...) -> None:
        num_new_generation_tokens = len(output.new_token_ids)
        self.num_generation_tokens += num_new_generation_tokens
        if is_prefilling:
            first_token_latency = self._time_since(req_stats.arrival_time)
            self.time_to_first_tokens_iter.append(first_token_latency)
            req_stats.first_token_ts = engine_core_timestamp
        else:
            itl = engine_core_timestamp - req_stats.last_token_ts
            self.inter_token_latencies_iter.append(itl)
        req_stats.num_generation_tokens += num_new_generation_tokens
        req_stats.last_token_ts = engine_core_timestamp

    def update_from_finished_request(self, finish_reason, request_id,
                                     num_prompt_tokens, max_tokens_param,
                                     req_stats, ...) -> None:
        e2e_latency = self._time_since(req_stats.arrival_time)
        queued_time = req_stats.scheduled_ts - req_stats.queued_ts
        prefill_time = req_stats.first_token_ts - req_stats.scheduled_ts
        decode_time = req_stats.last_token_ts - req_stats.first_token_ts
        inference_time = req_stats.last_token_ts - req_stats.scheduled_ts
        mean_time_per_output_token = (
            decode_time / (req_stats.num_generation_tokens - 1)
            if req_stats.num_generation_tokens - 1 > 0 else 0
        )
        ...
```

## 导读

vLLM 的 `/metrics` 有几十个指标，但真正回答「服务快不快、吞吐多大」的只有一小撮，而它们的口径极易误读：`vllm:generation_tokens` 是累计计数器不是速率，`vllm:prompt_tokens` 只算 prefill token 不算 decode token，`vllm:e2e_request_latency_seconds` 是直方图不是单个数字。本课把这些指标按 Counter/Gauge/Histogram 三类拆开，落到 stats.py 的累计逻辑上，让你能正确回答「这个实例每秒到底处理多少 token、p99 延迟多少」。

先建立反例：监控面板显示 `vllm:generation_tokens` 在 5 秒内从 1,000,000 涨到 1,300,000，有人直接报告「吞吐 60k token/s」。正确算法是用 `rate()` 求变化率：`rate(vllm:generation_tokens_total[5m])` 才是每秒生成速率；直接把累计值当速率会随实例运行时间无限增长，是新手最常见的口径错误。

本课与前课的关系：vllm-01-02 讲 TTFT/TPOT 四段区间怎么从时间戳算，vllm-01-07 讲 SLO 怎么用分位数验收——本课把这些区间与累计量映射到 `/metrics` 的具体指标名与 PromQL 查询方式，是「源码到可观测」的桥梁。拆分理由：指标的口径定义（本课）与「用指标做 SLO 管理」（01-07）各自有独立失败模式——前者错在单位换算，后者错在统计目标。

## 分章正文

### 三类指标：Counter、Gauge 与 Histogram

kicker: "01 · OBSERVE"

Prometheus 三类指标语义完全不同：Counter 单调递增（`vllm:generation_tokens`、`vllm:prompt_tokens`、`vllm:request_success`、`vllm:num_preemptions`），Gauge 上下波动（`vllm:num_requests_running`、`vllm:num_requests_waiting`、`vllm:kv_cache_usage_perc`），Histogram 记录样本分布（`vllm:time_to_first_token_seconds`、`vllm:inter_token_latency_seconds`、`vllm:e2e_request_latency_seconds`、`vllm:iteration_tokens_total`、`vllm:request_queue_time_seconds`）。

规则：Counter 必须用 `rate()` 或 `increase()` 看变化率，直接读值没有意义；Gauge 直接读值；Histogram 用 `histogram_quantile()` 取分位数。违反这个规则是绝大多数指标误读的根源。

#### 本章结论

Counter 用 rate、Gauge 直读、Histogram 用 histogram_quantile——先分类再查询。

### 吞吐的两根柱子：prompt 与 generation

kicker: "02 · MODEL"

吞吐要拆两半：`vllm:prompt_tokens`（prefill 阶段处理的输入 token，按来源拆分：本地计算/缓存命中/外部传输）与 `vllm:generation_tokens`（生成的输出 token）。两者合起来是引擎真正处理的 token 总量，但语义完全不同：prompt token 是「输入成本」，generation token 是「输出产品」。`vllm:iteration_tokens_total` 直方图记录每次 engine step 处理的 token 数（含两者），用于观察单步 batch 大小。

`request_success` 计数器按完成原因（stop/length/abort/error）记录请求结果，配合 `request_max_num_generation_tokens` 直方图能看出「请求要多少输出、实际完成多少」——如果大量 `length` 完成且 `max_tokens` 直方图顶到上限，说明客户端的 max_tokens 设置限制了生成长度。

#### 本章结论

吞吐 = prompt_tokens（输入成本）+ generation_tokens（输出产品）；iteration_tokens 观察单步 batch；request_success 按原因统计请求结果。

### 延迟四直方图与 TPOT 均值

kicker: "03 · SOURCE"

四个延迟直方图：`time_to_first_token_seconds`（TTFT）、`inter_token_latency_seconds`（ITL，即 TPOT 样本）、`e2e_request_latency_seconds`（端到端）、`request_queue_time_seconds`（排队）。它们的样本来源在 stats.py 中：TTFT 在 `update_from_output` 的 `is_prefilling` 分支用 `_time_since(arrival_time)` 记录；ITL 在非 prefill 分支用相邻 token 时间差记录；e2e 与 queue time 在 `update_from_finished_request` 从 arrival/queued/scheduled/first/last 时间戳推出。

`request_time_per_output_token_seconds` 直方图记录每个请求的 `mean_time_per_output_token`（TPOT 均值）——与 `inter_token_latency_seconds` 的区别：前者是「每个请求的 decode 平均间隔」样本，后者是「每次 token 间隔」样本，两者统计粒度不同，数值接近但不相等。

#### 本章结论

四个延迟直方图对应五个区间中的四个；TTFT/ITL 在输出到达时记录，e2e/queue 在请求结束时结算；TPOT 均值与 ITL 统计粒度不同。

### 事件时间戳的因果链

kicker: "04 · FAILURE"

区间计算的正确性依赖引擎核按顺序记录事件：QUEUED（入队）→ SCHEDULED（首次调度）→ NEW_TOKENS（首 token）→ … → NEW_TOKENS（末 token）。三个失败边界：

1. **抢占重排**：请求被抢占后再次 SCHEDULED，`update_from_events` 用 `if scheduled_ts == 0.0` 只记首次——否则排队时间会被抢占后的调度时间覆盖，queue_time 失真。设计文档明确：decode 期间抢占影响 ITL/decode/inference 区间，prefill 期间抢占影响 TTFT/prefill 区间。
2. **arrival 与 engine 时间源混用**：`arrival_time` 是前端墙钟（`time.time()`），`*_ts` 是引擎核单调时间，TTFT 用 `_time_since(arrival_time)` 混用两者——文档承认这是设计事实，跨进程时钟偏移会引入少量误差。
3. **单 token 响应**：`num_generation_tokens - 1 = 0` 时 `mean_time_per_output_token` 取 0（per-request metrics 字段为 null），直方图不产生 TPOT 样本——空响应不参与 TPOT 统计。

#### 本章结论

区间依赖事件时间戳因果链；抢占不覆盖 scheduled_ts；arrival 与引擎时间混用是设计事实；单 token 响应无 TPOT 样本。

### 指标口径的工程取舍

kicker: "05 · ENGINEERING"

vLLM 把「区间计算」放在引擎核而不是前端，是因为前端看不到 QUEUED/SCHEDULED 事件的精确时刻（设计文档原文 "the frontend does not have visibility into the timing of the QUEUED and SCHEDULED events"）。代价是引擎核每步都要处理事件流并维护每个请求的时间戳状态，高并发下 `IterationStats` 成为 CPU 热点——官方因此提示 per-request metrics 在高并发下开销不可忽略（`--enable-per-request-metrics` 文档）。取舍：聚合直方图（/metrics）开销小、粒度粗；逐请求 metrics 精确、开销大。生产上默认用直方图，需要账单/SLA 审计才开 per-request。

#### 本章结论

区间计算放引擎核是「前端无事件可见性」的必然；聚合直方图与逐请求 metrics 是开销/精度的取舍。

### 怎么验证：PromQL 查询口径

kicker: "06 · VERIFY"

正确查询模板：生成吞吐 `rate(vllm:generation_tokens_total[5m])`；输入吞吐 `rate(vllm:prompt_tokens_total[5m])`；p99 TTFT `histogram_quantile(0.99, rate(vllm:time_to_first_token_seconds_bucket[5m]))`；运行/等待深度直接读 gauge；KV 使用率 `vllm:kv_cache_usage_perc`；排队 p95 `histogram_quantile(0.95, rate(vllm:request_queue_time_seconds_bucket[5m]))`。本课示例离线复现三类指标与五区间的换算，验证「累计值 ≠ 速率」与「均值 ≠ p99」两个核心口径。

#### 本章结论

用 rate/histogram_quantile 查询吞吐与分位数；离线用示例验证指标口径换算。

## 核心机制

- Counter 用 rate/increase，Gauge 直读，Histogram 用 histogram_quantile。
- 吞吐 = prompt_tokens（输入）+ generation_tokens（输出），iteration_tokens 观察单步 batch。
- 五区间由 QUEUED/SCHEDULED/NEW_TOKENS 事件时间戳计算，前端无事件可见性。
- 抢占不覆盖 scheduled_ts（`if == 0.0`），decode/prefill 抢占影响不同区间。
- arrival_time 用墙钟、*_ts 用单调时间，混用是设计事实。
- 聚合直方图与逐请求 metrics 是开销/精度取舍，默认用直方图。

## 常见误区

- 把 Counter 累计值当速率；必须 `rate()` 才有意义。
- 用平均值当延迟指标；分位数才反映长尾（vllm-01-07 已论证）。
- 混淆 `request_time_per_output_token_seconds`（请求级 TPOT 均值）与 `inter_token_latency_seconds`（token 级间隔）。
- 以为前端能自己算区间；QUEUED/SCHEDULED 事件只在引擎核可见。
- 忽略 `request_success` 的完成原因维度；大量 length 完成说明 max_tokens 设小了。

```python
def interval_from_timestamps(t: dict[str, float]) -> dict[str, float]:
    """从事件时间戳算出五个区间（与 stats.py 同构）。"""
    return {
        "queued": t["scheduled"] - t["queued"],
        "prefill": t["first_token"] - t["scheduled"],
        "decode": t["last_token"] - t["first_token"],
        "inference": t["last_token"] - t["scheduled"],
        "e2e": t["finished"] - t["arrival"],
    }
```

## 可运行示例

```python
def rate(counter: list[float], window_seconds: float) -> float:
    """Counter 的变化率：rate() 语义。"""
    return (counter[-1] - counter[0]) / window_seconds


def quantile_from_histogram(percentile: float,
                            buckets: dict[float, int]) -> float:
    total = sum(buckets.values())
    target = percentile * total
    acc = 0
    prev_bound, prev_acc = 0.0, 0
    for bound, count in sorted(buckets.items()):
        acc += count
        if acc >= target:
            frac = (target - prev_acc) / (acc - prev_acc) if count else 0
            return prev_bound + frac * (bound - prev_bound)
        prev_bound, prev_acc = bound, acc
    return prev_bound


def intervals(t: dict[str, float], num_generation_tokens: int) -> dict[str, float]:
    """复刻 stats.py update_from_finished_request 的五区间 + TPOT 均值。"""
    out = {
        "queued": t["scheduled"] - t["queued"],
        "prefill": t["first_token"] - t["scheduled"],
        "decode": t["last_token"] - t["first_token"],
        "inference": t["last_token"] - t["scheduled"],
        "e2e": t["finished"] - t["arrival"],
    }
    out["mean_tpot"] = (
        out["decode"] / (num_generation_tokens - 1)
        if num_generation_tokens - 1 > 0 else 0.0
    )
    return out


# ---- 断言 1：累计值不是速率 ----
generation_counter = [1_000_000, 1_100_000, 1_200_000, 1_300_000]
assert 300_000 / 300.0 == 1000.0                  # 5 分钟窗口 rate=1000/s
assert rate(generation_counter, 300.0) == 1000.0
assert generation_counter[-1] != rate(generation_counter, 300.0)  # 值≠速率

# ---- 断言 2：五区间计算 ----
t = {"arrival": 100.0, "queued": 101.0, "scheduled": 105.0,
     "first_token": 106.0, "last_token": 116.0, "finished": 117.0}
iv = intervals(t, num_generation_tokens=101)
assert iv["queued"] == 4.0                         # 105 - 101
assert iv["prefill"] == 1.0                        # 106 - 105
assert iv["decode"] == 10.0                        # 116 - 106
assert iv["inference"] == 11.0                     # 116 - 105
assert abs(iv["e2e"] - 17.0) < 1e-9                # 117 - 100
assert abs(iv["mean_tpot"] - 0.1) < 1e-9           # 10 / (101-1)

# ---- 断言 3：单 token 响应 TPOT 为 0（与 per-request null 一致）----
iv1 = intervals(t, num_generation_tokens=1)
assert iv1["mean_tpot"] == 0.0

# ---- 断言 4：分位数 vs 均值（90 快 + 10 慢 → p95 暴露长尾）----
ttft_samples = [100] * 90 + [20000] * 10
buckets: dict[float, int] = {}
for s in ttft_samples:
    b = (s // 1000 + 1) * 1000.0
    buckets[b] = buckets.get(b, 0) + 1
p95 = quantile_from_histogram(0.95, buckets)
mean = sum(ttft_samples) / len(ttft_samples)
assert p95 > 10000 and mean < 3000                 # p95 远大于均值

# ---- 断言 5：抢占不覆盖 scheduled_ts（首次写入语义）----
def update_scheduled(scheduled_ts: float, event_ts: float) -> float:
    return scheduled_ts if scheduled_ts != 0.0 else event_ts


sched = 0.0
sched = update_scheduled(sched, 105.0)            # 首次 SCHEDULED
sched = update_scheduled(sched, 130.0)            # 抢占后再次 SCHEDULED
assert sched == 105.0                             # 保持首次值，queue 不虚增

# ---- 断言 6：prompt/generation 拆分 ----
prompt_total, generation_total = 400_000, 900_000
assert prompt_total + generation_total == 1_300_000
```

## 搭积木复现

### 积木 1：实现 rate 语义

实现 `rate(counter, window)`，断言 `(末值-首值)/窗口` 与直接读末值不同——钉死「Counter 要 rate」。

### 积木 2：实现五区间换算

实现 `intervals()`（复刻 update_from_finished_request），用一组时间戳断言 queued/prefill/decode/inference/e2e 各自等于相邻时间戳之差。

### 积木 3：实现 TPOT 均值与单 token 边界

加入 `mean_tpot = decode / (tokens-1)`，断言 101 token 时 0.1、1 token 时 0——对应 per-request 字段 null 语义。

### 积木 4：实现直方图分位数

实现 `quantile_from_histogram`，用 95 快 + 5 慢的长尾样本断言 p95 > 15s 而均值 < 2s——分位数与均值分离。

### 积木 5：实现首次 SCHEDULED 保护

## 自检

### 问题

监控显示 `vllm:generation_tokens` 累计值 5 分钟内从 2,000,000 涨到 2,600,000，`vllm:prompt_tokens` 从 500,000 涨到 600,000；同时 `vllm:time_to_first_token_seconds` 直方图 p99 为 1.5s、均值 0.3s。请写出正确查询与解读：这 5 分钟的生成/输入吞吐各是多少？p99 TTFT 与均值差 5 倍说明什么？为什么不能用累计值直接报告吞吐？

### 站内答案

结论：生成吞吐 = (2,600,000 - 2,000,000)/300 = 2000 token/s，输入吞吐 = (600,000 - 500,000)/300 ≈ 333 token/s；p99 1.5s vs 均值 0.3s 说明存在长尾（少数请求 TTFT 远超中位数），均值被大量短请求稀释；累计值随时间无限增长，必须用 rate() 求变化率。机制：`vllm:generation_tokens` 与 `vllm:prompt_tokens` 是 Counter（单调递增），Prometheus 语义要求 `rate(vllm:generation_tokens_total[5m])` 才有速率意义；TTFT 直方图样本在 stats.py `update_from_output` 的 `is_prefilling` 分支用 `_time_since(arrival_time)` 记录（L377-426），`histogram_quantile(0.99, rate(vllm:time_to_first_token_seconds_bucket[5m]))` 返回分位数。源码证据：`IterationStats` 字段定义与 `update_from_output`/`update_from_finished_request`（stats.py L349-529）、`PromptTokenStats` 按来源拆分 prompt token（L301-347）；官方口径见 Usage Metrics · General Metrics 与 Design · Metrics 的 Interval Calculations。可运行验证：本课示例断言 1 验证 `rate()` 与累计值不同、断言 2 验证五区间换算、断言 4 验证 p99 与均值分离。工程取舍：用直方图监控（开销小、支持分位数）满足日常排障；需要单请求审计才开 `--enable-per-request-metrics`（官方提示高并发下 CPU 开销不可忽略）；告警应基于 p99/p95 与 burn rate 而非均值。适用边界：指标名在 v0.26.0 有效，版本升级可能改名（官方 Deprecation Policy 允许 `--show-hidden-metrics-for-version` 过渡）；多模型/多 LoRA 时指标带 model_name 标签需分组查询；spec decode 的草稿 token 计入 generation 统计但实际不是最终输出，精确输出量需另算。
