## 官方入口

title: "Engine Arguments · CacheConfig"
url: "https://docs.vllm.ai/en/latest/configuration/engine_args/#cacheconfig"

[CacheConfig 参数区](https://docs.vllm.ai/en/latest/configuration/engine_args/#cacheconfig)对 `--gpu-memory-utilization` 的官方定义是「The fraction of GPU memory to be used for the model executor」（用于 model executor 的 GPU 显存比例），默认 0.92，并明确说明它是 per-instance 上限、与同卡其他实例无关；同页的 `--kv-cache-memory-bytes` 可以跳过自动 profiling、直接指定每 GPU 的 KV cache 字节数。本课拆开这个「比例」的基数到底是哪一块内存，以及 KV cache 字节如何变成块数。版本边界 v0.26.0。

### 逐段讲解

- `request_memory`（`vllm/v1/worker/utils.py` L425-445）算出「申请额」：`requested_memory = ceil(total_memory * gpu_memory_utilization)`，基数是一整张卡的**总显存**；若当前空闲显存小于申请额直接抛 ValueError，提示降低 utilization 或减少同卡占用。
- `determine_available_memory` 先跑一次 `profile_run()`（用 dummy 输入做一次完整 forward），测量三块非 KV 开销：权重内存、激活峰值增量（`torch_peak_increase`）、非 torch 内存增量；可选的 CUDA graph 内存估计也在此计入。
- KV 可用内存公式：`available_kv_cache_memory_bytes = requested_memory - non_kv_cache_memory - cudagraph_memory_estimate`，即「申请额 - 模型与运行时开销 = KV cache 余量」，而不是「总显存 - 已用 = 余量」。
- 如果指定了 `kv_cache_memory_bytes`，直接跳过 profiling 结果，日志明确提示该模式「does not respect the gpu_memory_utilization config」。
- 字节到块：`get_kv_cache_configs`（`vllm/v1/core/kv_cache_utils.py` L2036 起）用 `available_memory // bytes_per_block` 得到每个 worker 的 `num_blocks`，多卡取各 rank 的最小值以保证一致。

### 源码节选

```python
# vllm/v1/worker/utils.py
def request_memory(init_snapshot: MemorySnapshot, cache_config: CacheConfig) -> int:
    """Calculate the amount of memory required by vLLM, then validate
    that the current amount of free memory is sufficient for that."""
    requested_memory = math.ceil(
        init_snapshot.total_memory * cache_config.gpu_memory_utilization
    )                                   # 基数 = 总显存，不是空闲显存
    if init_snapshot.free_memory < requested_memory:
        raise ValueError(
            f"Free memory on device {init_snapshot.device_} "
            f"({format_gib(init_snapshot.free_memory)}/"
            f"{format_gib(init_snapshot.total_memory)} GiB) on startup "
            f"is less than desired GPU memory utilization "
            f"({cache_config.gpu_memory_utilization}, "
            f"{format_gib(requested_memory)} GiB). Decrease GPU memory "
            f"utilization or reduce GPU memory used by other processes."
        )
    return requested_memory

# vllm/v1/worker/gpu_worker.py
@torch.inference_mode()
def determine_available_memory(self) -> int:
    if kv_cache_memory_bytes := self.cache_config.kv_cache_memory_bytes:
        # 手工指定模式：跳过 profiling，忽略 gpu_memory_utilization
        self.model_runner.profile_run()
        logger.info(msg)   # 日志明确提示不尊重 utilization 配置
        return self._reserve_mm_ipc_gpu_memory(kv_cache_memory_bytes)

    with memory_profiling(
        self.init_snapshot,
        weights_memory=int(self.model_runner.model_memory_usage),
    ) as profile_result:
        self.model_runner.profile_run()      # 一次 dummy forward 测量峰值
        profile_torch_peak = torch.accelerator.memory_stats(self.device).get(
            "allocated_bytes.all.peak", 0
        )
        # CUDA graph 内存估计（默认开启，v0.21.0 起）
        cudagraph_memory_estimate = self.model_runner.profile_cudagraph_memory()

    profile_result.non_kv_cache_memory = (
        profile_result.non_torch_increase
        + profile_result.torch_peak_increase
        + profile_result.weights_memory
    )
    free_gpu_memory = profile_result.after_profile.free_memory
    self.available_kv_cache_memory_bytes = (
        self.requested_memory
        - profile_result.non_kv_cache_memory
        - cudagraph_memory_estimate_applied
    )   # KV cache = 申请额 - 模型/激活/graph 开销
    return self._reserve_mm_ipc_gpu_memory(
        int(self.available_kv_cache_memory_bytes)
    )
```

删减说明：省略了多模态 IPC 显存预留（`_reserve_mm_ipc_gpu_memory`）、`max_model_len=-1` 自动适配与 `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` 环境开关的完整日志分支；被删逻辑不影响「基数 = 总显存」与「KV = 申请额 - 非 KV 开销」两个核心公式，但视频等多模态场景还会额外预留 IPC 共享内存。

## 导读

把「0.92」翻译错，是 vLLM 显存排障里最常见的一类错误。有人以为它表示「KV cache 最多用 92% 的显存」，有人以为基数是「当前空闲显存」。两者都会在实际部署中翻车：模型权重已经吃掉 40GB，`0.92 × 80GB = 73.6GB` 的申请额减去权重和激活后，KV cache 只分到十几 GB，并发一上来就 OOM；或者同卡还跑着别的实例，空闲显存只有 30GB，`0.92` 直接触发启动期 ValueError。

本课把公式拆到底：`requested = ceil(total × util)` → `kv_bytes = requested − weights − peak_activations − cudagraph` → `num_blocks = kv_bytes // bytes_per_block`。看懂这条链，就能解释「为什么调大 utilization 不一定让 KV 变大」「为什么同卡跑两个实例要各自按比例让路」「为什么 kv-cache-memory-bytes 是最后的兜底手段」。第三课说的「KV 块不足触发抢占」，根源就在这里。

## 分章正文

### 一个 0.92 的误会

kicker: "01 · OBSERVE"

在 80GB 的 H100 上启动 Llama-3-70B（fp16 权重约 140GB，显然放不下），换成 Llama-3-8B（权重约 16GB）。日志显示「Available KV cache memory: 58 GiB」——不是 `0.92 × 80 = 73.6`，也不是 `80 − 16 = 64`。为什么？

因为 `requested = ceil(80 × 0.92) ≈ 73.6GB`，减去权重 16GB、激活峰值与 CUDA graph 预留后，KV 只拿到约 58GB。这个数字回答了开头的问题：`gpu_memory_utilization` 是「给 vLLM 这个进程的**总显存预算比例**」，权重、激活、graph 全部从这份预算里出，KV cache 拿的是**余量**。把 0.92 当成「KV 占用比例」或「空闲显存比例」都会错得离谱。

#### 本章结论

0.92 是进程总预算比例；KV cache = 预算 − 模型与运行时开销，不是预算本身。

### 基数：总显存，不是空闲显存

kicker: "02 · BASE"

`request_memory` 源码一行说透：`requested_memory = ceil(total_memory * gpu_memory_utilization)`。基数 `total_memory` 是卡的总容量，与启动时已经有多少空闲无关；紧接着的校验是 `free_memory < requested_memory` 就抛错。也就是说：同卡有其他进程占了 20GB，你仍按 80GB 的 0.92 申请 73.6GB，启动直接失败，并提示「Decrease GPU memory utilization or reduce GPU memory used by other processes」。

这是设计选择而非缺陷：vLLM 假设自己独占申请额内的显存，用 profile 测量「申请额内还剩下多少给 KV」，而不是被动地「有多少空闲用多少」。两个实例同卡部署时，每个实例的 util 必须各自让路（比如都设 0.45），总和不超过 1 且留出系统余量，否则后启动的实例必然报错。

#### 本章结论

基数是卡的总显存；申请额超出空闲时启动期抛错，同卡多实例必须按比例分摊。

### 三个租户：权重、激活、CUDA graph

kicker: "03 · TENANTS"

申请额内部有三个非 KV 租户，全部由 `profile_run()` 的一次 dummy forward 实测得出：`weights_memory`（模型权重，构造 worker 时就已知）、`torch_peak_increase`（激活峰值，profile 前后 PyTorch 分配峰值之差）、`non_torch_increase`（非 torch 运行时内存，如 NCCL 缓冲）。v0.21.0 起 CUDA graph 内存估计也计入（默认开启），避免「graph 捕获后 KV 越界」的经典 OOM。

这三个数字直接决定 KV 余量，也解释了三个常见现象：`max_model_len` 越大激活峰值越高，KV 反而变小；开启 CUDA graph 后日志会提示「等价 utilization 变低」，需要调高 util 维持原来的 KV；量化权重（fp8/INT4）降低 `weights_memory`，KV 余量随之增大。改任何影响峰值显存的参数，都要重新 profile，不要沿用旧日志的数字。

#### 本章结论

权重、激活峰值、CUDA graph 是申请额内的三个固定租户，KV 只拿剩余部分。

### KV 余量的两个公式

kicker: "04 · FORMULA"

核心公式二连：`available_kv_cache_memory_bytes = requested − non_kv_cache_memory − cudagraph_estimate`；随后 `num_blocks = available // bytes_per_block`，其中 `bytes_per_block = block_size × 每 token KV 字节数`（block_size 默认 16 token，每 token KV 字节数由层数、KV heads、head dim 与 dtype 决定）。`get_kv_cache_configs` 在 `vllm/v1/core/kv_cache_utils.py` 里对所有 worker 汇总后取最小块数，保证 TP/PP 各 rank 一致。

把两个公式连起来就能做预算：80GB 卡、util 0.92、非 KV 开销 15.6GB（含 graph）→ KV ≈ 58GB；若每 token KV 为 0.4KB（8B 模型典型值），则 `58GB / (16 × 0.4KB) ≈ 9.1M 块`，每个 16-token 块 6.4KB。并发上限 ≈ 块数 ÷ 每请求平均块数——这就是第三课 KV 压力的来源。

#### 本章结论

KV 余量由「预算 − 开销」得出，块数由「余量 ÷ 每块字节」得出，多卡取最小。

### kv_cache_memory_bytes：手工模式的边界

kicker: "05 · MANUAL"

`--kv-cache-memory-bytes` 跳过 profiling，直接以指定字节数作为 KV 内存，日志明确警告它「does not respect the gpu_memory_utilization config」。它的适用场景是：你不想让 profile 的偶发波动影响 KV 大小（例如需要精确复现容量），或者 profiling 本身不稳定。代价是失去了自动保护：如果权重 + 激活 + 指定 KV 之和超过实际显存，启动或运行期直接 OOM，没有任何兜底。

官方文档建议的用法是先跑一次默认配置，从日志读「Available KV cache memory」的建议值，再把它写进 `kv_cache_memory_bytes`；之后如果显存环境变化（同卡其他进程增减），要手工重估。这是「自动 profiling 不可用时」的逃生舱，不是常规配置手段。

#### 本章结论

手工模式以字节为准、忽略 util；稳定但失去 OOM 保护，只能用于明确需要固定 KV 的场景。

### 多卡与多实例的合计口径

kicker: "06 · MULTI"

`gpu_memory_utilization` 的文档强调它是「per-instance limit，只作用于当前 vLLM 实例」。TP/PP 多卡场景下，每张卡独立执行同一套公式（各 rank 空闲显存可能不同），`get_kv_cache_configs` 取最小块数保证一致性——某张卡被别的进程占用更多时，全实例的 KV 被它拉低。多实例场景则要求所有实例的 util 之和留出余量，否则后启动者报 ValueError。

诊断清单：KV 比预期小 → 查 `non_kv_cache_memory`（模型大、激活峰高、graph 估计）；同卡多实例后启动报错 → 查各自 util 之和是否超过 1；TP 卡间 KV 不一致 → 查是否有一张卡被其他进程占用。这些都能在 `vllm serve` 的启动日志里找到数字。

#### 本章结论

per-instance 预算按卡独立计算、全局取最小；多实例分摊 util、TP 检查单卡占用。

## 核心机制

- `requested = ceil(total_memory × gpu_memory_utilization)`，基数是卡的总显存。
- KV 可用 = 申请额 − 权重 − 激活峰值 − CUDA graph 估计，KV 是预算内的余量。
- 块数 = KV 字节 ÷ 每块字节（block_size × 每 token KV 字节），多卡取最小。
- `kv_cache_memory_bytes` 手工模式忽略 util、失去 OOM 保护。

## 常见误区

- 把 0.92 当成「KV cache 占显存比例」；它管的是整个 model executor 的预算。
- 把基数当成空闲显存；基数是总显存，空闲不足时启动期直接报错。
- 以为调大 `max_model_len` 只增加 KV；它同时抬高激活峰值，KV 余量可能反而变小。
- 忽略 CUDA graph 估计：不开 graph 预留的旧 util 值在 v0.21.0+ 会让 KV 越界。
- 同卡多实例各自设 0.92，后启动实例必然 ValueError。

## 实现变体

### 变体 A：自动 profiling（默认）

useWhen: "显存环境稳定、独占整卡，希望每次启动根据实测自动决定 KV 大小。"
tradeoff: "获得：自动适配权重/激活/graph 变化，无需手工维护数字；牺牲：profiling 有波动，同配置两次启动的 KV 可能略有差异。"

#### 代码

```python
def auto_kv_bytes(total: int, util: float, non_kv: int, graph: int) -> int:
    requested = math.ceil(total * util)
    return requested - non_kv - graph   # gpu_worker.py 的 available_kv_cache_memory_bytes
```

### 变体 B：kv_cache_memory_bytes 手工固定

useWhen: "需要精确复现容量、profiling 不稳定，或已经用默认配置跑出可靠的建议值。"
tradeoff: "获得：KV 大小完全确定、可复现；牺牲：忽略 util、失去 OOM 兜底，显存环境变化后需手工重估。"

#### 代码

```python
def manual_kv_bytes(kv_cache_memory_bytes: int) -> int:
    return kv_cache_memory_bytes   # 官方文档：先用默认配置跑出建议值再固化
```

## 可运行示例

```python
import math


def request_memory(total_memory: int, gpu_memory_utilization: float,
                   free_memory: int) -> int:
    """复刻 worker/utils.py 的 request_memory。"""
    requested = math.ceil(total_memory * gpu_memory_utilization)
    if free_memory < requested:
        raise ValueError(
            f"Free memory {free_memory} < requested {requested}: "
            "decrease gpu_memory_utilization"
        )
    return requested


def available_kv_bytes(requested: int, non_kv: int, cudagraph: int) -> int:
    """复刻 gpu_worker.py 的 available_kv_cache_memory_bytes。"""
    return requested - non_kv - cudagraph


def num_blocks(kv_bytes: int, bytes_per_block: int) -> int:
    return kv_bytes // bytes_per_block   # kv_cache_utils.py：available // bytes_per_block


# 80GB 卡、util 0.92、权重 16GB、激活峰值 1.2GB、graph 1.0GB
total = 80 * 1024**3
free = 78 * 1024**3                      # 同卡已用 2GB（例如别的进程）
requested = request_memory(total, 0.92, free)
assert requested == math.ceil(total * 0.92)
non_kv = 16 * 1024**3 + int(1.2 * 1024**3) + int(0.8 * 1024**3)
graph = int(1.0 * 1024**3)
kv = available_kv_bytes(requested, non_kv, graph)
# 58GiB 量级：权重与运行时开销从预算内扣除，KV 是余量
assert kv < 0.92 * total and kv < total - 16 * 1024**3

# 块数：block_size=16、每 token KV 0.4KB
bytes_per_block = 16 * int(0.4 * 1024)
blocks = num_blocks(kv, bytes_per_block)
assert blocks == kv // bytes_per_block

# 同卡多实例：util 之和超过 1 时后启动者报错（空闲 8GB < 申请 73.6GB）
try:
    request_memory(80 * 1024**3, 0.92, int(8 * 1024**3))
    raise AssertionError("must fail: free < requested")
except ValueError:
    pass

# 手工模式：忽略 util，直接用字节数
kv_manual = 40 * 1024**3
assert kv_manual != available_kv_bytes(requested, non_kv, graph)

# max_model_len 变大 -> 激活峰值升高 -> KV 余量变小（反直觉现象）
kv_small_act = available_kv_bytes(requested, non_kv + int(2 * 1024**3), graph)
assert kv_small_act < kv
```

## 自检

### 问题

80GB 卡上部署 8B 模型（fp16 权重 16GB），`gpu_memory_utilization=0.92`，启动日志显示 Available KV cache memory 约 58GB，而你的预期是 73.6GB。请解释 15.6GB 差在哪，写出 KV 余量与块数的完整公式，并说明同卡再起一个 0.92 实例会发生什么。

### 站内答案

结论：`requested = ceil(80GB × 0.92) ≈ 73.6GB` 是进程总预算，权重 16GB、激活峰值约 1.2GB、CUDA graph 估计约 1GB、非 torch 运行时约 0.8GB 都从预算内扣除，KV 余量 ≈ 73.6 − 19 ≈ 54.6GB（量级与日志一致）；再起一个 0.92 实例时，后启动者按总显存申请 73.6GB，而空闲已不足，启动期抛 ValueError。机制：`request_memory`（worker/utils.py L425-445）以 `total_memory` 为基数；`determine_available_memory`（gpu_worker.py L448-615）用 `profile_run` 实测非 KV 开销后，`available_kv_cache_memory_bytes = requested − non_kv − cudagraph`；`get_kv_cache_configs`（kv_cache_utils.py L2036 起）再以 `available // bytes_per_block` 求块数，多卡取最小。可运行验证：把本课示例的数值代入 `request_memory` 与 `available_kv_bytes`，断言 KV < 0.92 × total 且 KV < total − weights；再调用一次 `request_memory(total, 0.92, 8GB)` 断言抛 ValueError。工程取舍：自动 profiling 让 KV 自适应权重与激活变化，代价是有波动且同配置两次启动可能差几个 GB；需要精确复现时用 `kv_cache_memory_bytes` 手工固定，但官方文档明确提示该模式忽略 util、环境变化后要重估，且失去 OOM 兜底。适用边界：本公式针对纯文本模型；多模态（视频）场景 `_reserve_mm_ipc_gpu_memory` 会再扣一块 IPC 共享内存，`max_model_len=-1` 会自动适配长度，这两条路径的 KV 余量会进一步变化。
